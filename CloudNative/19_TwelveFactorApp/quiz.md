## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | B | Один репозиторий — множество деплоев в разные среды. Различия только в конфигурации. |
| 2 | C | Конфигурация хранится в environment variables, не в коде или файлах репозитория. |
| 3 | B | База данных — attached resource, подключаемый через URL. Смена БД не требует изменения кода. |
| 4 | B | Процессы должны быть stateless — без shared state в памяти. State хранится во внешних сервисах. |
| 5 | B | Приложение само экспортирует HTTP (или другой) сервис, слушая порт. Не зависит от внешнего веб-сервера. |
| 6 | C | Build (компиляция) → Release (build + config) → Run (запуск процессов). |
| 7 | C | Логи пишутся в stdout. Система (Docker, K8s) собирает и агрегирует их. |
| 8 | D | SQLite в dev и PostgreSQL в prod — нарушение parity. Нужны одинаковые сервисы везде. |
| 9 | B | Горизонтальное масштабирование через добавление процессов/контейнеров. |
| 10 | B | Disposability = быстрый запуск (секунды) и graceful shutdown (обработка SIGTERM). |
| 11 | B | Зависимости явно объявлены в manifest (requirements.txt) и изолированы (virtualenv, container). |
| 12 | B | Admin tasks выполняются как one-off процессы в том же environment, с тем же кодом и конфигом. |
| 13 | B | Если можно сделать код open-source без раскрытия секретов — конфигурация правильно отделена. |
| 14 | B | Смена backing service = смена URL в environment variable. Код не меняется. |
| 15 | C | Состояние сессии хранится во внешнем хранилище (Redis, DB), не в памяти процесса. |

| Результат | Оценка |

| **8-10 (50-69%)** | ⚠️ Удовлетворительно |
| **< 8 (<50%)** | 📚 Нужно повторить |
