## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | C | Один репозиторий — множество деплоев в разные среды. Различия только в конфигурации. |
| 2 | C | Конфигурация хранится в environment variables, не в коде или файлах репозитория. |
| 3 | B | База данных — attached resource, подключаемый через URL. Смена БД не требует изменения кода. |
| 4 | C | Процессы должны быть stateless — без shared state в памяти. State хранится во внешних сервисах. |
| 5 | C | Приложение само экспортирует HTTP (или другой) сервис, слушая порт. Не зависит от внешнего веб-сервера. |
| 6 | A | Build (компиляция) → Release (build + config) → Run (запуск процессов). |
| 7 | A | Логи пишутся в stdout. Система (Docker, K8s) собирает и агрегирует их. |
| 8 | A | SQLite в dev и PostgreSQL в prod — нарушение parity. Нужны одинаковые сервисы везде. |
| 9 | D | Горизонтальное масштабирование через добавление процессов/контейнеров. |
| 10 | C | Disposability = быстрый запуск (секунды) и graceful shutdown (обработка SIGTERM). |
| 11 | B | Зависимости явно объявлены в manifest (requirements.txt) и изолированы (virtualenv, container). |
| 12 | C | Admin tasks выполняются как one-off процессы в том же environment, с тем же кодом и конфигом. |
| 13 | C | Если можно сделать код open-source без раскрытия секретов — конфигурация правильно отделена. |
| 14 | C | Смена backing service = смена URL в environment variable. Код не меняется. |
| 15 | A | Состояние сессии хранится во внешнем хранилище (Redis, DB), не в памяти процесса. |
