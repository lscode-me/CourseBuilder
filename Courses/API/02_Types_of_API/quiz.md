## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | B | Stateless означает, что сервер не хранит состояние между запросами. Каждый запрос содержит всю необходимую информацию для его обработки. |
| 2 | B | POST используется для создания нового ресурса в REST API. GET для чтения, PUT для обновления, DELETE для удаления. |
| 3 | D | GET, PUT, DELETE являются идемпотентными (повторный вызов даёт тот же результат). POST не идемпотентен, так как создаёт новый ресурс. |
| 4 | C | В REST ресурсы идентифицируются через URI. GET /api/users/123 правильно идентифицирует пользователя с ID 123. |
| 5 | B | WSDL (Web Services Description Language) — это язык описания веб-сервисов, формальное описание SOAP API через XML. |
| 6 | D | SOAP подходит для enterprise интеграций с формальными контрактами (WSDL) и требованиями безопасности (WS-Security). |
| 7 | C | RPC фокусируется на вызове методов/функций, REST фокусируется на работе с ресурсами через HTTP методы. |
| 8 | B | JSON-RPC — это спецификация RPC, использующая JSON для кодирования вызовов удалённых процедур. |
| 9 | C | gRPC — это современная реализация RPC от Google, использующая Protocol Buffers (бинарный формат) и HTTP/2 для высокой производительности. |
| 10 | B | Event-based API — это архитектура, где системы взаимодействуют через события вместо традиционных запросов-ответов. |
| 11 | B | Webhook — это способ доставки событий через HTTP POST запросы на URL, указанный клиентом при подписке. |
| 12 | A | Message queues используются для надёжной доставки событий между системами в event-based архитектуре. |
| 13 | D | REST лучше всего подходит для простого CRUD API публичного веб-приложения благодаря простоте и кэшируемости. |
| 14 | A | REST использует стандартные HTTP механизмы кэширования (Cache-Control, ETag), что делает его хорошо подходящим для кэширования. |
| 15 | A | SOAP использует XML формат для всех сообщений (запросов и ответов). |
| 16 | B | Для вызова метода с параметрами RPC подход более подходящий. REST лучше для работы с ресурсами. |
| 17 | D | В event-based API, когда событие публикуется, все подписчики на это событие получают его. |
| 18 | A | gRPC обеспечивает высокую производительность благодаря использованию Protocol Buffers (бинарный формат) и HTTP/2 (мультиплексирование). |
| 19 | B | В REST вложенные ресурсы структурируются через путь: GET /api/users/123/orders получает заказы пользователя 123. |
| 20 | A | SOAP имеет встроенные стандарты безопасности WS-Security, что делает его подходящим для enterprise интеграций. |
| 21 | C | В RPC удалённая процедура вызывается через POST запрос с указанием имени метода и параметров в теле запроса. |
| 22 | D | Event-based API обеспечивает слабую связь (decoupling) — источник события не знает о получателях, что упрощает архитектуру. |
| 23 | A | При успешном создании ресурса REST API должен вернуть статус-код 201 Created. |
| 24 | D | SOAP подходит для enterprise интеграций с распределёнными транзакциями благодаря формальным контрактам и стандартам. |
| 25 | D | Для микросервисов gRPC (RPC) лучше для внутренней коммуникации (высокая производительность), REST для публичных API (простота). |

## Scoring Guide

Подсчитайте количество правильных ответов:

| Результат | Оценка | Рекомендации |
|-----------|--------|--------------|
| **23-25 правильных (90-100%)** | 🏆 Отлично! | Вы отлично усвоили материал. Переходите к следующему модулю. |
| **18-22 правильных (70-89%)** | ✅ Хорошо | Хороший результат! Повторите темы, в которых ошиблись. |
| **13-17 правильных (50-69%)** | ⚠️ Удовлетворительно | Рекомендуется перечитать соответствующие разделы лекции. |
| **Менее 13 правильных (<50%)** | 📚 Нужно повторить | Внимательно перечитайте лекцию и попробуйте ещё раз. |
