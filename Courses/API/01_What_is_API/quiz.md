## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | C | API — это интерфейс, определяющий способ взаимодействия систем. Интеграция — это процесс соединения систем, который использует API. |
| 2 | A | Нарушение контракта ломает интеграцию, так как клиент и сервер перестают понимать формат данных друг друга. |
| 3 | C | Стандарты упрощают интеграцию, обеспечивают совместимость и значительно снижают количество необходимого кода для преобразований. |
| 4 | B | В синхронной интеграции клиент блокируется до получения ответа. В асинхронной клиент может продолжать работу параллельно. |
| 5 | C | Двунаправленная интеграция означает, что данные могут передаваться в обе стороны между системами (A ↔ B). |
| 6 | A | Выбор паттерна зависит от требований, но Hub-and-Spoke обычно лучше масштабируется для большого количества систем. |
| 7 | D | Для N систем без стандартов нужно N*(N-1)/2 адаптеров. Для 10 систем это 45 адаптеров. |
| 8 | B | Интерфейс API скрывает детали реализации, предоставляя стандартный способ взаимодействия без знания внутреннего устройства. |
| 9 | D | Контрактный подход не исправляет ошибки автоматически. Он обеспечивает предсказуемость, независимость и тестируемость. |
| 10 | C | Batch интеграция эффективна для обработки больших объёмов данных, когда не требуется немедленная реакция. |
| 11 | A | Согласно контракту, невалидный email должен возвращать Response 400 с сообщением "Invalid email format". |
| 12 | C | Правильный подход: API должен быть независимым от конкретных интеграций. Интеграция использует API, но не наоборот. |
| 13 | A | JSON API — это стандарт, определяющий единую структуру JSON ответов API. REST — это архитектурный стиль, а не формат данных. |
| 14 | B | Стандарты уменьшают количество необходимых адаптеров, а не увеличивают. Все остальные варианты — преимущества стандартов. |
| 15 | B | Синхронная интеграция предпочтительна, когда клиенту нужен немедленный результат для продолжения работы. |
| 16 | D | Однонаправленная интеграция означает поток данных только в одном направлении (CRM → Analytics). |
| 17 | D | При изменении контракта необходимо использовать версионирование, чтобы не сломать существующих клиентов. |
| 18 | A | Контракт можно тестировать независимо от реализации: проверять формат запросов, ответов, коды ошибок. |
| 19 | B | При Point-to-Point интеграции количество соединений растёт экспоненциально: N*(N-1)/2 для N систем. |
| 20 | D | Формальный контракт (например, OpenAPI) — лучшая форма документации, так как он машиночитаем и может использоваться для генерации кода. |
| 21 | D | Без стандартов каждая пара систем требует отдельного адаптера для преобразования форматов данных. |
| 22 | B | В Hub-and-Spoke центральным узлом является специальный компонент (Integration Hub), который маршрутизирует данные между системами. |
| 23 | C | Асинхронная интеграция позволяет клиенту продолжать работу, не дожидаясь ответа от сервера. |
| 24 | D | Из OpenAPI спецификации можно сгенерировать клиент, сервер, валидировать запросы и создать документацию. |
| 25 | A | Контракт должен быть стабильным, чтобы не ломать существующих клиентов при изменениях. Это критично для надёжности интеграции. |

## Scoring Guide

Подсчитайте количество правильных ответов:

| Результат | Оценка | Рекомендации |
|-----------|--------|--------------|
| **23-25 правильных (90-100%)** | 🏆 Отлично! | Вы отлично усвоили материал. Переходите к следующему модулю. |
| **18-22 правильных (70-89%)** | ✅ Хорошо | Хороший результат! Повторите темы, в которых ошиблись. |
| **13-17 правильных (50-69%)** | ⚠️ Удовлетворительно | Рекомендуется перечитать соответствующие разделы лекции. |
| **Менее 13 правильных (<50%)** | 📚 Нужно повторить | Внимательно перечитайте лекцию и попробуйте ещё раз. |
