## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | A | Authentication проверяет "кто ты" (личность), Authorization проверяет "что тебе разрешено" (права доступа). Это разные этапы безопасности. |
| 2 | A | Сначала Authentication (проверка личности), затем Authorization (проверка прав). Нельзя проверять права, не зная, кто пользователь. |
| 3 | B | API Key — это уникальный ключ, идентифицирующий клиента API. Он используется для аутентификации запросов. |
| 4 | A | API Key следует передавать в заголовке запроса, а не в URL (виден в логах) или теле запроса. |
| 5 | B | Basic Authentication — это метод аутентификации через HTTP заголовок Authorization с username:password, закодированными в Base64. |
| 6 | C | Base64 — это кодирование, не шифрование. Без HTTPS пароль может быть перехвачен, так как легко декодируется. |
| 7 | D | OAuth — это протокол авторизации, позволяющий приложению получать доступ к ресурсам пользователя без передачи пароля. |
| 8 | D | OAuth включает Resource Owner (пользователь), Client (приложение), Authorization Server (выдаёт токены), Resource Server (API). |
| 9 | C | OAuth Scopes определяют права доступа, которые разрешены токену. Например, "read:users" или "write:posts". |
| 10 | B | API Key следует генерировать с помощью криптографически безопасного генератора случайных значений для безопасности. |
| 11 | A | Base64 — это кодирование, которое легко декодируется обратно. Оно не обеспечивает безопасность, только преобразует формат. |
| 12 | A | После успешной OAuth авторизации клиент получает токен доступа (access token) для доступа к защищённым ресурсам. |
| 13 | C | API Key следует хранить в хешированном виде (например, SHA-256) для безопасности, чтобы при утечке нельзя было использовать оригинальный ключ. |
| 14 | D | Формат заголовка: "Basic " + base64(username:password). Base64 кодирование username:password добавляется после "Basic ". |
| 15 | B | Делегирование доступа означает, что пользователь даёт приложению доступ к ресурсам без передачи пароля приложению. |
| 16 | B | API Keys следует использовать для простых API сервер-сервер коммуникации, когда не нужна гибкость в управлении доступом. |
| 17 | D | OAuth flow включает: запрос авторизации, получение кода авторизации, обмен кода на токен, использование токена для доступа. |
| 18 | D | API Keys не имеют встроенного механизма отзыва. Если ключ скомпрометирован, нужно удалить его вручную. |
| 19 | D | Основное ограничение Basic Auth: пароль передаётся в каждом запросе, нет механизма отзыва токенов, ограниченная гибкость. |
| 20 | D | OAuth обеспечивает безопасность без передачи пароля, гибкость через scopes, возможность отзыва токенов, делегирование доступа. |
| 21 | A | Authentication проверяет личность пользователя — кто он, правильные ли учётные данные. |
| 22 | B | Authorization проверяет права доступа пользователя — что ему разрешено делать с ресурсами. |
| 23 | A | Валидация API Key должна происходить на сервере при получении запроса, до обработки данных. |
| 24 | B | Resource Owner в OAuth — это пользователь, владелец ресурсов, к которым приложение запрашивает доступ. |
| 25 | B | Для публичного API с множественными клиентами лучше использовать OAuth, так как он обеспечивает безопасность, гибкость и делегирование доступа. |
