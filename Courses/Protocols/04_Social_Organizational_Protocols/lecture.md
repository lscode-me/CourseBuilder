## 1. Введение: организации как сети протоколов

Организации — это не просто группы людей. Это **сети протоколов** — формализованных договорённостей о том, как люди взаимодействуют для достижения общих целей. Каждый процесс в организации — это протокол: от ежедневных митингов до найма новых сотрудников, от code review до управления инцидентами.

Понимание организационных протоколов критично для:

- Эффективной работы в команде
- Масштабирования организаций
- Создания предсказуемых процессов
- Снижения конфликтов и неопределённости

В этом модуле мы рассмотрим четыре ключевых организационных протокола:

1. **Митинги** — координация синхронного общения
2. **Найм** — процесс добавления новых участников
3. **Code review** — контроль качества кода
4. **Инцидент-менеджмент** — управление кризисными ситуациями

## 2. Протокол митингов

### 2.1 Проблема: координация синхронного общения

**Проблема:** Команде нужно синхронно обсудить вопросы, принять решения, синхронизировать работу. Как обеспечить эффективное использование времени всех участников?

**Решение:** Протокол митинга — формализованная структура синхронного общения.

### 2.2 Структура протокола митинга

**Роли:**

- **Организатор**: готовит agenda, ведёт митинг, следит за временем

- **Участники**: готовят свои вопросы, участвуют в обсуждении, принимают решения

- **Секретарь** (опционально): ведёт notes, документирует решения

**Правила (структура митинга):**

1. **Подготовка** (до митинга):
   - Организатор создаёт agenda с темами и временем
   - Участники готовят материалы по своим темам
   - Agenda отправляется заранее (минимум за день)

2. **Начало митинга**:
   - Митинг начинается вовремя
   - Организатор напоминает agenda и правила
   - Устанавливается таймер для каждой темы

3. **Во время митинга**:
   - Следуем agenda, не отклоняемся без необходимости
   - Каждый говорит по очереди, не перебиваем
   - Фокусируемся на решениях, а не на обсуждении проблем
   - Следим за временем, не превышаем лимит на тему

4. **Принятие решений**:
   - Решения формулируются явно
   - Назначается ответственный за каждое решение
   - Определяются следующие шаги и дедлайны

5. **Завершение митинга**:
   - Резюмируются решения и action items
   - Определяется следующий митинг (если нужен)
   - Notes отправляются участникам

**Ожидания:**

- Участники ожидают, что митинг будет эффективным и по времени
- Организатор ожидает, что участники подготовились
- Все ожидают, что решения будут задокументированы

### 2.3 Типы митингов

**Standup (daily sync):**

- Короткий митинг (15 минут)
- Каждый участник отвечает на 3 вопроса: что сделал, что планирует, есть ли блокеры
- Фокус на синхронизации, не на решении проблем

**Planning:**

- Планирование работы на спринт/период
- Оценка задач, приоритизация
- Определение целей и метрик

**Retrospective:**

- Обсуждение того, что прошло хорошо и что можно улучшить
- Формулирование action items для улучшений
- Фокус на процессе, а не на людях

**Decision-making:**

- Принятие конкретных решений
- Обсуждение вариантов, выбор лучшего
- Документирование решения и обоснования

### 2.4 Нарушения протокола

**Отсутствие agenda:**

- Участники не знают, о чём будет митинг
- Митинг становится неструктурированным
- Теряется время

**Отклонение от agenda:**

- Обсуждение нерелевантных тем
- Превышение времени
- Недостижение целей митинга

**Отсутствие решений:**

- Обсуждение без принятия решений
- Неясность следующих шагов
- Повторное обсуждение тех же вопросов

### 2.5 Применение в технических системах

Протокол митинга применяется в:

- **Синхронные коммуникации** в распределённых системах: координация между сервисами

- **Consensus protocols**: синхронное принятие решений в распределённых системах

- **Event coordination**: синхронизация событий между компонентами

## 3. Протокол найма

### 3.1 Проблема: добавление новых участников

**Проблема:** Организации нужно добавить нового участника (сотрудника), который будет эффективно работать в команде. Как обеспечить правильный выбор и интеграцию?

**Решение:** Протокол найма — формализованная последовательность шагов для оценки и интеграции кандидатов.

### 3.2 Структура протокола найма

**Роли:**

- **Рекрутер/HR**: публикует вакансию, фильтрует резюме, координирует процесс

- **Hiring manager**: определяет требования, принимает финальное решение

- **Интервьюеры**: оценивают кандидатов по разным аспектам (технические, культурные)

- **Кандидат**: проходит процесс, демонстрирует навыки

**Правила (последовательность):**

1. **Определение требований**:
   - Hiring manager определяет роль, требования, компенсацию
   - Создаётся job description

2. **Публикация и поиск**:
   - Вакансия публикуется на платформах
   - Рекрутер ищет кандидатов (активный поиск)

3. **Первичный отбор**:
   - Резюме фильтруются по критериям
   - Рекрутер проводит первичный скрининг (phone screen)

4. **Техническая оценка**:
   - Техническое задание или coding interview
   - Оценка технических навыков

5. **Интервью**:
   - Несколько раундов интервью с разными интервьюерами
   - Оценка разных аспектов (технические, культурные, коммуникативные)

6. **Принятие решения**:
   - Интервьюеры делятся feedback
   - Hiring manager принимает решение
   - Кандидату отправляется offer или rejection

7. **Онбординг** (если offer принят):
   - Подготовка рабочего места и доступа
   - Введение в команду и процессы
   - Обучение инструментам и кодбазе

**Ожидания:**

- Кандидат ожидает справедливую оценку и понятный процесс
- Организация ожидает, что кандидат честно представляет свои навыки
- Обе стороны ожидают уважительного отношения

### 3.3 Варианты протокола

**Быстрый найм:**
Для срочных позиций процесс ускоряется, некоторые этапы объединяются.

**Многоэтапный найм:**
Для senior позиций процесс расширен: больше интервью, более глубокие оценки.

**Реферальный найм:**
Кандидаты приходят по рекомендациям, процесс может быть упрощён.

### 3.4 Обработка ошибок

**Кандидат не подходит:**

- Rejection с конструктивным feedback (опционально)
- Сохранение контакта для будущих возможностей

**Offer отклонён:**

- Анализ причин
- Улучшение процесса или компенсации для будущих кандидатов

**Проблемы после найма:**

- Проблемный период (probation period) для оценки
- Возможность завершения найма при несоответствии

### 3.5 Применение в технических системах

Протокол найма применяется в:

- **Добавление узлов в распределённую систему**: оценка и интеграция новых серверов

- **Onboarding новых сервисов**: проверка совместимости и интеграция в систему

- **Добавление участников в консенсус**: проверка соответствия требованиям перед добавлением

## 4. Протокол code review

### 4.1 Проблема: контроль качества кода

**Проблема:** Код должен быть качественным, безопасным и соответствовать стандартам команды. Как обеспечить контроль качества без блокировки разработки?

**Решение:** Протокол code review — формализованный процесс проверки кода перед интеграцией.

### 4.2 Структура протокола code review

**Роли:**

- **Автор PR**: создаёт изменения, отвечает на комментарии, вносит правки

- **Ревьюер**: проверяет код, оставляет комментарии, одобряет или запрашивает изменения

- **Мейнтейнер**: мержит PR после одобрения

**Правила (последовательность):**

1. **Создание PR**:
   - Автор создаёт feature branch
   - Делает изменения и коммиты
   - Создаёт Pull Request с описанием изменений

2. **Проверка PR**:
   - Автоматические проверки (CI): тесты, линтеры, проверки безопасности
   - PR должен пройти все автоматические проверки

3. **Ревью**:
   - Ревьюер проверяет код на:
     - Корректность логики
     - Соответствие стандартам кода
     - Производительность
     - Безопасность
     - Тестируемость
   - Ревьюер оставляет комментарии (approve, request changes, или просто комментарии)

4. **Ответ на комментарии**:
   - Автор отвечает на комментарии
   - Вносит изменения (если запрошены)
   - Обновляет PR

5. **Одобрение**:
   - После устранения всех замечаний ревьюер одобряет PR
   - Может потребоваться несколько раундов ревью

6. **Мерж**:
   - Мейнтейнер мержит PR после одобрения
   - Возможны дополнительные проверки (например, approval от нескольких ревьюеров)

**Ожидания:**

- Автор ожидает конструктивную обратную связь и разумные сроки ревью
- Ревьюер ожидает готовый к ревью код и ответы на комментарии
- Мейнтейнер ожидает, что код прошёл ревью перед мержем

### 4.3 Правила хорошего code review

**Для ревьюера:**

- Будьте конструктивны, фокусируйтесь на коде, а не на человеке
- Объясняйте "почему", а не только "что"
- Хвалите хорошие решения
- Не блокируйте по мелочам
- Ревьюйте в разумные сроки (в течение дня)

**Для автора:**

- Создавайте небольшие PR (легче ревьюить)
- Пишите понятные описания изменений
- Отвечайте на все комментарии
- Не принимайте комментарии лично

### 4.4 Нарушения протокола

**Мерж без ревью:**

- Возможны баги и проблемы безопасности
- Нарушение стандартов кода
- Технический долг

**Неконструктивные комментарии:**

- Конфликты в команде
- Демотивация автора
- Плохая культура команды

**Игнорирование комментариев:**

- Задержка мержа
- Конфликты с ревьюером
- Возможная блокировка PR

### 4.5 Применение в технических системах

Протокол code review применяется в:

- **Валидация изменений**: автоматическая проверка изменений перед применением

- **Quality gates**: проверки качества перед деплоем

- **Security reviews**: проверки безопасности перед релизом

## 5. Протокол инцидент-менеджмента

### 5.1 Проблема: управление кризисными ситуациями

**Проблема:** Система сломалась, пользователи страдают, нужно быстро восстановить работу. Как координировать действия команды в кризисной ситуации?

**Решение:** Протокол инцидент-менеджмента — формализованный процесс обнаружения, эскалации, решения и анализа инцидентов.

### 5.2 Структура протокола инцидент-менеджмента

**Роли:**

- **On-call инженер**: первый, кто обнаруживает или получает алерт об инциденте

- **Incident commander**: координирует решение инцидента

- **Responders**: инженеры, работающие над решением

- **Communicator**: общается с пользователями и стейкхолдерами

- **Scribe**: документирует происходящее

**Правила (последовательность):**

1. **Обнаружение**:
   - Инцидент обнаруживается через мониторинг, алерты или сообщения пользователей
   - On-call инженер подтверждает инцидент

2. **Объявление инцидента**:
   - Создаётся инцидент (в системе тикетов или чате)
   - Определяется severity (P0, P1, P2, P3)
   - Назначается incident commander

3. **Триаж и координация**:
   - Incident commander координирует команду
   - Определяются приоритеты и план действий
   - Назначаются responders для разных аспектов проблемы

4. **Решение**:
   - Responders работают над решением
   - Применяются временные фиксы (workarounds) для восстановления сервиса
   - Применяется постоянное решение

5. **Коммуникация**:
   - Communicator обновляет статус для пользователей
   - Регулярные обновления (каждые 15-30 минут для P0)

6. **Разрешение**:
   - Инцидент разрешён, сервис восстановлен
   - Инцидент закрывается

7. **Постмортем**:
   - Анализ того, что произошло и почему
   - Определение action items для предотвращения в будущем
   - Документирование уроков

**Ожидания:**

- Пользователи ожидают быстрого восстановления и обновлений статуса
- Команда ожидает чёткой координации и распределения ролей
- Организация ожидает обучения на ошибках через постмортемы

### 5.3 Severity уровни

**P0 (Critical):**

- Полный отказ сервиса
- Большое количество пользователей затронуто
- Немедленная реакция, все hands on deck

**P1 (High):**

- Частичный отказ или деградация
- Значительное количество пользователей затронуто
- Быстрая реакция, приоритет над другой работой

**P2 (Medium):**

- Ограниченное влияние
- Workaround доступен
- Решение в течение рабочего дня

**P3 (Low):**

- Минимальное влияние
- Не критично для пользователей
- Решение в обычном порядке

### 5.4 Нарушения протокола

**Отсутствие координации:**

- Хаос, люди работают над одним и тем же
- Дублирование усилий
- Медленное решение

**Отсутствие коммуникации:**

- Пользователи не знают, что происходит
- Стейкхолдеры не информированы
- Потеря доверия

**Отсутствие постмортема:**

- Ошибки повторяются
- Нет обучения на ошибках
- Технический долг накапливается

### 5.5 Применение в технических системах

Протокол инцидент-менеджмента применяется в:

- **Failure handling**: автоматическое обнаружение и обработка сбоев

- **Circuit breakers**: автоматическое отключение проблемных компонентов

- **Chaos engineering**: преднамеренное создание инцидентов для проверки устойчивости

## 6. Организации как сети протоколов

### 6.1 Взаимосвязь протоколов

Организационные протоколы не существуют изолированно. Они образуют **сеть протоколов**, где выход одного протокола становится входом другого:

- **Найм** → **Онбординг** → **Работа** (митинги, code review)

- **Code review** → **Деплой** → **Мониторинг** → **Инцидент-менеджмент**

- **Инцидент-менеджмент** → **Постмортем** → **Улучшения** → **Code review**

### 6.2 Масштабирование через протоколы

Протоколы позволяют масштабировать организации:

- Новые сотрудники быстро интегрируются через формализованные процессы
- Команды могут работать независимо, следуя общим протоколам
- Процессы становятся предсказуемыми и автоматизируемыми

### 6.3 Эволюция протоколов

Организационные протоколы эволюционируют:

- Начинаются как неформальные соглашения
- Формализуются по мере роста организации
- Автоматизируются через инструменты
- Улучшаются через ретроспективы и постмортемы

---

## 💡 Key Takeaways

- **Организации — это сети протоколов**: Каждый процесс в организации — это протокол: митинги, найм, code review, инцидент-менеджмент. Понимание этих протоколов критично для эффективной работы.

- **Протоколы создают предсказуемость**: Формализованные процессы делают работу предсказуемой, снижают конфликты и неопределённость, позволяют масштабировать организации.

- **Роли и правила критичны**: Чёткое определение ролей и правил в организационных протоколах обеспечивает эффективную координацию и снижает конфликты.

- **Протоколы эволюционируют**: Организационные протоколы начинаются как неформальные соглашения и формализуются по мере роста организации, создавая основу для масштабирования.

- **Нарушения имеют последствия**: Нарушение организационных протоколов (мерж без ревью, отсутствие координации в инцидентах) приводит к проблемам, которые можно предотвратить следованием протоколу.
