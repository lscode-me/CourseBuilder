## 2. Stateful vs Stateless

### 2.1 Stateless протоколы

**Stateless** — протокол не хранит состояние между запросами.

**Характеристики:**

- Каждый запрос содержит всю необходимую информацию
- Сервер не помнит предыдущие запросы
- Любой запрос может быть обработан любым сервером

**Примеры:**

- HTTP (без cookies/sessions)
- DNS
- REST API (ideally)

**Преимущества:**

- Простота: не нужно управлять состоянием
- Масштабируемость: легко добавлять серверы
- Надёжность: при падении сервера состояние не теряется

**Недостатки:**

- Overhead: приходится передавать контекст в каждом запросе
- Сложность клиента: клиент должен помнить состояние

**Пример:**
```
GET /api/users/123 HTTP/1.1
Authorization: Bearer token123
```
Каждый запрос содержит всю информацию (user ID, токен).

### 2.2 Stateful протоколы

**Stateful** — протокол хранит состояние между запросами.

**Характеристики:**

- Сервер помнит предыдущие взаимодействия
- Запросы могут ссылаться на контекст сессии
- Клиент привязан к конкретному серверу

**Примеры:**

- FTP (контрольное соединение хранит состояние)
- WebSocket (постоянное соединение)
- TCP (состояние соединения)

**Преимущества:**

- Эффективность: не нужно передавать контекст каждый раз
- Богатые взаимодействия: можно строить сложные сессии

**Недостатки:**

- Сложность: нужно управлять состоянием
- Масштабируемость: sticky sessions или shared state
- Надёжность: при падении сервера состояние теряется

**Пример FTP:**
```
Client: USER admin
Server: 331 Password required
Client: PASS secret
Server: 230 Login successful
Client: LIST
Server: [файлы] (сервер помнит, что клиент залогинен)
```

### 2.3 Гибридные подходы

**HTTP с сессиями:**
```
Stateless протокол + stateful session через cookies

GET /dashboard HTTP/1.1
Cookie: session_id=abc123

Сервер: находит сессию abc123 и возвращает данные
```

**Преимущества:**

- HTTP остаётся stateless (можно кэшировать, масштабировать)
- Сессия управляется через внешнее хранилище (Redis, database)

## 3. Synchronous vs Asynchronous

### 3.1 Synchronous протоколы

**Synchronous** — отправитель ждёт ответа перед продолжением.

**Характеристики:**

- Блокирующий вызов
- Строгий порядок: запрос → ответ
- Простая модель программирования

**Примеры:**

- HTTP (request → response)
- RPC
- SQL queries

**Преимущества:**

- Простота: понятная модель
- Порядок: ответы приходят в порядке запросов

**Недостатки:**

- Блокировка: клиент ждёт
- Низкая пропускная способность

**Пример:**
```python
response = requests.get('https://api.example.com/users/123')
# Блокируется до получения ответа

print(response.json())
```

### 3.2 Asynchronous протоколы

**Asynchronous** — отправитель не ждёт ответа, продолжает работу.

**Характеристики:**

- Неблокирующий вызов
- Ответ приходит позже (callback, promise, event)
- Сложная модель программирования

**Примеры:**

- Message queues (RabbitMQ, Kafka)
- Websockets (events)
- Async HTTP (with promises)

**Преимущества:**

- Высокая пропускная способность
- Не блокирует клиента

**Недостатки:**

- Сложность: callbacks, promises, async/await
- Порядок не гарантирован

**Пример:**
```python
import asyncio
import aiohttp

async def fetch_user(user_id):
    async with aiohttp.ClientSession() as session:
        async with session.get(f'https://api.example.com/users/{user_id}') as response:
            return await response.json()

# Отправляет запрос, не блокируется

task = asyncio.create_task(fetch_user(123))
# Продолжает работу

print("Fetching user...")
# Позже получает результат

user = await task
```

### 3.3 Request-Response vs Fire-and-Forget

**Request-Response (sync):**

- Клиент ожидает ответ
- HTTP, gRPC

**Fire-and-Forget (async):**

- Клиент отправляет и не ждёт ответа
- Message queues, UDP

## 4. Человеческие vs Машинные

### 4.1 Человеческие протоколы

**Человеческие** — протоколы для взаимодействия людей.

**Характеристики:**

- Неформальные или semi-формальные
- Гибкие, адаптируемые
- Зависят от культуры и контекста
- Могут иметь исключения

**Примеры:**

- Бытовые протоколы (очередь, покупка)
- Социальные протоколы (митинги, code review)
- Деловая переписка

**Особенности:**

- Естественный язык
- Неоднозначность допустима (разрешается через общение)
- Эволюционируют неформально

### 4.2 Машинные протоколы

**Машинные** — протоколы для взаимодействия машин.

**Характеристики:**

- Формальные, строго определённые
- Жёсткие правила
- Не зависят от контекста
- Нет исключений (или они формализованы)

**Примеры:**

- Сетевые протоколы (TCP, HTTP)
- API протоколы (REST, gRPC)
- Протоколы баз данных

**Особенности:**

- Бинарный или структурированный формат
- Неоднозначность недопустима
- Версионирование для эволюции

### 4.3 Гибридные протоколы

**Человеко-машинные** — протоколы для взаимодействия людей с машинами.

**Примеры:**

- HTML (машинный, но отображается для людей)
- CLI интерфейсы
- REST API (JSON читается людьми)

**Требования:**

- Читаемость для людей
- Формальность для машин

## 5. Открытые vs Закрытые

### 5.1 Открытые протоколы

**Открытые** — публичная спецификация, доступная всем.

**Характеристики:**

- Спецификация публична (RFC, standards)
- Множество реализаций от разных вендоров
- Interoperability между реализациями

**Примеры:**

- HTTP (RFC 7230-7237)
- TCP/IP (RFC 793, 791)
- OpenAPI для REST

**Преимущества:**

- Interoperability: разные системы работают вместе
- Инновации: любой может реализовать
- Долговечность: не зависит от одного вендора

**Недостатки:**

- Медленная эволюция (нужен consensus)
- Компромиссы (угодить всем)

### 5.2 Закрытые (проприетарные) протоколы

**Закрытые** — спецификация не публична, контролируется одной организацией.

**Характеристики:**

- Спецификация секретна или ограниченна
- Обычно одна реализация (или лицензированные)
- Lock-in к вендору

**Примеры:**

- Skype protocol (был закрытым)
- Некоторые игровые протоколы
- Внутренние протоколы компаний

**Преимущества:**

- Быстрая эволюция (нет consensus)
- Оптимизация под конкретные нужды
- Контроль над экосистемой

**Недостатки:**

- Нет interoperability
- Vendor lock-in
- Риск исчезновения с вендором

### 5.3 De facto стандарты

**De facto** — закрытый протокол становится стандартом из-за популярности.

**Примеры:**

- Adobe PDF (сначала закрытый, затем открытый стандарт ISO)
- Microsoft Office formats (закрытые, но де-факто стандарт)

## 6. Текстовые vs Бинарные

### 6.1 Текстовые протоколы

**Текстовые** — данные представлены как текст (ASCII, UTF-8).

**Примеры:**

- HTTP/1.1
- SMTP
- JSON API

**Преимущества:**

- Читаемость (можно отлаживать в текстовом редакторе)
- Простота реализации

**Недостатки:**

- Больший размер
- Медленнее парсинг

### 6.2 Бинарные протоколы

**Бинарные** — данные в бинарном формате.

**Примеры:**

- HTTP/2
- Protocol Buffers
- TCP headers

**Преимущества:**

- Компактность
- Быстрый парсинг

**Недостатки:**

- Нечитаемость (нужны специальные инструменты)
- Сложнее реализация

## 💡 Key Takeaways

- **Stateful vs Stateless — компромисс**: Stateless проще масштабировать, stateful эффективнее. HTTP stateless, но с сессиями через cookies.

- **Sync vs Async — производительность vs сложность**: Sync проще, async быстрее. Выбор зависит от требований к latency и throughput.

- **Человеческие vs машинные — формальность**: Человеческие протоколы гибкие и неформальные, машинные строгие и формальные. Гибридные (HTML, JSON) читаемы для обоих.

- **Открытые vs закрытые — interoperability vs контроль**: Открытые протоколы обеспечивают interoperability, закрытые — контроль и быструю эволюцию. De facto стандарты — компромисс.

- **Множественная классификация**: Протоколы классифицируются по множеству осей одновременно. HTTP: stateless, sync, machine/human, open, text.
