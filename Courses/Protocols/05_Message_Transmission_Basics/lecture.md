## 1. Введение: передача сообщений

В основе всех протоколов коммуникации лежит **передача сообщений** — процесс отправки информации от отправителя к получателю. Но простая отправка данных недостаточна: нужно гарантировать доставку, обрабатывать ошибки, управлять синхронностью.

В этом модуле мы рассмотрим фундаментальные концепции протоколов передачи:

1. **Сигнал и сообщение** — что передаём и как
2. **Синхронность и асинхронность** — когда происходит передача
3. **Подтверждения и таймауты** — гарантии доставки
4. **Потери и ошибки** — что делать когда что-то идёт не так

Эти концепции лежат в основе всех протоколов передачи — от простых сигналов до сложных сетевых протоколов.

## 2. Сигнал и сообщение

### 2.1 Сигнал vs сообщение

**Сигнал** — простейшая форма передачи информации: наличие или отсутствие чего-то, изменение состояния.

**Примеры сигналов:**

- Светофор: красный/жёлтый/зелёный
- Звонок телефона: есть звонок / нет звонка
- Флаг на корабле: поднят / опущен

**Сообщение** — структурированная информация с семантикой.

**Примеры сообщений:**

- Текст письма: "Встречаемся в 15:00"
- HTTP запрос: `GET /api/users HTTP/1.1`
- Команда: `git commit -m "Fix bug"`

**Разница:**

- Сигнал передаёт состояние (есть/нет, включено/выключено)
- Сообщение передаёт информацию (что, когда, как)

### 2.2 Кодирование информации

Информация должна быть **закодирована** для передачи:

**Бинарное кодирование:**

- 0/1 для цифровых сигналов
- Байты для сообщений
- Протокол определяет интерпретацию битов

**Пример:**
```

Сигнал: 1 = есть данные, 0 = нет данных
Сообщение: байты [0x48, 0x65, 0x6C, 0x6C, 0x6F] = "Hello" (UTF-8)
```

### 2.3 Структура сообщения

Протокол определяет **структуру сообщения**:

**Заголовок (header):**

- Метаданные: тип, размер, адреса
- Используется протоколом для маршрутизации и обработки

**Тело (body/payload):**

- Фактические данные
- Интерпретируется приложением

**Пример HTTP сообщения:**
```

GET /api/users HTTP/1.1          ← Заголовок запроса
Host: example.com
Accept: application/json

                                    ← Тело (пустое для GET)
```

## 3. Синхронность и асинхронность

### 3.1 Синхронные протоколы

**Синхронный протокол** — отправитель ждёт ответа перед продолжением.

**Характеристики:**

- Блокирующее ожидание ответа
- Простая модель: запрос → ответ
- Низкая сложность реализации
- Ограниченная пропускная способность

**Пример: HTTP (синхронный):**
```

Клиент: GET /api/users
        [ждёт ответа...]
Сервер: 200 OK
        {"users": [...]}
Клиент: [получил ответ, продолжает]
```

**Применение:**

- Когда нужен немедленный ответ
- Когда порядок важен
- Когда простота важнее производительности

### 3.2 Асинхронные протоколы

**Асинхронный протокол** — отправитель не ждёт ответа, продолжает работу.

**Характеристики:**

- Неблокирующая отправка
- Сложная модель: отправка → обработка позже → ответ
- Высокая пропускная способность
- Сложность управления состоянием

**Пример: Message Queue (асинхронный):**
```

Producer: отправляет сообщение в очередь
          [не ждёт, продолжает работу]
Queue: хранит сообщение
Consumer: обрабатывает сообщение позже
          отправляет результат в другую очередь
Producer: получает результат позже (через callback/polling)
```

**Применение:**

- Когда ответ не нужен немедленно
- Когда нужна высокая пропускная способность
- Когда обработка занимает много времени

### 3.3 Гибридные протоколы

Многие протоколы поддерживают **оба режима**:

**Пример: HTTP с async обработкой:**
```

Клиент: POST /api/long-task
Сервер: 202 Accepted
        {"task_id": "123"}
        [задача обрабатывается асинхронно]
Клиент: GET /api/tasks/123/status
Сервер: 200 OK
        {"status": "completed", "result": "..."}
```

## 4. Подтверждения и таймауты

### 4.1 Проблема: гарантия доставки

**Проблема:** Как узнать, что сообщение доставлено? Сообщение может быть потеряно, получатель может быть недоступен.

**Решение:** **Подтверждения (acknowledgments)** — получатель подтверждает получение.

### 4.2 Протокол с подтверждениями

**Базовая схема:**
```

Отправитель: отправляет сообщение
             [ждёт подтверждения]
Получатель: получает сообщение
            отправляет подтверждение (ACK)
Отправитель: получает ACK
             [знает, что сообщение доставлено]
```

**Если ACK не пришёл:**

- Возможна потеря сообщения
- Возможна потеря ACK
- Нужен механизм повторной отправки

### 4.3 Таймауты

**Таймаут** — максимальное время ожидания ответа.

**Применение:**

- Ожидание подтверждения
- Ожидание ответа на запрос
- Определение недоступности получателя

**Пример с таймаутом:**
```

Отправитель: отправляет сообщение
             [устанавливает таймаут: 5 секунд]
             [ждёт ACK...]
             
Если ACK пришёл в течение 5 секунд:
    → сообщение доставлено
Иначе:
    → таймаут, возможна потеря
    → повторная отправка
```

### 4.4 Последовательные номера

Для обработки дубликатов используются **последовательные номера**:

```

Сообщение 1: отправлено → ACK получен ✓
Сообщение 2: отправлено → таймаут
Сообщение 2: повторная отправка → ACK получен ✓
Сообщение 3: отправлено → ACK получен ✓
```

Получатель может определить дубликаты по номеру и проигнорировать их.

## 5. Потери и ошибки

### 5.1 Типы проблем

**Потеря сообщения:**

- Сообщение отправлено, но не доставлено
- Обнаруживается через отсутствие ACK
- Решение: повторная отправка

**Потеря подтверждения:**

- Сообщение доставлено, но ACK потерян
- Отправитель думает, что сообщение потеряно
- Решение: повторная отправка (получатель должен обработать дубликат)

**Искажение данных:**

- Сообщение доставлено, но данные повреждены
- Обнаруживается через checksum/CRC
- Решение: повторная отправка

**Задержка:**

- Сообщение доставлено, но с большой задержкой
- Может быть устаревшим
- Решение: таймаут, игнорирование устаревших сообщений

### 5.2 Обнаружение ошибок

**Checksum:**

- Сумма байтов сообщения
- Простая, но слабая защита

**CRC (Cyclic Redundancy Check):**

- Полиномиальная проверка
- Сильная защита от случайных ошибок

**Пример структуры сообщения с проверкой:**
```

[Заголовок] [Данные] [CRC]
     ↓          ↓       ↓
  10 байт   100 байт  4 байта
```

Получатель вычисляет CRC и сравнивает с переданным.

### 5.3 Обработка ошибок

**Стратегии:**

1. **Повторная отправка (retry):**
   - При потере или ошибке
   - Ограниченное количество попыток
   - Экспоненциальная задержка между попытками

2. **Игнорирование:**
   - Для некритичных сообщений
   - При устаревших данных

3. **Эскалация:**
   - Сообщение об ошибке вышестоящему уровню
   - Логирование для анализа

**Пример протокола с обработкой ошибок:**
```

Отправитель: отправляет сообщение с CRC
             [ждёт ACK с таймаутом 5 сек]
             
Если ACK получен:
    → успех
Иначе если попыток < 3:
    → повторная отправка (задержка: 2^попытка секунд)
Иначе:
    → ошибка: сообщение не доставлено
    → эскалация: уведомление приложению
```

## 6. Примеры протоколов передачи

### 6.1 Простой протокол "ping-pong"

**Протокол:**

1. Отправитель отправляет "ping"
2. Получатель отвечает "pong"
3. Если "pong" не пришёл за 1 секунду → таймаут

**Использование:**

- Проверка доступности
- Измерение задержки (latency)

### 6.2 Протокол с подтверждениями

**Протокол:**

1. Отправитель отправляет сообщение с номером N
2. Получатель получает, проверяет CRC
3. Если CRC корректна: отправляет ACK(N)
4. Если CRC некорректна: отправляет NAK(N)
5. Отправитель: если ACK → следующее сообщение, если NAK → повтор

### 6.3 Протокол с окном (sliding window)

Для повышения пропускной способности используется **окно** — несколько сообщений в полёте:

```

Окно размером 3:
Отправитель отправляет: 1, 2, 3
Получает ACK(1) → отправляет 4
Получает ACK(2) → отправляет 5
...
```

Это позволяет не ждать каждого ACK перед отправкой следующего сообщения.

## 💡 Key Takeaways

- **Сигнал vs сообщение**: Сигнал передаёт состояние (есть/нет), сообщение передаёт структурированную информацию. Протокол определяет кодирование и структуру.

- **Синхронность vs асинхронность**: Синхронные протоколы просты, но блокируют; асинхронные эффективны, но сложны. Выбор зависит от требований.

- **Подтверждения и таймауты**: Подтверждения гарантируют доставку, таймауты определяют недоступность. Последовательные номера предотвращают проблемы с дубликатами.

- **Обработка ошибок**: Потери, искажения и задержки неизбежны. Протоколы должны обнаруживать ошибки (CRC) и обрабатывать их (повтор, эскалация).

- **Надёжность через повтор**: Повторная отправка с ограничениями и экспоненциальной задержкой — стандартный способ обеспечения надёжности в ненадёжных каналах.
