## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | A | Проблема "remap" при наивном хешировании делает его непригодным для динамических кластеров |
| 2 | B | Стабильность распределения ключей (Monotonicity) — главное свойство |
| 3 | C | Кольцевая топология позволяет легко определять соседей и диапазоны ответственности |
| 4 | B | Узлы хешируются в то же пространство, что и ключи |
| 5 | A | Стандартное правило: двигаемся по кольцу (0..MAX) и берем первый встречный узел |
| 6 | A | Новый узел встает в кольцо и "откусывает" часть диапазона у следующего узла, забирая его ключи |
| 7 | C | VNodes разбивают данные на мелкие гранулы, позволяя гибко балансировать нагрузку |
| 8 | B | Weight-based distribution реализуется через количество VNodes |
| 9 | A | Replication Factor (RF) определяет, на скольки последовательных узлах лежит копия |
| 10 | C | Это убирает лишний сетевой хоп (hop) и снижает нагрузку на координаторы |
| 11 | C | Chord добавляет "finger table" (быстрые ссылки через кольцо) для масштабируемого поиска |
| 12 | A | Consistent Hashing распределяет ключи, но не запросы. Один популярный ключ может положить узел |
| 13 | D | Сама схема хеширования не дает надежности. Нужна репликация (хранение на N узлах) |
| 14 | D | HRW stateless, но требует O(N) вычислений хеша на каждый запрос, что дорого при большом N |
| 15 | B | Локализация сбоя. Падение одного кеша не инвалидирует весь глобальный кеш |
| 16 | A | Децентрализованный обмен метаданными (membership protocol) |
| 17 | C | Именно этот ключ определяет, на какой шард попадет запись |
| 18 | B | Хеширование убивает локальность данных. Для диапазонов нужны B-tree или Order Preserving Partitioners |
| 19 | D | Используется, например, в HBase или Cassandra (старые версии), но создает Hotspots |
| 20 | C | Перемещается ровно столько данных, сколько нужно для выравнивания баланса (1/N часть) |
