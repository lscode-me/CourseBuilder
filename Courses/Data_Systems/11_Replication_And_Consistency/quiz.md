## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | C | Репликация страхует от потери узла и позволяет читать данные параллельно |
| 2 | D | В Single Leader модели Followers доступны только для чтения (Read-Only) |
| 3 | C | Leader подтверждает запись до репликации. Сбой в этот момент = потеря данных |
| 4 | C | Из-за асинхронной природы Followers всегда немного отстают от Leader |
| 5 | C | Это обеспечивает UX консистентность для самого автора изменений |
| 6 | D | Позволяет писать быстро в ближайший DC, а репликация идет по медленному каналу |
| 7 | B | Отсутствие единой точки истины требует стратегии слияния версий с разных мастеров |
| 8 | C | "Слепая" перезапись может уничтожить важные данные конкурентной транзакции |
| 9 | D | Семейство Dynamo использует кольцо и кворумы без выделенного лидера |
| 10 | C | Принцип Дирихле: читающее и пишущее множества должны пересекаться |
| 11 | B | Не нужно ждать всех N узлов, достаточно W подтверждений для успеха |
| 12 | B | "Ленивое" восстановление согласованности при обращении к данным |
| 13 | B | Высокая задержка записи (latency), но отсутствие репликационного лага для читателя |
| 14 | D | Это катастрофический сценарий, требующий механизмов Fencing (изоляции старого лидера) |
| 15 | A | Приоритет Availability (AP): пишем куда угодно, лишь бы записать, потом передадим владельцу |
| 16 | C | Недетерминированные функции делают реплики рассинхронизированными |
| 17 | A | Самый надежный способ (используется в Postgres), гарантирует побитовую идентичность |
| 18 | B | Защищает от эффекта, когда после обновления страницы данные "исчезают" из-за попадания на отстающую реплику |
| 19 | A | Вертикальное масштабирование — это один узел. Репликация — это копии на разных узлах |
| 20 | D | В соответствии с CAP теоремой, они выбирают Availability при Partition |
