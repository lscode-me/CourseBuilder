## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | A | Индексы создаются для ускорения поиска (SELECT), ценой замедления записи |
| 2 | C | Без индекса СУБД вынуждена сканировать всю таблицу (Full Table Scan) |
| 3 | C | B-tree — сбалансированное дерево, поиск занимает логарифмическое время |
| 4 | A | В B+ tree данные только в листьях, листья связаны, что ускоряет range scan |
| 5 | A | B-tree хранит данные упорядоченно, идеально для диапазонов |
| 6 | C | Hash Index не хранит порядок, поэтому `>` или `<` не работают эффективно |
| 7 | D | Bitmap идеален для малого числа уникальных значений и логических операций |
| 8 | D | Каждая вставка требует обновления всех индексов таблицы |
| 9 | C | B-tree эффективен при высокой селективности (много уникальных значений) |
| 10 | B | Работает правило "Leftmost Prefix" — важен порядок слева направо |
| 11 | C | Пропущен первый столбец `a`, индекс не может быть использован для поиска |
| 12 | A | Высокая селективность означает, что индекс "отсекает" много лишнего |
| 13 | C | Если индекс содержит все запрашиваемые поля, чтение самой таблицы ("кучи") не нужно |
| 14 | B | В среднем хеш-таблица дает O(1), в худшем случае коллизий O(n) |
| 15 | C | Побитовые операции процессора (bitwise operations) экстремально быстры |
| 16 | B | Индексы персистентны и хранятся на диске, подгружаясь в Buffer Pool |
| 17 | A | Primary Key обычно реализуется как уникальный B-tree (кластерный) индекс |
| 18 | D | Каждый лишний индекс — это накладные расходы на запись и хранение |
| 19 | A | Коллизии обрабатываются, но превращают O(1) в O(k) или O(n) |
| 20 | D | Консистентность требует удаления ссылок из всех индексов |

## Scoring Guide

- **18-20 правильных (90-100%)**: Отлично! Вы разбираетесь в индексах.

- **14-17 правильных (70-89%)**: Хорошо. Обратите внимание на составные индексы.

- **10-13 правильных (50-69%)**: Удовлетворительно. Повторите B-tree vs Hash.

- **Менее 10 правильных (< 50%)**: Рекомендуется перечитать материал.
