## Answer Key

| # | Answer | Explanation |
|---|--------|-------------|
| 1 | A | Персистентность и возможность перечитывания (Replay) — главная фишка Лога |
| 2 | A | Партиционирование позволяет разделить нагрузку. Топик — логическая сущность, Партиция — физическая |
| 3 | A | Порядок гарантируется только для сообщений, попавших в одну партицию (обычно с одним ключом) |
| 4 | B | Offset — это просто порядковый номер в логе партиции. Легковесный "индекс" |
| 5 | C | Группа масштабирует чтение. Kafka следит, чтобы партиции не обрабатывались дважды внутри группы |
| 6 | D | Допустима потеря, но недопустимы дубли. Самая быстрая семантика |
| 7 | A | Если ack не дошел до брокера, продюсер пошлет сообщение снова. Консьюмер должен быть готов |
| 8 | A | Критически важно для At-least-once. Например, `SET balance = 100` идемпотентно, `balance += 10` — нет |
| 9 | D | Полезно для хранения "текущего состояния" в Kafka (например, профили пользователей) |
| 10 | A | Последовательная запись — самая быстрая операция для HDD и SSD |
| 11 | D | Это обеспечивает семантическую связь: все события одного пользователя летят в одну партицию (строгий порядок) |
| 12 | D | Позволяет интегрировать Legacy БД в событийную архитектуру |
| 13 | D | Kafka — это не вечное хранилище (как БД), а буфер. Retention контролирует очистку |
| 14 | C | Pull позволяет консьюмеру не захлебнуться (Backpressure), если брокер слишком быстр |
| 15 | B | Stream позволяет получать business value мгновенно (Real-time analytics) |
| 16 | C | Эффективное использование OS API для пересылки байт без лишних переключений контекста CPU |
| 17 | D | Архитектура Kafka — Single Leader Replication на уровне партиции |
| 18 | A | Только реплики из ISR могут стать новым Лидером при сбое, гарантируя сохранность данных |
| 19 | C | Самая медленная, но самая надежная настройка. Guarantee Durability |
| 20 | B | Возможность "отмотать время назад" полезна при исправлении багов в обработчиках |
