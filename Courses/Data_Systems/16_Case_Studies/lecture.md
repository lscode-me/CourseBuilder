## Case Study 1: URL Shortener (TinyURL / bit.ly)

**Задача**: Превратить длинную ссылку `google.com/search?q=cat` в короткую `bit.ly/AbC12`.

### 1.1 Структуры данных

Нам нужен **Map**.
`Key (ShortCode) -> Value (LongURL)`

### 1.2 Выбор базы данных

- **Read/Write ratio**: Читают (1000) намного чаще, чем создают (1). Read Heavy.

- **Данные**: Простой Key-Value.

- **Выбор**: NoSQL Key-Value Store (Redis для кеша + DynamoDB/Cassandra/Postgres для хранения).

### 1.3 Алгоритм генерации (ShortCode)

Как сделать уникальный ID из 6-7 символов?

- MD5/SHA256 хеш? Слишком длинный (32 символа).
- **Counter + Base62 Encoding**.
    1. Берем глобальный счетчик (Auto-increment ID): `100500`.
    2. Переводим число 100500 в систему счисления Base62 (a-z, A-Z, 0-9).
    3. `100500` -> `AbC`.

**Проблема распределенного счетчика**:
Если у нас 10 серверов, как им генерировать уникальные ID, не блокируя друг друга?

*   **Решение**: Zookeeper выдает диапазоны (Ranges).
    *   Server A: 1 - 1,000,000
    *   Server B: 1,000,001 - 2,000,000
    *   Теперь каждый сервер инкрементит свой локальный `atomic long` без сети. Быстро!

### 1.4 Архитектура

1.  **Write**: User -> LB -> App -> Zookeeper (Range) -> DB (Insert).
2.  **Read**: User -> LB -> Redis (Get). Если нет -> DB (Get) -> 301 Redirect.

## Case Study 2: Twitter Timeline / News Feed

**Задача**: Показать пользователю твиты от тех, на кого он подписан.
**Проблема**: SQL запрос `SELECT * FROM Tweets WHERE user_id IN (SELECT followee FROM Follows)` убивает базу данных при миллионах фолловеров.

### 2.1 Подход 1: Pull Model (Fan-out on Read)

Когда Вася заходит на сайт, мы идем в таблицу Follows, находим друзей, берем их последние твиты, сортируем в памяти.

*   **Плюс**: Простая запись.

*   **Минус**: Очень медленное чтение.

### 2.2 Подход 2: Push Model (Fan-out on Write)

Когда Илон Маск пишет твит, мы сразу кладем этот твит (или его ID) в **личную очередь** (Timeline) каждого фолловера.

*   **Структура**: User Timeline = `List` (Redis List).

*   **Плюс**: Чтение мгновенное (O(1)). Просто `Redis.LRCANGE`.

*   **Минус**: Если у Илона 100 млн фолловеров, нужно сделать 100 млн записей. Это называется **Write Amplification**.

### 2.3 Гибридный подход

*   Для обычных людей (у кого < 5000 фолловеров): Используем **Push**.
*   Для "Селебрити" (миллионы фолловеров): Используем **Pull**. Их твиты не рассылаются, а подмешиваются в ленту при чтении.

## Case Study 3: Uber / Nearby Drivers

**Задача**: Показать 10 ближайших машин. Водители двигаются каждые 5 секунд.

### 3.1 Наивный подход

`SELECT * FROM Drivers WHERE distance(me, driver) < 5km`.
Это **Full Table Scan** по всей базе водителей мира. Не работает.

### 3.2 Гео-индекс (Quadtree / Geohash)

Мир делится на сетку (Grid).
Каждый водитель принадлежит какой-то ячейке.
Geohash "u4pru" (центр города).

**Структура данных**:
Map: `Geohash -> Set[DriverID]`

### 3.3 Обновления

Водитель двигается -> Geohash меняется.
Это очень частая операция (High Write Throughput).

*   SQL база (B-tree) может не справиться с постоянной перестройкой индекса.
*   **Решение**: Хранить текущие позиции в **Redis Geo** (In-Myemory).

**Redis Geo API**:
- `GEOADD drivers 13.361 38.115 "Driver 1"`
- `GEORADIUS drivers 15 37 200 km`

Старые точки не нужны (нам не важно, где таксист был час назад, если мы ищем такси сейчас).

## 4. Общие паттерны (Summary)

1.  **Unique IDs**: UUID (большой, random) vs Snowflake (время + машина + sequence, сортируемый).
2.  **Caching**: Cache-Aside паттерн везде. "Самый быстрый запрос тот, которого не было".
3.  **Asynchrony**: Тяжелые задачи (отправка email, обработка видео, Fan-out твитов) — всегда в Kafka/RabbitMQ.
4.  **Sharding**: Ключ шардирования (Partition Key) определяет масштабируемость.
    *   URL Shortener: по ShortCode.
    *   Twitter: по UserID.
    *   Uber: по Geohash.

## 5. Финальное напутствие

Мы прошли путь от `O(n)` до распределенных систем с петабайтами данных.
Вы увидели, что магии нет.

*   **Cassandra** — это просто много **LSM-деревьев**.

*   **Redis** — это просто **Hash Map**.

*   **System Design** — это умение комбинировать эти кирпичики.

## 💡 Key Takeaways

- **URL Shortener**: Используй Counter Range + Base62.

- **News Feed**: Push (Fan-out) для чтения O(1), гибрид для селебрити.

- **Geo**: Geohash/Quadtree для быстрого поиска соседей, Redis для скорости.
- Масштабирование — это поиск узких мест и замена "универсальных" структур на "специализированные" (SQL -> NoSQL, Array -> Index).
