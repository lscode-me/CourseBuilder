## 1. Что такое JSON

### 1.1 История и происхождение

**JSON** (JavaScript Object Notation) — текстовый формат обмена данными, который стал де-факто стандартом для веб-разработки.

**История создания:**

- **2001 год**: Дуглас Крокфорд (Douglas Crockford) начал работу над форматом для обмена данными между браузером и сервером

- **2002 год**: Первая публичная презентация JSON на конференции

- **2005 год**: Официальный сайт json.org запущен

- **2013 год**: ECMA-404 — первый официальный стандарт JSON

- **2017 год**: RFC 8259 — стандарт IETF, закрепивший UTF-8 как обязательную кодировку

**Почему JSON был создан?**

В начале 2000-х веб-разработчики столкнулись с проблемой обмена данными между клиентом и сервером:

1. **XML был слишком сложным** — многословный синтаксис, сложный парсинг, избыточность
2. **Нужен был простой формат** — легко читать и писать человеку, легко парсить программе
3. **JavaScript набирал популярность** — формат должен был естественно работать с JavaScript
4. **Требовалась независимость от языка** — данные должны работать везде

**Философия дизайна JSON:**

Крокфорд сформулировал принцип: "JSON — это минимальный, портативный, текстовый формат обмена данными". Он сознательно убрал из JavaScript Object Notation всё лишнее:

- Нет комментариев (чтобы избежать проблем с парсингом)
- Нет trailing comma (упрощение парсера)
- Только двойные кавычки (единообразие)
- Строгий синтаксис (предсказуемость)

### 1.2 Определение и характеристики

**JSON** — текстовый формат обмена данными, основанный на подмножестве синтаксиса JavaScript.

**Ключевые характеристики:**

| Характеристика | Описание |
|----------------|----------|
| **Текстовый формат** | Читается человеком и машиной |
| **Независим от языка** | Работает в любом языке программирования |
| **Легковесный** | Минимальный синтаксис, быстрый парсинг |
| **Самодокументируемый** | Структура данных понятна из формата |
| **Стандартизированный** | ECMA-404, RFC 8259 |
| **UTF-8 кодировка** | Поддержка всех языков мира |

**Сравнение с альтернативами:**

| Формат | Год создания | Сложность | Размер | Скорость парсинга | Человекочитаемость |
|--------|--------------|-----------|--------|-------------------|-------------------|
| **XML** | 1998 | Высокая | Большой | Медленный | Средняя |
| **JSON** | 2001 | Низкая | Малый | Быстрый | Высокая |
| **YAML** | 2001 | Средняя | Средний | Средний | Очень высокая |
| **MessagePack** | 2011 | Низкая | Очень малый | Очень быстрый | Нет (бинарный) |

### 1.3 Где используется JSON

| Область | Применение |
|---------|------------|
| Web API | REST API запросы и ответы |
| Конфигурации | package.json, tsconfig.json |
| Базы данных | MongoDB, PostgreSQL JSONB |
| Логирование | Structured logging |
| Обмен данными | Между сервисами, клиентом и сервером |

### 1.3 Пример JSON

```json

{
  "name": "Alice",
  "age": 30,
  "isActive": true,
  "balance": null,
  "skills": ["Python", "SQL", "Docker"],
  "address": {
    "city": "Moscow",
    "zip": "101000"
  }
}

```

**Структура этого примера:**

```

Object (корневой уровень)
├── "name": String ("Alice")
├── "age": Number (30)
├── "isActive": Boolean (true)
├── "balance": Null
├── "skills": Array
│   ├── [0]: String ("Python")
│   ├── [1]: String ("SQL")
│   └── [2]: String ("Docker")
└── "address": Object (вложенный)
    ├── "city": String ("Moscow")
    └── "zip": String ("101000")
```

## 2. Синтаксис JSON

### 2.1 Типы данных

JSON поддерживает **6 типов данных** — это минимальный набор, достаточный для представления большинства структур данных.

**Почему именно 6 типов?**

Дизайн JSON основан на принципе минимализма:

- **String, Number, Boolean, Null** — примитивные типы (базовые строительные блоки)

- **Array** — для упорядоченных коллекций

- **Object** — для структурированных данных (ассоциативные массивы)

Этих типов достаточно для представления любых данных, а добавление новых типов усложнило бы парсинг и стандартизацию.

| Тип | Пример | Описание | Использование |
|-----|--------|----------|---------------|
| **String** | `"hello"` | Строка в двойных кавычках | Текст, даты (как строки), идентификаторы |
| **Number** | `42`, `3.14`, `-5`, `1e10` | Число (целое или дробное) | Количества, цены, координаты |
| **Boolean** | `true`, `false` | Логическое значение | Флаги, состояния включено/выключено |
| **Null** | `null` | Отсутствие значения | Опциональные поля, отсутствующие данные |
| **Array** | `[1, 2, 3]` | Упорядоченный список | Списки, множества, последовательности |
| **Object** | `{"key": "value"}` | Набор пар ключ-значение | Структурированные данные, записи, конфигурации |

**Визуальное представление типов:**

```

JSON Value
│
├─── Primitive Types
│   ├── String: "text"
│   ├── Number: 42, 3.14, -5, 1e10
│   ├── Boolean: true, false
│   └── Null: null
│
└─── Composite Types
    ├── Array: [value1, value2, ...]
    └── Object: {"key1": value1, "key2": value2, ...}
```

### 2.2 Строки (Strings)

**Почему только двойные кавычки?**

В JSON строки должны быть в двойных кавычках (`"..."`), а не в одинарных (`'...'`). Это решение было принято по нескольким причинам:

1. **Единообразие** — один способ записи строк упрощает парсинг
2. **Совместимость с JavaScript** — в JS объектные литералы используют двойные кавычки
3. **Избежание конфликтов** — одинарные кавычки часто используются в HTML (`<div class='example'>`)

**Структура строки:**

```

"  [содержимое строки]  "
 ↑                      ↑
начало                 конец
```

Строка может содержать:
- Любые Unicode символы (UTF-8 кодировка)
- Escape-последовательности для специальных символов
- Многострочный текст (через `\n`)

```json

{
  "simple": "Hello, World!",
  "unicode": "Привет, мир! 你好 🎉",
  "escaped": "Line 1\nLine 2\tTabbed",
  "quotes": "He said \"Hello\"",
  "path": "C:\\Users\\name",
  "special": "\u0041",
  "empty": "",
  "multiline_escaped": "First line\nSecond line\nThird line"
}

```

**Escape-последовательности:**

Escape-последовательности позволяют включить в строку символы, которые иначе были бы интерпретированы как часть синтаксиса JSON.

| Последовательность | Значение | Зачем нужно |
|-------------------|----------|-------------|
| `\"` | Двойная кавычка | Чтобы включить кавычку внутри строки |
| `\\` | Обратный слеш | Чтобы включить сам обратный слеш |
| `\/` | Прямой слеш | Опционально (можно писать `/` без escape) |
| `\n` | Новая строка (LF) | Перенос строки в тексте |
| `\r` | Возврат каретки (CR) | Для совместимости с Windows (`\r\n`) |
| `\t` | Табуляция | Отступы в тексте |
| `\b` | Backspace | Редко используется |
| `\f` | Form feed | Редко используется |
| `\uXXXX` | Unicode символ (4 hex цифры) | Для символов вне ASCII |

**Примеры использования:**

```json

{
  "message": "He said \"Hello\" to me",
  "windows_path": "C:\\Users\\Documents\\file.txt",
  "unix_path": "/home/user/documents/file.txt",
  "multiline": "Line 1\nLine 2\nLine 3",
  "emoji": "Smile: \u263A or 😊",
  "mixed": "Text with \"quotes\" and\nnewlines"
}

```

**Важно:** В JSON строки не могут содержать реальные переносы строк. Все переносы должны быть экранированы через `\n`.

### 2.3 Числа (Numbers)

**Почему JSON не поддерживает специальные форматы чисел?**

JSON использует десятичную систему счисления без специальных префиксов. Это решение упрощает парсинг и обеспечивает переносимость между языками:

- **Нет hex/octal** — разные языки интерпретируют их по-разному

- **Нет Infinity/NaN** — не все языки их поддерживают одинаково

- **Нет ведущих нулей** — могут интерпретироваться как octal в некоторых языках

**Формат числа в JSON:**

```

[знак][целая часть][.дробная часть][e/E][знак экспоненты][экспонента]

  -      42         .14159         e    -                 3
```

**Поддерживаемые форматы:**

| Формат | Пример | Описание |
|--------|--------|----------|
| Целое положительное | `42` | Обычное целое число |
| Целое отрицательное | `-17` | Отрицательное число |
| Дробное | `3.14159` | Десятичная дробь |
| Экспоненциальная запись | `1.5e10` | 1.5 × 10¹⁰ = 15000000000 |
| Отрицательная экспонента | `2.5e-3` | 2.5 × 10⁻³ = 0.0025 |
| Ноль | `0` | Ноль (может быть `0.0`) |

```json

{
  "integer": 42,
  "negative": -17,
  "float": 3.14159,
  "exponent": 1.5e10,
  "negativeExp": 2.5e-3,
  "zero": 0,
  "large": 1e308,
  "small": 1e-308
}

```

**Не поддерживаются:**

| Формат | Пример | Почему не поддерживается |
|--------|--------|--------------------------|
| Ведущие нули | `007` | Может интерпретироваться как octal |
| Hex числа | `0xFF` | Не все языки поддерживают одинаково |
| Infinity | `Infinity` | Не все языки имеют этот тип |
| NaN | `NaN` | Разные языки обрабатывают по-разному |
| Октальные | `0o755` | Не стандартизировано |
| Двоичные | `0b1010` | Не стандартизировано |

**Ограничения точности:**

JSON не определяет точность чисел, что может привести к проблемам:

```json

{
  "large_integer": 9007199254740992,
  "precision_issue": 0.1 + 0.2
}

```

**Проблема:** JavaScript использует IEEE 754 double precision, где максимальное безопасное целое — `2^53 - 1` (9007199254740991). Большие числа могут терять точность.

**Решение:** Для больших чисел используйте строки:

```json

{
  "id": "9007199254740993",
  "precise_decimal": "123.45678901234567890"
}

```

### 2.4 Массивы (Arrays)

**Структура массива:**

```

[  элемент1, элемент2, элемент3, ...  ]
↑                                    ↑
начало                             конец
```

Массивы в JSON — это упорядоченные списки значений. Индексация начинается с 0.

**Характеристики массивов:**

- **Упорядоченность** — порядок элементов сохраняется

- **Гетерогенность** — могут содержать разные типы

- **Вложенность** — могут содержать другие массивы и объекты

- **Динамический размер** — могут быть пустыми или содержать любое количество элементов

```json

{
  "numbers": [1, 2, 3, 4, 5],
  "strings": ["apple", "banana", "cherry"],
  "mixed": [1, "two", true, null],
  "nested": [[1, 2], [3, 4]],
  "empty": [],
  "complex": [
    {"id": 1, "name": "Alice"},
    {"id": 2, "name": "Bob"}
  ]
}

```

**Визуальное представление:**

```

Array: [1, 2, 3, 4, 5]
       │  │  │  │  │
       │  │  │  │  └─ [4] = 5
       │  │  │  └──── [3] = 4
       │  │  └─────── [2] = 3
       │  └────────── [1] = 2
       └───────────── [0] = 1
```

**Использование массивов:**

- Списки однотипных элементов (идентификаторы, теги)
- Упорядоченные коллекции (история событий, результаты поиска)
- Многомерные структуры (матрицы, таблицы)

### 2.5 Объекты (Objects)

**Структура объекта:**

```

{  "ключ1": значение1, "ключ2": значение2, ...  }
↑                                              ↑
начало                                       конец
```

Объекты в JSON — это неупорядоченные наборы пар ключ-значение (ассоциативные массивы, словари, хеш-таблицы).

**Почему ключи в кавычках?**

Ключи объектов в JSON **всегда** должны быть строками в двойных кавычках. Это требование обеспечивает:

1. **Однозначность парсинга** — парсер всегда знает, где начинается ключ
2. **Поддержку специальных символов** — ключи могут содержать пробелы, дефисы и т.д.
3. **Совместимость** — единый формат для всех ключей

```json

{
  "user": {
    "name": "Alice",
    "email": "alice@example.com"
  },
  "settings": {
    "theme": "dark",
    "notifications": {
      "email": true,
      "push": false
    }
  },
  "special-keys": {
    "key with spaces": "value",
    "key-with-dashes": "value",
    "123numeric": "value"
  }
}

```

**Правила объектов:**

| Правило | Описание | Пример |
|---------|----------|--------|
| **Ключи в кавычках** | Всегда двойные кавычки | `"name"` ✅, `name` ❌ |
| **Порядок не гарантирован** | Парсеры могут менять порядок | `{"a":1,"b":2}` может стать `{"b":2,"a":1}` |
| **Дубликаты ключей** | Поведение не определено стандартом | `{"a":1,"a":2}` — undefined |
| **Уникальность ключей** | Рекомендуется использовать уникальные ключи | Лучше избегать дубликатов |

**Визуальное представление:**

```

Object: {"name": "Alice", "age": 30}
        │                │
        │                └─ "age" → 30
        └────────────────── "name" → "Alice"
```

**Вложенность объектов:**

Объекты могут быть вложены друг в друга на любую глубину:

```json

{
  "level1": {
    "level2": {
      "level3": {
        "value": "deep nesting"
      }
    }
  }
}

```

**Использование объектов:**

- Структурированные данные (пользователи, товары, конфигурации)
- Словари и карты (ключ → значение)
- Конфигурационные файлы
- Представление записей из баз данных

### 2.6 Полный пример

```json

{
  "id": 1,
  "name": "John Doe",
  "email": "john@example.com",
  "age": 30,
  "isVerified": true,
  "balance": 1250.50,
  "tags": ["developer", "blogger"],
  "profile": {
    "bio": "Software engineer",
    "avatar": null,
    "social": {
      "twitter": "@johndoe",
      "github": "johndoe"
    }
  },
  "history": [
    {"action": "login", "timestamp": "2024-01-15T10:30:00Z"},
    {"action": "purchase", "timestamp": "2024-01-15T11:45:00Z"}
  ]
}

```

## 3. Распространённые ошибки

Этот раздел поможет избежать самых частых ошибок при работе с JSON. Понимание причин этих ограничений поможет лучше запомнить правила.

### 3.1 Trailing comma (хвостовая запятая)

**Что такое trailing comma?**

Trailing comma (хвостовая запятая) — это запятая после последнего элемента в массиве или объекте.

**Почему это запрещено?**

В JSON trailing comma запрещена по нескольким причинам:

1. **Упрощение парсера** — парсеру не нужно проверять, является ли запятая последней
2. **Избежание двусмысленности** — запятая после последнего элемента может быть интерпретирована как начало нового элемента
3. **Совместимость** — не все парсеры обрабатывают trailing comma одинаково

❌ **Ошибка:**

```json

{
  "name": "Alice",
  "age": 30,
}

```

**Ошибка парсера:**
```

SyntaxError: Unexpected token } in JSON at position 25
```

✅ **Правильно:**

```json

{
  "name": "Alice",
  "age": 30
}

```

**Исключение:** В некоторых языках (JavaScript ES5+, Python) trailing comma разрешена в объектах и массивах, но не в JSON.

**Практический совет:** При редактировании JSON вручную легко забыть удалить запятую при удалении последнего элемента. Используйте валидаторы для проверки.

### 3.2 Одинарные кавычки

**Почему только двойные кавычки?**

JSON требует двойные кавычки для строк и ключей объектов. Это одно из самых строгих правил JSON.

**Причины:**

1. **Единообразие** — один способ записи упрощает парсинг
2. **Совместимость** — JavaScript объектные литералы используют двойные кавычки
3. **Избежание конфликтов** — одинарные кавычки часто используются в других контекстах (SQL, HTML)

❌ **Ошибка:**

```json

{
  'name': 'Alice',
  "description": 'User name'
}

```

**Ошибка парсера:**
```

SyntaxError: Expected property name or '}' in JSON at position 2
```

✅ **Правильно:**

```json

{
  "name": "Alice",
  "description": "User name"
}

```

**Важно:** Это правило распространяется и на ключи объектов, и на значения строк.

### 3.3 Комментарии

**Почему JSON не поддерживает комментарии?**

Это одно из самых спорных решений в дизайне JSON. Дуглас Крокфорд объясняет это так:

1. **Упрощение парсера** — комментарии усложняют парсинг
2. **Избежание проблем** — комментарии могут содержать важную информацию, которая теряется при обработке
3. **Минимализм** — JSON должен быть максимально простым

**История:** Изначально JSON поддерживал комментарии (как в JavaScript), но они были удалены из спецификации для упрощения.

❌ **Ошибка:**

```json

{
  "name": "Alice",  // user name
  /* multi-line comment */
  "age": 30
}

```

**Ошибка парсера:**
```

SyntaxError: Unexpected token / in JSON at position 20
```

✅ **JSON не поддерживает комментарии!**

**Альтернативы для конфигураций с комментариями:**

| Формат | Поддержка комментариев | Использование |
|--------|------------------------|---------------|
| **JSON** | ❌ Нет | API, обмен данными |
| **JSONC** | ✅ Да (`//`, `/* */`) | VS Code settings, конфиги |
| **JSON5** | ✅ Да (`//`, `/* */`) | Конфигурации, более читаемый JSON |
| **YAML** | ✅ Да (`#`) | Конфигурации, CI/CD |
| **TOML** | ✅ Да (`#`) | Конфигурации (Cargo, Poetry) |

> **💡 Pro Tip:**  
> Для конфигураций с комментариями используйте YAML, JSONC (VS Code), или JSON5. Для API и обмена данными — строгий JSON.

### 3.4 Unquoted keys (ключи без кавычек)

**Почему ключи должны быть в кавычках?**

В JavaScript объектных литералах ключи могут быть без кавычек, если они являются валидными идентификаторами. В JSON это запрещено.

**Причины:**

1. **Однозначность** — парсер всегда знает, где начинается ключ
2. **Специальные символы** — ключи могут содержать пробелы, дефисы и другие символы
3. **Совместимость** — единый формат для всех парсеров

❌ **Ошибка:**

```json

{
  name: "Alice",
  user-name: "Bob",
  "valid-key": "Charlie"
}

```

**Ошибка парсера:**
```

SyntaxError: Expected property name or '}' in JSON at position 7
```

✅ **Правильно:**

```json

{
  "name": "Alice",
  "user-name": "Bob",
  "valid-key": "Charlie"
}

```

**Важно:** Даже если ключ является валидным идентификатором JavaScript, в JSON он должен быть в кавычках.

### 3.5 Специальные числа

**Почему Infinity и NaN не поддерживаются?**

JavaScript имеет специальные числовые значения `Infinity` и `NaN`, но они не являются частью стандарта JSON.

**Причины:**

1. **Не все языки поддерживают** — не все языки программирования имеют эти концепции
2. **Разная семантика** — разные языки обрабатывают их по-разному
3. **Упрощение** — JSON должен быть максимально простым и переносимым

❌ **Ошибка:**

```json

{
  "value": NaN,
  "max": Infinity,
  "min": -Infinity
}

```

**Ошибка парсера:**
```

SyntaxError: Unexpected token N in JSON at position 15
```

✅ **Альтернативы:**

```json

{
  "value": null,
  "max": 1e308,
  "min": -1e308,
  "is_nan": true,
  "is_infinity": true
}

```

**Рекомендации:**

| Ситуация | Решение |
|----------|---------|
| **NaN** | Использовать `null` или добавить флаг `"is_nan": true` |
| **Infinity** | Использовать очень большое число (`1e308`) или флаг |
| **Отрицательная бесконечность** | Использовать очень маленькое число (`-1e308`) |
| **Неопределённость** | Использовать `null` или отдельное поле с описанием |

**Практический пример:**

```json

{
  "calculation_result": null,
  "error": "Division by zero",
  "max_safe_value": 1.7976931348623157e308,
  "metadata": {
    "has_error": true,
    "error_type": "infinity"
  }
}

```

### 6.4 Кастомная сериализация

```python

import json
from datetime import datetime, date
from decimal import Decimal

class CustomEncoder(json.JSONEncoder):
    """Кастомный энкодер для типов, которые JSON не поддерживает."""
    
    def default(self, obj):
        if isinstance(obj, datetime):
            return obj.isoformat()
        if isinstance(obj, date):
            return obj.isoformat()
        if isinstance(obj, Decimal):
            return float(obj)
        if isinstance(obj, bytes):
            return obj.decode('utf-8')
        if isinstance(obj, set):
            return list(obj)
        return super().default(obj)

# Использование

data = {
    "timestamp": datetime.now(),
    "price": Decimal("19.99"),
    "tags": {"python", "json"}
}

json_string = json.dumps(data, cls=CustomEncoder, indent=2)
print(json_string)

```

### 6.5 Работа с большими файлами

**Проблема больших JSON файлов:**

Когда JSON файл содержит миллионы записей, загрузка всего файла в память становится проблематичной:

- **Память** — весь файл загружается в RAM

- **Время** — парсинг большого файла занимает много времени

- **Блокировка** — процесс блокируется на время парсинга

**Решение: JSON Lines (JSONL)**

JSON Lines — это формат, где каждая строка файла является отдельным валидным JSON объектом. Это позволяет обрабатывать файл построчно.

**Формат JSON Lines:**

```

{"name": "Alice", "age": 30}
{"name": "Bob", "age": 25}
{"name": "Charlie", "age": 35}
```

Каждая строка — отдельный JSON объект. Нет общего массива или объекта-обёртки.

**Преимущества JSON Lines:**

| Преимущество | Описание |
|--------------|----------|
| **Потоковая обработка** | Можно читать построчно, не загружая весь файл |
| **Эффективность памяти** | Обрабатывается одна запись за раз |
| **Добавление данных** | Легко добавлять новые строки в конец файла |
| **Параллельная обработка** | Можно обрабатывать разные части файла параллельно |

```python

import json

# Для очень больших файлов — построчное чтение JSON Lines
def read_jsonl(filepath):
    """Читает JSON Lines файл (один JSON объект на строку)."""
    with open(filepath, 'r', encoding='utf-8') as f:
        for line_num, line in enumerate(f, 1):
            line = line.strip()
            if line:  # Пропускаем пустые строки
                try:
                    yield json.loads(line)
                except json.JSONDecodeError as e:
                    print(f"Error on line {line_num}: {e}")
                    continue

# Записать JSON Lines
def write_jsonl(filepath, items):
    """Записывает iterable как JSON Lines."""
    with open(filepath, 'w', encoding='utf-8') as f:
        for item in items:
            f.write(json.dumps(item, ensure_ascii=False) + '\n')

# Использование

users = [
    {"name": "Alice", "age": 30},
    {"name": "Bob", "age": 25},
    {"name": "Charlie", "age": 35}
]
write_jsonl("users.jsonl", users)

# Чтение построчно
for user in read_jsonl("users.jsonl"):
    print(user)

```

**Сравнение форматов:**

| Формат | Структура | Использование |
|--------|-----------|---------------|
| **JSON** | Один объект/массив | API ответы, конфигурации |
| **JSON Lines** | Много объектов (по строке) | Логи, большие датасеты, стриминг |

**Пример: обработка большого файла**

```python

# Обработка файла с миллионами записей

def process_large_file(filepath):
    """Обрабатывает большой JSON Lines файл построчно."""
    count = 0
    for record in read_jsonl(filepath):
        # Обработка одной записи
        process_record(record)
        count += 1
        if count % 10000 == 0:
            print(f"Processed {count} records")

# Память используется только для одной записи за раз
```

from jsonschema import validate, ValidationError

schema = {
    "type": "object",

        "age": {"type": "integer", "minimum": 0}
    },

## 8. Альтернативы JSON

**Когда JSON не подходит?**

JSON — отличный формат, но у него есть ограничения. Понимание этих ограничений поможет выбрать правильный формат для задачи.

### 8.1 Когда JSON не подходит

**Ограничения JSON и решения:**

| Ограничение | Проблема | Альтернатива | Когда использовать |
|-------------|----------|--------------|-------------------|
| **Нет комментариев** | Невозможно документировать конфигурацию | YAML, TOML, JSON5, JSONC | Конфигурационные файлы |
| **Verbose для конфигов** | Много кавычек и скобок | YAML, TOML | Человекочитаемые конфиги |
| **Нет бинарных данных** | Нельзя хранить изображения, файлы | Base64 encoding, BSON | Медиа, вложения |
| **Медленный парсинг** | Большие файлы парсятся медленно | MessagePack, Protocol Buffers | Высокопроизводительные системы |
| **Нет схемы** | Нет встроенной валидации структуры | JSON Schema, TypeScript types | API контракты |
| **Большой размер** | Много избыточных символов | MessagePack, CBOR | Сетевой трафик, хранилище |
| **Нет типов данных** | Нет дат, байтов, множеств | BSON, MessagePack | Сложные типы данных |

**Сравнительная таблица форматов:**

| Формат | Тип | Комментарии | Бинарный | Скорость | Размер | Использование |
|--------|-----|-------------|----------|----------|--------|---------------|
| **JSON** | Текстовый | ❌ | ❌ | Средняя | Средний | API, обмен данными |
| **YAML** | Текстовый | ✅ | ❌ | Медленная | Большой | Конфигурации, CI/CD |
| **TOML** | Текстовый | ✅ | ❌ | Средняя | Средний | Конфигурации (Rust, Python) |
| **JSON5** | Текстовый | ✅ | ❌ | Средняя | Средний | Улучшенный JSON |
| **MessagePack** | Бинарный | ❌ | ✅ | Быстрая | Малый | Высокая производительность |
| **BSON** | Бинарный | ❌ | ✅ | Быстрая | Средний | MongoDB |
| **Protocol Buffers** | Бинарный | ❌ | ✅ | Очень быстрая | Очень малый | Микросервисы, gRPC |
| **XML** | Текстовый | ✅ | ❌ | Медленная | Большой | Документы, старые системы |

## 9. Best Practices

**Зачем нужны best practices?**

Следование best practices при работе с JSON обеспечивает:

1. **Совместимость** — данные работают во всех системах
2. **Читаемость** — код и данные легче понимать
3. **Поддерживаемость** — проще вносить изменения
4. **Производительность** — оптимальная обработка данных

### 9.1 Именование ключей

**Выбор стиля именования:**

В JSON нет строгих правил для именования ключей, но важно выбрать один стиль и придерживаться его во всём проекте.

**Популярные стили:**

| Стиль | Пример | Где используется | Преимущества |
|-------|--------|-------------------|--------------|
| **camelCase** | `firstName`, `lastName` | JavaScript, Java | Компактность, стандарт JS |
| **snake_case** | `first_name`, `last_name` | Python, Ruby, SQL | Читаемость, стандарт Python |
| **kebab-case** | `first-name`, `last-name` | HTML, CSS, URL | Читаемость, URL-friendly |
| **PascalCase** | `FirstName`, `LastName` | C#, TypeScript types | Ясность, типы |

```json

// ✅ camelCase (JavaScript style)
{"firstName": "Alice", "lastName": "Smith"}

// ✅ snake_case (Python style)
{"first_name": "Alice", "last_name": "Smith"}

// ❌ Смешивание стилей
{"firstName": "Alice", "last_name": "Smith"}

// ❌ Пробелы в ключах (технически валидно, но не рекомендуется)
{"first name": "Alice"}

```

**Рекомендации:**

- **Выберите один стиль** для всего проекта

- **Используйте осмысленные имена** — `userName` лучше, чем `un`

- **Избегайте сокращений** — `firstName` лучше, чем `fn`

- **Будьте последовательны** — если начали с `camelCase`, продолжайте

### 9.2 Даты и время

**Проблема с датами в JSON:**

JSON не имеет встроенного типа для дат и времени. Они должны быть представлены как строки, но какой формат использовать?

**ISO 8601 — стандарт де-факто:**

ISO 8601 — международный стандарт для представления дат и времени. Он обеспечивает:

1. **Однозначность** — формат понятен всем системам
2. **Сортировка** — строки сортируются в хронологическом порядке
3. **Часовые пояса** — поддержка UTC и локальных зон
4. **Точность** — поддержка миллисекунд и микросекунд

**Формат ISO 8601:**

```

YYYY-MM-DDTHH:mm:ss[.sss][Z|±HH:mm]
│    │  │  │ │  │  │      │  │
│    │  │  │ │  │  │      │  └─ Часовой пояс
│    │  │  │ │  │  │      └──── UTC (Z) или смещение
│    │  │  │ │  │  └─────────── Дробные секунды
│    │  │  │ │  └────────────── Секунды
│    │  │  │ └───────────────── Минуты
│    │  │  └─────────────────── Часы
│    │  └────────────────────── Разделитель даты/времени
│    └────────────────────────── День
└─────────────────────────────── Год
```

```json

// ✅ ISO 8601 format (рекомендуется)
{
  "created_at": "2024-01-15T10:30:00Z",
  "updated_at": "2024-01-15T10:30:00+03:00",
  "timestamp": "2024-01-15T10:30:00.123Z",
  "date_only": "2024-01-15"
}

// ❌ Нестандартные форматы (избегайте)
{
  "date": "01/15/2024",
  "time": "10:30 AM",
  "datetime": "January 15, 2024 10:30 AM",
  "unix_timestamp": 1705312200
}

```

**Почему ISO 8601?**

| Преимущество | Описание |
|--------------|----------|
| **Стандарт** | Признан во всём мире |
| **Сортировка** | Лексикографическая сортировка = хронологическая |
| **Парсинг** | Поддерживается всеми языками |
| **Часовые пояса** | Явное указание UTC или смещения |

**Примеры использования:**

```json

{
  "events": [
    {
      "id": 1,
      "name": "Meeting",
      "start_time": "2024-01-15T09:00:00Z",
      "end_time": "2024-01-15T10:00:00Z",
      "timezone": "UTC"
    },
    {
      "id": 2,
      "name": "Conference",
      "start_time": "2024-01-15T14:00:00+03:00",
      "end_time": "2024-01-15T18:00:00+03:00",
      "timezone": "Europe/Moscow"
    }
  ]
}

```

## 10. Common Pitfalls

### 10.1 Кодировка файла

❌ **Ошибка:** Сохранять JSON не в UTF-8

```python
# Всегда указывайте encoding

with open("data.json", "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False)

```

### 10.2 Неэкранированные строки

❌ **Ошибка:**

```json

{"message": "Line 1
Line 2"}

```

✅ **Правильно:**

```json

{"message": "Line 1\nLine 2"}

```

### 10.3 Decimal и float

❌ **Проблема:**

```python

import json
from decimal import Decimal

# Ошибка!
json.dumps({"price": Decimal("19.99")})
# TypeError: Object of type Decimal is not JSON serializable
```

✅ **Решение:**

```python

json.dumps({"price": Decimal("19.99")}, default=str)
# или используйте CustomEncoder из раздела 6.4

```

### 10.4 Круговые ссылки

❌ **Проблема:**

```python

a = {"b": None}
b = {"a": a}
a["b"] = b

json.dumps(a)
# ValueError: Circular reference detected

```

✅ **Решение:** Избегайте циклических структур или используйте специальные библиотеки.

## 💡 Key Takeaways

**Основные выводы из этого модуля:**

- **JSON — простой и универсальный формат**: 6 типов данных (string, number, boolean, null, array, object), строгий синтаксис, нет комментариев. Создан Дугласом Крокфордом в 2001 году для упрощения обмена данными в веб-приложениях.

- **Валидация критически важна**: Всегда проверяйте JSON перед использованием. Используйте `jq .` или `python -m json.tool` для проверки синтаксиса. Ошибки в JSON могут привести к сбоям приложения.

- **jq — мощный инструмент командной строки**: Не только валидация, но и фильтрация, трансформация, агрегация данных. Незаменим для работы с API и логами.

- **Кодировка — UTF-8 обязательна**: JSON по стандарту RFC 8259 должен быть в UTF-8. Всегда используйте `encoding='utf-8'` и `ensure_ascii=False` в Python для корректной работы с нелатинскими символами.

- **Даты — ISO 8601 стандарт**: Используйте формат `2024-01-15T10:30:00Z` для дат и времени. Это обеспечивает совместимость, сортировку и правильную обработку часовых поясов.

- **Понимание ограничений**: JSON не поддерживает комментарии, trailing comma, специальные числа (Infinity, NaN). Для конфигураций с комментариями используйте YAML, JSONC или JSON5.

- **Best practices важны**: Выберите один стиль именования (camelCase или snake_case) и придерживайтесь его. Используйте ISO 8601 для дат, строковые ID для больших чисел, явные null для опциональных полей.
