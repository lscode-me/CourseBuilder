# Операционные и технические сложности
## Отказы, latency, масштабирование и SLA

---

## 🎯 Learning Objectives

- Понимать операционные риски платёжных систем
- Знать требования к надёжности и производительности
- Понимать SLA и мониторинг

---

## 1. Критичность платежей

### 1.1 Почему важна надёжность

- Прямые финансовые потери
- Репутационный ущерб
- Регуляторные санкции
- Потеря клиентов

### 1.2 Ожидания

| Аспект | Требование |
|--------|------------|
| Доступность | 99.9-99.99% |
| Latency | <200-500ms |
| Успешность | >99% |
| Восстановление | <30 минут |

---

## 2. Типы отказов

### 2.1 Технические

| Тип | Причина | Последствия |
|-----|---------|-------------|
| Инфраструктура | Падение серверов, сети | Полная недоступность |
| Приложение | Баги, утечки памяти | Ошибки, таймауты |
| База данных | Блокировки, переполнение | Медленные операции |
| Зависимости | Падение партнёров | Невозможность обработки |

### 2.2 Операционные

- Человеческие ошибки
- Неудачные релизы
- Неправильные конфигурации
- Исчерпание лимитов

### 2.3 Внешние

- DDoS-атаки
- Сбои провайдеров
- Форс-мажоры

---

## 3. Latency

### 3.1 Компоненты

```
Общий latency = Network + Application + Database + External APIs
```

### 3.2 Типичные значения

| Компонент | Latency |
|-----------|---------|
| Сеть клиента | 10-100ms |
| Наше приложение | 20-50ms |
| База данных | 5-20ms |
| Платёжная система | 100-500ms |
| Банк | 200-1000ms |

### 3.3 Оптимизация

- Кэширование
- Connection pooling
- Асинхронные операции
- Географическое распределение
- Оптимизация запросов

## 4. Масштабирование

### 4.1 Вызовы

- Пиковые нагрузки (Black Friday, праздники)
- Рост бизнеса
- Сезонность

### 4.2 Стратегии

| Тип | Подход |
|-----|--------|
| Вертикальное | Более мощные серверы |
| Горизонтальное | Больше серверов |

### 4.3 Архитектурные паттерны

- Микросервисы
- Event-driven
- CQRS (разделение read/write)
- Шардинг данных

## 5. SLA и SLO

### 5.1 Определения

- **SLA** (Service Level Agreement) — контракт с клиентом
- **SLO** (Service Level Objective) — внутренние цели
- **SLI** (Service Level Indicator) — метрики

### 5.2 Типичные SLA

| Метрика | SLA |
|---------|-----|
| Uptime | 99.9% (8.76 часов простоя/год) |
| Latency (p99) | <500ms |
| Успешность | >99.5% |

### 5.3 Расчёт доступности

```
99.9% = 8.76 часов простоя в год = 43.8 минут в месяц
99.99% = 52.6 минут простоя в год = 4.38 минут в месяц
```

### 5.4 Компенсации

| Уровень | Компенсация |
|---------|-------------|
| <99.9% | 10% скидка |
| <99.5% | 25% скидка |
| <99.0% | 50% скидка |

## 6. Мониторинг

### 6.1 Что мониторить

| Уровень | Метрики |
|---------|---------|
| Инфраструктура | CPU, RAM, Disk, Network |
| Приложение | Latency, Errors, Throughput |
| Бизнес | Транзакции, Конверсия, Revenue |
| Зависимости | Доступность, Latency |

### 6.2 Инструменты

- **Metrics:** Prometheus, Datadog
- **Logs:** ELK, Splunk
- **Tracing:** Jaeger, Zipkin
- **Alerting:** PagerDuty, OpsGenie

### 6.3 Dashboards

- Real-time статус
- Исторические тренды
- Сравнение с SLO
- Drill-down

## 7. Реагирование на инциденты

### 7.1 Процесс

```
Обнаружение → Оценка → Эскалация → Устранение → Post-mortem
```

### 7.2 Роли

| Роль | Обязанности |
|------|-------------|
| On-call | Первичная реакция |
| Incident Commander | Координация |
| SME | Техническое решение |
| Communications | Информирование |

### 7.3 Severity

| Уровень | Описание | Время реакции |
|---------|----------|---------------|
| P1 | Полный отказ | 5 минут |
| P2 | Частичный отказ | 30 минут |
| P3 | Деградация | 4 часа |
| P4 | Минорные проблемы | 24 часа |

## 8. Disaster Recovery

### 8.1 Стратегии

| Стратегия | RTO | RPO | Стоимость |
|-----------|-----|-----|-----------|
| Backup | Часы | Часы | Низкая |
| Warm standby | Минуты | Минуты | Средняя |
| Hot standby | Секунды | Минимальный | Высокая |
| Multi-region | Секунды | Нет потерь | Очень высокая |

### 8.2 Ключевые метрики

- **RTO** (Recovery Time Objective) — время восстановления
- **RPO** (Recovery Point Objective) — допустимая потеря данных

---

## 9. Best Practices

### 9.1 Проектирование

- Design for failure
- Graceful degradation
- Circuit breakers
- Retry с exponential backoff
- Idempotency

### 9.2 Операции

- Chaos engineering
- Regular failover testing
- Capacity planning
- Runbooks для инцидентов

### 9.3 Платёжная специфика

- Reconciliation всех транзакций
- Idempotency keys
- Timeout handling
- Резервные каналы

---

## 💡 Key Takeaways

- **Платёжные системы критичны** — требуют высокой надёжности
- **SLA 99.9%** — стандарт индустрии
- **Мониторинг обязателен** — метрики, логи, алерты
- **Инциденты неизбежны** — важна скорость реакции
- **Design for failure** — принцип проектирования
