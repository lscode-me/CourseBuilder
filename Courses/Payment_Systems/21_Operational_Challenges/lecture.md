## 1. Критичность платёжных систем

### 1.1 Почему платежи особенно критичны

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                   ПОЧЕМУ ПЛАТЕЖИ — КРИТИЧЕСКАЯ ИНФРАСТРУКТУРА              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   💰 ПРЯМЫЕ ФИНАНСОВЫЕ ПОТЕРИ                                               │
│   • Каждая минута простоя = потерянные продажи                             │
│   • Крупный ритейлер: $1M+ потерь в час при отказе платежей                │
│   • Black Friday: $100K+ в минуту для крупных магазинов                    │
│                                                                             │
│   📉 РЕПУТАЦИОННЫЙ УЩЕРБ                                                    │
│   • "Магазин не принимает карты" = отток клиентов                          │
│   • Социальные сети усиливают негатив                                       │
│   • Восстановление репутации — годы                                         │
│                                                                             │
│   ⚖️ РЕГУЛЯТОРНЫЕ САНКЦИИ                                                   │
│   • Платёжные системы (Visa/MC) требуют SLA                                 │
│   • Штрафы за систематические проблемы                                      │
│   • Риск отзыва лицензии/прекращения сотрудничества                        │
│                                                                             │
│   🔗 ЗАВИСИМОСТИ БИЗНЕС-ПРОЦЕССОВ                                          │
│   • Заказы не могут быть завершены                                          │
│   • Логистика блокируется                                                   │
│   • Цепочка проблем распространяется                                        │
│                                                                             │
│   📊 ПРИМЕРЫ КРУПНЫХ ИНЦИДЕНТОВ:                                           │
│   • Visa outage (2018): 5.2M транзакций за 10 часов в Европе               │
│   • RBS outage (2012): 6.5M клиентов без доступа к счетам неделями         │
│   • TSB migration (2018): 1.9M клиентов заблокированы, £330M убытков       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 Ожидания к платёжным системам

| Параметр | Минимум | Хороший уровень | Отличный уровень |
|----------|---------|-----------------|------------------|
| Доступность (Uptime) | 99.5% | 99.9% | 99.99% |
| Latency (P50) | <500ms | <200ms | <100ms |
| Latency (P99) | <2s | <1s | <500ms |
| Успешность транзакций | 97% | 99% | 99.5% |
| Время восстановления (RTO) | <4 часа | <1 час | <15 мин |
| Допустимая потеря данных (RPO) | <1 час | <5 мин | 0 |

### 1.3 Расчёт доступности

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       РАСЧЁТ ДОСТУПНОСТИ (SLA)                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   SLA             Простой в год       Простой в месяц    Простой в неделю  │
│   ─────────       ─────────────       ───────────────    ────────────────  │
│   99%             3.65 дня            7.3 часа           1.68 часа          │
│   99.5%           1.83 дня            3.65 часа          50.4 минуты        │
│   99.9%           8.76 часа           43.8 минуты        10.1 минуты        │
│   99.95%          4.38 часа           21.9 минуты        5.04 минуты        │
│   99.99%          52.6 минуты         4.38 минуты        1.01 минуты        │
│   99.999%         5.26 минуты         26.3 секунды       6.05 секунды       │
│                                                                             │
│   ФОРМУЛА:                                                                  │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Uptime % = (Total Time - Downtime) / Total Time × 100               │  │
│   │                                                                      │  │
│   │ Пример: 99.9% за месяц                                               │  │
│   │ Total = 30 × 24 × 60 = 43,200 минут                                  │  │
│   │ Max Downtime = 43,200 × 0.001 = 43.2 минуты                          │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   КОМПОЗИТНАЯ ДОСТУПНОСТЬ (последовательные зависимости):                  │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Total SLA = SLA₁ × SLA₂ × SLA₃ × ...                                │  │
│   │                                                                      │  │
│   │ Пример: Gateway (99.9%) → Processor (99.9%) → Bank (99.9%)          │  │
│   │ Total = 0.999 × 0.999 × 0.999 = 0.997 = 99.7%                       │  │
│   │                                                                      │  │
│   │ ⚠️ Чем больше зависимостей, тем ниже общая доступность!            │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. Типы отказов платёжных систем

### 2.1 Классификация отказов

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         ТИПЫ ОТКАЗОВ                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ПОЛНЫЙ ОТКАЗ (Hard failure)                                               │
│   ├── Система полностью недоступна                                          │
│   ├── Все транзакции отклоняются                                            │
│   └── Причины: катастрофический сбой, потеря связи с ЦОД                   │
│                                                                             │
│   ЧАСТИЧНЫЙ ОТКАЗ (Partial failure)                                         │
│   ├── Часть функций работает                                                │
│   ├── Определённые типы карт/операций недоступны                           │
│   └── Причины: сбой одного из компонентов/провайдеров                      │
│                                                                             │
│   ДЕГРАДАЦИЯ (Degradation)                                                  │
│   ├── Система работает, но медленно                                         │
│   ├── Повышенный процент ошибок                                             │
│   └── Причины: перегрузка, проблемы с БД, утечки памяти                    │
│                                                                             │
│   INTERMITTENT (Периодические сбои)                                         │
│   ├── Случайные отказы отдельных транзакций                                │
│   ├── Сложно диагностировать                                                │
│   └── Причины: race conditions, сетевые проблемы, таймауты                 │
│                                                                             │
│   SILENT FAILURES (Тихие отказы)                                            │
│   ├── Система думает, что работает                                          │
│   ├── Данные повреждаются или теряются                                      │
│   └── Причины: баги логики, несогласованность данных                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 Технические причины отказов

| Уровень | Тип проблемы | Примеры | Последствия |
|---------|--------------|---------|-------------|
| **Инфраструктура** | Hardware | Отказ диска, сервера, сетевого оборудования | Полная/частичная недоступность |
| | Network | Потеря связи, congestion, packet loss | Таймауты, разрывы |
| | Cloud | AWS/GCP outage, проблемы availability zone | Массовый простой |
| **Приложение** | Баги | NPE, race conditions, deadlocks | Ошибки, crashes |
| | Ресурсы | Memory leaks, file descriptor exhaustion | Деградация, OOM |
| | Конфигурация | Неправильные настройки, credentials | Отказ подключений |
| **База данных** | Блокировки | Lock contention, deadlocks | Замедление |
| | Ёмкость | Disk full, connection pool exhaustion | Отказ записи |
| | Репликация | Replication lag, split-brain | Inconsistency |
| **Зависимости** | Внешние API | Падение банка, ПС, провайдера | Невозможность обработки |
| | Timeout | Медленный ответ партнёра | Накопление очередей |

### 2.3 Операционные причины

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ОПЕРАЦИОННЫЕ ПРИЧИНЫ ОТКАЗОВ                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   👤 ЧЕЛОВЕЧЕСКИЙ ФАКТОР                                                    │
│   • Ошибки при деплое (неправильная версия, конфигурация)                  │
│   • Случайное удаление данных                                               │
│   • Неправильные изменения в БД                                             │
│   • Ошибки при масштабировании                                              │
│   → Статистика: 60-80% инцидентов связаны с human error                    │
│                                                                             │
│   🚀 РЕЛИЗЫ И ИЗМЕНЕНИЯ                                                     │
│   • Регрессии в новом коде                                                  │
│   • Несовместимость версий                                                  │
│   • Неполное тестирование                                                   │
│   • Проблемы миграций данных                                                │
│   → Change freeze в критичные периоды (Black Friday)                       │
│                                                                             │
│   📈 CAPACITY                                                               │
│   • Неожиданный рост нагрузки                                               │
│   • Исчерпание лимитов (API rate limits, connections)                      │
│   • Недостаток ресурсов при пиках                                          │
│   → Capacity planning и load testing обязательны                           │
│                                                                             │
│   📜 ПРОЦЕССНЫЕ                                                             │
│   • Истёкшие сертификаты                                                    │
│   • Не продлённые лицензии/контракты                                       │
│   • Забытые scheduled jobs                                                  │
│   → Automation и monitoring предотвращают                                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.4 Внешние угрозы

| Угроза | Описание | Защита |
|--------|----------|--------|
| **DDoS** | Массированная атака на отказ в обслуживании | WAF, CDN, rate limiting |
| **Атаки на API** | Credential stuffing, enumeration | Rate limiting, CAPTCHA |
| **Сбои провайдеров** | AWS/GCP outage, ISP проблемы | Multi-cloud, failover |
| **Форс-мажоры** | Природные катастрофы, отключение электричества | Geo-redundancy |

### 3.2 Метрики latency

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      МЕТРИКИ LATENCY                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ПЕРЦЕНТИЛИ (percentiles):                                                 │
│                                                                             │
│   P50 (median)  — 50% запросов быстрее этого значения                      │
│   P90           — 90% запросов быстрее                                      │
│   P95           — 95% запросов быстрее                                      │

│                                                                             │
│   ПОЧЕМУ ВАЖЕН P99, А НЕ AVERAGE:                                          │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Пример: 1000 транзакций                                              │  │
│   │ • 990 выполнились за 100ms                                           │  │
│   │ • 10 выполнились за 5000ms                                           │  │
│   │                                                                      │  │
│   │ Average = (990×100 + 10×5000) / 1000 = 149ms  ← выглядит хорошо      │  │
│   │ P99 = 5000ms  ← показывает реальную проблему                         │  │
│   │                                                                      │  │
│   │ 10 клиентов из 1000 ждут 5 секунд = плохой UX                       │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   SLO RECOMMENDATIONS:                                                      │
│   • P50 < 200ms   — хороший пользовательский опыт                          │
│   • P99 < 1000ms  — допустимо для платежей                                 │
│   • P99.9 < 3000ms — максимум для редких случаев                           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.3 Оптимизация latency

| Техника | Где применять | Эффект |
|---------|---------------|--------|
| **Connection pooling** | БД, HTTP clients | -50-100ms на запрос |
| **Кэширование** | Справочники, конфиги, BIN-таблицы | -5-50ms |
| **Async processing** | Логирование, аналитика, уведомления | Не блокирует основной поток |
| **CDN / Edge** | Статика, географически близкие PoP | -20-100ms RTT |
| **Prepared statements** | SQL запросы | -5-20ms |
| **Batch operations** | Reconciliation, reporting | Снижение нагрузки |
| **Circuit breakers** | Внешние зависимости | Быстрый fail вместо ожидания |
| **DNS optimization** | Все внешние вызовы | -10-50ms |

│   ┌─────────────────────────────────────────────────────────────────────┐  │

│                                                                             │

│   │                                                                      │  │
│   │ Сценарий:                                                            │  │
│   │ 1. Клиент отправляет платёж                                          │  │

│   │ 4. НО: банк списал деньги на 31-й секунде                           │  │
│   │                                                                      │  │
│   │ Решение: Idempotency key + status check + reconciliation            │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 4. Масштабирование платёжных систем

### 4.1 Причины необходимости масштабирования

| Причина | Описание | Пример |
|---------|----------|--------|
| **Пиковые нагрузки** | Кратковременные всплески | Black Friday: 10x нагрузка |
| **Рост бизнеса** | Органический рост | Новые клиенты, регионы |
| **Сезонность** | Регулярные паттерны | Праздники, зарплатные дни |
| **Маркетинговые акции** | Flash sales, промо | Распродажа — пик за минуты |
| **Новые продукты** | Запуск фич | Новый способ оплаты |

### 4.2 Стратегии масштабирования

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    СТРАТЕГИИ МАСШТАБИРОВАНИЯ                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ВЕРТИКАЛЬНОЕ (Scale Up)                                                   │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ • Увеличение ресурсов одного сервера                                 │  │
│   │ • CPU, RAM, Disk, Network                                            │  │
│   │                                                                      │  │
│   │ ✓ Плюсы: Простота, нет изменений в архитектуре                      │  │
│   │ ✗ Минусы: Ограничения оборудования, дорого, SPOF                   │  │
│   │                                                                      │  │
│   │ Применение: БД (до определённого предела), legacy системы           │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   ГОРИЗОНТАЛЬНОЕ (Scale Out)                                                │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ • Добавление новых серверов/инстансов                               │  │
│   │ • Распределение нагрузки между ними                                 │  │
│   │                                                                      │  │
│   │ ✓ Плюсы: Теоретически неограниченное масштабирование, надёжность    │  │
│   │ ✗ Минусы: Сложность архитектуры, state management                  │  │
│   │                                                                      │  │
│   │ Применение: Stateless сервисы, API gateways, workers                │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   АВТОМАСШТАБИРОВАНИЕ (Auto-scaling)                                        │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ • Автоматическое добавление/удаление ресурсов                       │  │
│   │ • На основе метрик (CPU, requests, queue length)                    │  │
│   │                                                                      │  │
│   │ Правила:                                                             │  │
│   │ • Scale out: CPU > 70% в течение 5 минут → +2 инстанса              │  │
│   │ • Scale in: CPU < 30% в течение 15 минут → -1 инстанс               │  │
│   │                                                                      │  │
│   │ ⚠️ Важно: Warm-up time (время запуска новых инстансов)              │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 5. SLA, SLO и SLI

### 5.1 Определения

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      SLA / SLO / SLI                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   SLI (Service Level Indicator) — МЕТРИКА                                   │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Конкретное измеримое значение качества сервиса                      │  │
│   │                                                                      │  │
│   │ Примеры:                                                             │  │
│   │ • Request latency (P99)                                              │  │
│   │ • Error rate                                                         │  │
│   │ • Availability (% successful requests)                               │  │
│   │ • Throughput (requests per second)                                   │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   SLO (Service Level Objective) — ЦЕЛЬ                                      │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Целевое значение SLI, к которому стремится команда                  │  │
│   │                                                                      │  │
│   │ Примеры:                                                             │  │
│   │ • P99 latency < 500ms                                                │  │
│   │ • Error rate < 0.1%                                                  │  │
│   │ • Availability > 99.9%                                               │  │
│   │                                                                      │  │
│   │ SLO обычно строже, чем SLA (запас)                                  │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   SLA (Service Level Agreement) — КОНТРАКТ                                  │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Юридически обязывающее соглашение с клиентом                        │  │
│   │                                                                      │  │
│   │ Содержит:                                                            │  │
│   │ • Гарантируемые уровни сервиса                                      │  │
│   │ • Методику измерения                                                 │  │
│   │ • Компенсации при нарушении                                          │  │
│   │ • Исключения (planned maintenance, force majeure)                   │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   ВЗАИМОСВЯЗЬ:                                                              │
│                                                                             │
│   SLI (измеряем) → SLO (целимся) → SLA (обещаем клиенту)                   │
│        ↑                                      │                            │
│        └──────── feedback loop ───────────────┘                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 Типичные SLA для платёжных систем

| Параметр | Standard SLA | Premium SLA | Enterprise SLA |
|----------|--------------|-------------|----------------|
| Uptime | 99.5% | 99.9% | 99.95% |
| P99 Latency | <2s | <1s | <500ms |
| Error rate | <1% | <0.5% | <0.1% |
| Support response | 24 часа | 4 часа | 1 час |
| Incident resolution | 48 часов | 8 часов | 4 часа |
| Planned maintenance | 8 часов/мес | 4 часа/мес | 2 часа/мес |

### 7.2 Роли в Incident Response

| Роль | Обязанности | Кто |
|------|-------------|-----|

### 7.3 Severity Matrix

| Severity | Описание | TTR Target | Эскалация |
|----------|----------|------------|-----------|
| **P1** | Полный отказ платежей, все клиенты затронуты | <1 час | VP/CTO немедленно |

| **P4** | Минорные проблемы, обходные пути есть | <5 дней | Ticket в backlog |

│   │                                                                      │  │
│   │ • Минимальная инфраструктура DR всегда работает                     │  │
│   │ • App серверы поднимаются по требованию                             │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   WARM STANDBY                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ RTO: минуты    RPO: секунды-минуты    Cost: $$$                     │  │
│   │                                                                      │  │
│   │ [Primary] ══replication══> [Warm DR]                                 │  │
│   │     │                          │                                     │  │
│   │     └── Full infra             └── Full infra (smaller scale)        │  │
│   │                                                                      │  │
│   │ • Полная инфраструктура в DR, но меньшего масштаба                  │  │
│   │ • Быстрое переключение, затем scale up                              │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   HOT STANDBY / MULTI-REGION ACTIVE-ACTIVE                                 │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ RTO: секунды    RPO: ~0    Cost: $$$$                               │  │
│   │                                                                      │  │
│   │ [Region A] ←═══ sync replication ═══→ [Region B]                    │  │
│   │      │                                      │                        │  │
│   │      └────────── Traffic (active) ──────────┘                        │  │
│   │                                                                      │  │
│   │ • Обе площадки активно обрабатывают трафик                          │  │
│   │ • Автоматический failover при отказе региона                        │  │
│   │ • Сложность: data consistency, split-brain                          │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 8.2 RTO и RPO

| Метрика | Определение | Для платежей |
|---------|-------------|--------------|
| **RTO (Recovery Time Objective)** | Максимально допустимое время восстановления сервиса | <30 мин для критичных |
| **RPO (Recovery Point Objective)** | Максимально допустимая потеря данных | 0 для финансовых данных |

### 8.3 Тестирование DR

- **Tabletop exercises** — обсуждение сценариев без реальных действий
- **Walkthrough** — пошаговая проверка процедур
- **Simulation** — тестирование failover на staging
- **Full failover test** — реальное переключение (раз в квартал/год)
- **Chaos engineering** — регулярное внедрение сбоев (Netflix Chaos Monkey)

## 9. Best Practices для платёжных систем

### 9.1 Проектирование для отказов (Design for Failure)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    DESIGN FOR FAILURE PRINCIPLES                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   IDEMPOTENCY (идемпотентность)                                            │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Повторный запрос с тем же idempotency key = тот же результат        │  │
│   │                                                                      │  │
│   │ POST /payments                                                       │  │
│   │ Idempotency-Key: "order-12345-attempt-1"                            │  │
│   │                                                                      │  │
│   │ 1-й запрос: создаёт платёж, возвращает ID                           │  │
│   │ 2-й запрос (retry): возвращает тот же ID без повторного списания   │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   CIRCUIT BREAKER                                                           │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Защита от каскадных отказов при проблемах с зависимостью            │  │
│   │                                                                      │  │
│   │ CLOSED ──(N errors)──> OPEN ──(timeout)──> HALF-OPEN                │  │
│   │    │                     │                     │                     │  │
│   │    │                     │                     ├── success → CLOSED  │  │
│   │    │                     │                     └── fail → OPEN       │  │
│   │    │                     │                                           │  │
│   │    └── requests pass     └── requests fail fast                      │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   RETRY WITH EXPONENTIAL BACKOFF                                            │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Attempt 1: immediate                                                 │  │
│   │ Attempt 2: wait 1s                                                   │  │
│   │ Attempt 3: wait 2s                                                   │  │
│   │ Attempt 4: wait 4s                                                   │  │
│   │ Attempt 5: wait 8s + jitter                                          │  │
│   │                                                                      │  │
│   │ + Jitter (случайность) чтобы избежать thundering herd               │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   GRACEFUL DEGRADATION                                                      │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ При проблемах — снижать функциональность, не падать полностью       │  │
│   │                                                                      │  │
│   │ • Fraud check недоступен → пропускать для мелких сумм               │  │
│   │ • Резервный процессор → переключиться автоматически                 │  │
│   │ • Логирование сломано → не блокировать платежи                      │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   BULKHEAD (изоляция)                                                       │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Изолировать компоненты чтобы сбой одного не влиял на другие         │  │
│   │                                                                      │  │
│   │ • Отдельные thread pools для разных клиентов                        │  │
│   │ • Отдельные instances для VIP клиентов                              │  │
│   │ • Rate limiting per client                                           │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 9.2 Платёжная специфика

| Практика | Описание | Важность |
|----------|----------|----------|
| **Reconciliation** | Ежедневная сверка всех транзакций с банками/ПС | 🔴 Критично |
| **Idempotency keys** | Для всех платёжных операций | 🔴 Критично |
| **Timeout handling** | Отдельная логика для timeout (unknown state) | 🔴 Критично |
| **Audit logging** | Полный лог всех операций для compliance | 🔴 Критично |
| **Резервные каналы** | Backup процессор, второй эквайер | 🟠 Важно |
| **Status page** | Публичная страница статуса для клиентов | 🟠 Важно |

## 💡 Key Takeaways

- **Платёжные системы критичны** — простой приводит к прямым финансовым потерям и репутационному ущербу
- **SLA 99.9%** означает max 43 минуты простоя в месяц — это стандарт индустрии
- **Композитная доступность** падает с количеством зависимостей — упрощайте архитектуру
- **Мониторинг Golden Signals** (Latency, Traffic, Errors, Saturation) обязателен
- **Idempotency** — ключевой принцип для платежей (retry-safe операции)
- **Design for Failure** — предполагайте, что всё сломается, проектируйте соответственно
- **Инцидент-менеджмент** — чёткие роли, процессы, blameless post-mortems
- **DR testing** — регулярно тестируйте failover, не только планируйте
