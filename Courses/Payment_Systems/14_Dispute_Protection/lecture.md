## 2. 3-D Secure

### 2.1 Что такое 3-D Secure

**3-D Secure (3DS)** — протокол аутентификации держателя карты при онлайн-платежах, разработанный Visa (Verified by Visa) и адаптированный другими ПС (Mastercard SecureCode, Amex SafeKey).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    КАК РАБОТАЕТ 3-D SECURE                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ТРИ ДОМЕНА (3 Domains):                                                   │
│                                                                             │
│   ┌───────────────┐   ┌───────────────┐   ┌───────────────┐                │
│   │   ISSUER      │   │ INTEROPERABILITY│  │   ACQUIRER    │               │
│   │   Domain      │   │   Domain       │   │   Domain      │               │
│   │               │   │                │   │               │               │
│   │  • Эмитент    │   │  • Card scheme │   │  • Эквайер    │               │
│   │  • ACS       │   │  • Directory   │   │  • Мерчант    │               │
│   │               │   │    Server      │   │  • 3DS Server │               │
│   └───────────────┘   └───────────────┘   └───────────────┘               │
│                                                                             │
│   ПРОЦЕСС:                                                                  │
│                                                                             │
│   1. Покупатель вводит данные карты на сайте мерчанта                      │
│          │                                                                  │
│          ▼                                                                  │
│   2. 3DS Server мерчанта отправляет Authentication Request                 │
│          │                                                                  │
│          ▼                                                                  │
│   3. Directory Server (Visa/MC) находит ACS эмитента                       │
│          │                                                                  │
│          ▼                                                                  │
│   4. ACS (Access Control Server) эмитента анализирует риск                 │
│          │                                                                  │
│          ├── Low Risk → Frictionless (одобрено без действий)               │
│          │                                                                  │
│          └── High Risk → Challenge (требуется верификация)                 │
│                   │                                                         │
│                   ▼                                                         │
│             5. Верификация (OTP, биометрия, push)                          │
│                   │                                                         │
│                   ▼                                                         │
│   6. ACS возвращает результат аутентификации                               │
│          │                                                                  │
│          ▼                                                                  │
│   7. При успехе — LIABILITY SHIFT к эмитенту                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 Liability Shift

| Сценарий | Ответственность за fraud |
|----------|--------------------------|
| 3DS не применялся | Мерчант (эквайер) |
| 3DS применён, аутентификация успешна | Эмитент (issuer) |
| 3DS применён, эмитент не поддерживает | Эмитент |
| 3DS применён, мерчант получил отказ от эмитента, но провёл платёж | Мерчант |

**Liability shift** означает, что при fraud chargeback на транзакции с успешной 3DS аутентификацией ответственность несёт эмитент, а не мерчант.

### 2.4 Frictionless vs Challenge

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    FRICTIONLESS vs CHALLENGE                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   FRICTIONLESS FLOW (бесшовный):                                            │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ • Эмитент анализирует данные транзакции                             │  │
│   │ • Риск оценивается как низкий                                        │  │
│   │ • Аутентификация происходит "за кадром"                             │  │
│   │ • Покупатель ничего не делает                                        │  │
│   │ • Liability shift сохраняется                                        │  │
│   │                                                                      │  │
│   │ Когда применяется:                                                   │  │
│   │ • Известное устройство/браузер                                       │  │
│   │ • История транзакций с мерчантом                                    │  │
│   │ • Низкая сумма                                                       │  │
│   │ • Соответствие типичному поведению                                   │  │
│   │                                                                      │  │
│   │ 70-95% транзакций могут быть frictionless                           │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   CHALLENGE FLOW (с верификацией):                                          │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ • Эмитент требует дополнительную проверку                           │  │
│   │ • Покупатель подтверждает личность                                   │  │
│   │                                                                      │  │
│   │ Методы верификации:                                                  │  │
│   │ • OTP через SMS                                                      │  │
│   │ • Push-уведомление в мобильный банк                                 │  │
│   │ • Биометрия (отпечаток, Face ID)                                    │  │
│   │ • Ответ на секретный вопрос                                          │  │
│   │                                                                      │  │
│   │ Когда применяется:                                                   │  │
│   │ • Новое устройство                                                   │  │
│   │ • Высокая сумма                                                      │  │
│   │ • Подозрительное поведение                                           │  │
│   │ • Первая транзакция с мерчантом                                     │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.5 Стратегии использования 3DS

| Стратегия | Описание | Применение |
|-----------|----------|------------|
| **3DS для всех** | Все транзакции через 3DS | Максимальная защита, может снизить конверсию |
| **Risk-based 3DS** | 3DS только для рискованных | Баланс защиты и конверсии |
| **Exemptions** | Использование исключений SCA | Для low-value, recurring, whitelisted |
| **Soft decline retry** | Повторная попытка с 3DS при отказе | Восстановление конверсии |

### 2.6 SCA Exemptions (PSD2)

В ЕС PSD2 требует SCA (Strong Customer Authentication), но есть исключения:

| Исключение | Условия | Пример |
|------------|---------|--------|
| **Low Value** | <€30, max 5 tx или €100 | Мелкие покупки |
| **TRA (Transaction Risk Analysis)** | Мерчант с низким fraud rate | Если fraud <0.13% — до €500 |
| **Whitelisting** | Клиент добавил мерчанта в "доверенные" | Регулярные покупки |
| **Recurring** | Повторяющиеся платежи на ту же сумму | Подписки |
| **MIT (Merchant Initiated)** | Инициирован мерчантом | Отложенные списания |

## 3. Fraud Detection

### 3.1 Сигналы риска

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    СИГНАЛЫ РИСКА (RED FLAGS)                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ДАННЫЕ ТРАНЗАКЦИИ:                                                        │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ 🔴 Высокий риск:                                                     │  │
│   │ • Сумма значительно выше средней для этого мерчанта                 │  │
│   │ • Первая транзакция на крупную сумму                                │  │
│   │ • Множество попыток с разными картами                                │  │
│   │ • Несколько заказов за короткое время                                │  │
│   │ • Разные billing и shipping адреса в высокорисковые страны          │  │
│   │                                                                      │  │
│   │ 🟠 Средний риск:                                                     │  │
│   │ • Разные billing/shipping адреса (внутри страны)                    │  │
│   │ • Необычное время покупки (ночь)                                     │  │
│   │ • Экспресс-доставка на крупный заказ                                │  │
│   │ • Электронные товары / gift cards                                    │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   УСТРОЙСТВО И СЕТЬ:                                                        │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ 🔴 Высокий риск:                                                     │  │
│   │ • IP из высокорисковой страны / proxy / VPN / Tor                   │  │
│   │ • Device fingerprint связан с fraud                                  │  │
│   │ • Mismatch IP и billing country                                      │  │
│   │ • Эмулятор или виртуальная машина                                   │  │
│   │                                                                      │  │
│   │ 🟠 Средний риск:                                                     │  │
│   │ • Новое устройство                                                   │  │
│   │ • Браузер с отключенными cookies/JS                                  │  │
│   │ • Mobile vs desktop аномалии                                         │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   ПОВЕДЕНИЕ ПОЛЬЗОВАТЕЛЯ:                                                   │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ 🔴 Высокий риск:                                                     │  │
│   │ • Copy-paste данных карты                                            │  │
│   │ • Прямой переход на checkout (без browsing)                         │  │
│   │ • Множественные изменения адреса                                     │  │
│   │                                                                      │  │
│   │ 🟠 Средний риск:                                                     │  │
│   │ • Быстрое заполнение формы (автозаполнение)                         │  │
│   │ • Отсутствие предыдущей истории на сайте                            │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Инструменты fraud detection

| Инструмент | Описание | Применение |
|------------|----------|------------|
| **Device Fingerprinting** | Уникальный ID устройства на основе 50+ параметров | Выявление повторного fraud |
| **IP Geolocation** | Определение страны, города, ISP по IP | Проверка соответствия billing |
| **Velocity Checks** | Анализ частоты транзакций | Обнаружение card testing |
| **BIN Analysis** | Проверка банка и страны карты | Geographic mismatch |
| **Email Analysis** | Возраст email, связанные breach-и | Выявление synthetic identity |
| **ML Models** | Машинное обучение на исторических данных | Автоматическое scoring |

### 3.3 Rules vs Machine Learning

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    RULES vs MACHINE LEARNING                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   RULES-BASED:                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ IF amount > $500 AND new_customer AND high_risk_country             │  │
│   │    THEN risk = HIGH                                                  │  │
│   │                                                                      │  │
│   │ ✓ Прозрачность — понятно почему сработало                           │  │
│   │ ✓ Быстрое внедрение новых правил                                    │  │
│   │ ✓ Compliance — объяснимые решения                                   │  │
│   │ ✗ Не видит сложные паттерны                                         │  │
│   │ ✗ Легко обойти если знать правила                                   │  │
│   │ ✗ Много false positives                                              │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   MACHINE LEARNING:                                                         │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Модель обучается на миллионах транзакций                            │  │
│   │ Выявляет скрытые паттерны                                            │  │
│   │                                                                      │  │
│   │ ✓ Выявляет сложные зависимости                                      │  │
│   │ ✓ Адаптируется к новым паттернам fraud                              │  │
│   │ ✓ Меньше false positives                                            │  │
│   │ ✗ "Чёрный ящик" — сложно объяснить решение                         │  │
│   │ ✗ Требует много данных для обучения                                 │  │
│   │ ✗ Может упустить новые типы fraud                                   │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   ЛУЧШАЯ ПРАКТИКА: Комбинация Rules + ML                                   │
│   • ML для scoring                                                          │
│   • Rules для known bad patterns                                            │
│   • Rules для compliance                                                    │
│   • Human review для edge cases                                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.4 Действия по уровню риска

| Risk Score | Действие | Примеры |
|------------|----------|---------|
| **Low (0-30)** | Пропустить | Постоянный клиент, типичная покупка |
| **Medium (31-70)** | 3DS / Step-up | Новый клиент, крупная сумма |
| **High (71-90)** | Manual review | Множественные red flags |
| **Very High (91-100)** | Автоматический отказ | Known fraud pattern |

## 4. Верификация данных

### 4.1 AVS (Address Verification Service)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    AVS (ADDRESS VERIFICATION SERVICE)                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   КАК РАБОТАЕТ:                                                             │
│   • Мерчант отправляет billing address с транзакцией                       │
│   • Эмитент сверяет с адресом в своей базе                                 │
│   • Возвращает AVS code                                                     │
│                                                                             │
│   ОСНОВНЫЕ AVS КОДЫ (Visa):                                                 │
│   ┌─────────────────────────────────────────────────────────────────────┐  │
│   │ Code │ Описание                              │ Рекомендация         │  │

│   │  Y   │ Address и ZIP совпадают               │ ✅ Low risk          │  │
│   │  A   │ Только address совпадает              │ ⚠️ Review            │  │
│   │  Z   │ Только ZIP совпадает                  │ ⚠️ Review            │  │
│   │  N   │ Ничего не совпадает                   │ 🔴 High risk         │  │
│   │  U   │ Данные недоступны                     │ ⚠️ Иностранная карта │  │
│   │  R   │ Система недоступна                    │ ⚠️ Retry             │  │
│   │  S   │ AVS не поддерживается                 │ ⚠️ Иностранная карта │  │
│   └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│   ОГРАНИЧЕНИЯ:                                                              │
│   • Работает в основном для US, UK, Canada                                 │
│   • Не все эмитенты поддерживают                                           │  │
│   • Разные форматы адресов в разных странах                                │
│   • Не 100% надёжность (опечатки, переезд)                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 CVV/CVC Verification

| Аспект | Описание |
|--------|----------|
| **Что проверяется** | 3/4-значный код на карте |
| **Цель** | Подтвердить физическое наличие карты |
| **CVV Match** | Код совпадает — низкий риск |
| **CVV Mismatch** | Код не совпадает — отклонить |
| **Ограничение** | Нельзя хранить после авторизации (PCI DSS) |

### 4.3 Дополнительные проверки

| Метод | Описание | Когда применять |
|-------|----------|-----------------|
| **Email verification** | Ссылка подтверждения на email | При регистрации |
| **Phone verification** | SMS-код | Крупные суммы, высокий риск |
| **ID verification** | Проверка документа | KYC требования, очень крупные суммы |
| **Callback** | Звонок клиенту | VIP-заказы, подозрительные транзакции |

## 8. Мониторинг и метрики

### 8.1 Ключевые метрики

| Метрика | Формула | Цель | Alert threshold |
|---------|---------|------|-----------------|
| **Chargeback Ratio** | CB count / TX count | <0.9% | >0.5% warning, >0.9% critical |
| **Chargeback Amount Ratio** | CB amount / TX amount | <0.9% | >0.5% warning |
| **Fraud Rate** | Fraud TX / Total TX | <0.5% | >0.3% warning |
| **Win Rate** | Won CB / Total CB | >30% | <20% review process |
| **Alert Resolution Rate** | Resolved alerts / Total alerts | >90% | <80% |
| **False Positive Rate** | Declined legit / Total declined | <5% | >10% review rules |

## 💡 Key Takeaways

- **3-D Secure** — главная защита от fraud chargebacks; используйте 3DS 2.0 для frictionless flow
- **Liability shift** защищает мерчанта при успешной 3DS аутентификации
- **Alert services** (Ethoca, Verifi) предотвращают регистрацию chargeback — дешевле, чем chargeback
- **Billing descriptor** должен быть узнаваемым — многие CB из-за "не узнаю транзакцию"
- **Быстрая поддержка** с правом делать refund решает проблемы до диспута
- **Для подписок**: reminder перед списанием, easy cancellation, прозрачные условия
- **Документирование** — основа для успешного representment; храните минимум 540 дней
- **Мониторинг** ratio в реальном времени — не допускайте превышения thresholds
