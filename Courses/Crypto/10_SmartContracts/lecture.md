## 1. Что такое смарт-контракт

Смарт-контракт — это самоисполняющийся код, который автоматически выполняет условия соглашения.

### 1.1 Концепция

**Определение:**

- Код, выполняющийся в блокчейне
- Автоматическое выполнение условий
- Нет необходимости в посредниках
- Необратимость выполнения

**Свойства:**

- Детерминированный
- Прозрачный
- Неизменяемый (после деплоя)
- Автономный

**Пример:**
```solidity

// Простой смарт-контракт
contract SimpleStorage {
    uint256 public value;
    
    function setValue(uint256 _value) public {
        value = _value;
    }
    
    function getValue() public view returns (uint256) {
        return value;
    }
}
```

### 1.2 Преимущества

**Автоматизация:**

- Нет необходимости в посредниках
- Автоматическое выполнение
- Снижение издержек

**Прозрачность:**

- Код открыт для всех
- Проверяемость логики
- Доверие через код

**Безопасность:**

- Криптографическая защита
- Децентрализация
- Невозможность изменения

## 2. Язык Solidity

Solidity — основной язык для разработки смарт-контрактов в Ethereum.

### 2.1 Основы Solidity

**Синтаксис:**

- Похож на JavaScript — Solidity был разработан с учётом популярности JavaScript, поэтому синтаксис похож, что облегчает изучение для веб-разработчиков
- Статическая типизация — все переменные должны иметь явно указанный тип (uint256, bool, address и т.д.), что помогает предотвратить ошибки
- Объектно-ориентированный — поддерживает классы (контракты), наследование, полиморфизм

**Типы данных:**

- `uint256`: целые числа
- `bool`: булевы значения
- `address`: адреса Ethereum
- `string`: строки
- `mapping`: ассоциативные массивы

**Пример:**
```solidity

pragma solidity ^0.8.0;

contract Token {
    mapping(address => uint256) public balances;
    
    function transfer(address to, uint256 amount) public {
        require(balances[msg.sender] >= amount, "Insufficient balance");
        balances[msg.sender] -= amount;
        balances[to] += amount;
    }
}
```

### 2.2 Ключевые концепции

**Модификаторы доступа:**

- `public`: доступно всем
- `private`: только внутри контракта
- `internal`: внутри контракта и наследников
- `external`: только извне

**Специальные переменные:**

- `msg.sender`: отправитель транзакции
- `msg.value`: количество отправленного эфира
- `block.timestamp`: время блока
- `address(this)`: адрес контракта

## 3. Типовые паттерны

Существуют стандартные паттерны для распространённых задач.

### 3.1 ERC-20 (Токены)

**Стандарт токенов:**
ERC-20 (Ethereum Request for Comments 20) — это стандарт для создания взаимозаменяемых токенов в Ethereum. Стандарт определяет набор функций, которые должны быть реализованы:

- `transfer`: перевод токенов с одного адреса на другой
- `approve`: разрешение другому адресу тратить токены от вашего имени (используется для децентрализованных бирж и других протоколов)
- `transferFrom`: перевод токенов от имени другого адреса (если было дано разрешение через approve)
Стандартизация позволяет токенам взаимодействовать с различными приложениями и кошельками.

**Пример:**
```solidity

contract ERC20Token {
    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;
    
    function transfer(address to, uint256 amount) public returns (bool) {
        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
        return true;
    }
}
```

### 3.2 Мультисиг

**Мультисиг кошелёк:**

- Требует несколько подписей
- Безопасность через распределение
- Используется для управления средствами

### 3.3 Временные замки

**Timelock:**

- Задержка выполнения
- Защита от спешки
- Время на обдумывание

## 4. Уязвимости и ошибки

Смарт-контракты уязвимы к различным атакам из-за необратимости кода.

### 4.1 Распространённые уязвимости

**Reentrancy:**

- Повторный вызов функции до завершения
- Может привести к краже средств
- Защита: checks-effects-interactions

**Integer Overflow:**

- Переполнение целых чисел
- Решено в Solidity 0.8.0+
- Ранее требовалась библиотека SafeMath

**Front-running:**

- Использование информации из мемпула
- Манипуляция порядком транзакций
- Защита сложна

**Пример уязвимости:**
```solidity

// УЯЗВИМЫЙ КОД - НЕ ИСПОЛЬЗУЙТЕ
contract Vulnerable {
    mapping(address => uint256) public balances;
    
    function withdraw() public {
        uint256 amount = balances[msg.sender];
        (bool success, ) = msg.sender.call{value: amount}("");
        balances[msg.sender] = 0;  // Слишком поздно!
    }
}
```

### 4.2 Best Practices

**Безопасность:**

- Используйте проверенные библиотеки
- Проводите аудит кода
- Тестируйте тщательно
- Используйте формальную верификацию

**Паттерны:**

- Checks-Effects-Interactions (CEI) — паттерн безопасности: сначала проверяем условия (checks), затем обновляем состояние (effects), и только потом взаимодействуем с внешними контрактами (interactions). Это защищает от reentrancy атак.
- Pull over Push payments — вместо отправки средств получателю (push), лучше позволить получателю самому забрать средства (pull). Это даёт больше контроля и защищает от проблем, если получатель — смарт-контракт с ошибками.
- Rate limiting — ограничение частоты операций для защиты от злоупотреблений
- Access control — контроль доступа, использование модификаторов для ограничения доступа к функциям только авторизованным адресам

## 5. Почему код — это закон (и почему это опасно)

"Code is Law" — философия, что код определяет правила, но это имеет риски.

### 5.1 Концепция

**"Code is Law":**

- Код определяет правила
- Нет центрального арбитра
- Автоматическое выполнение
- Нет возможности отмены

**Преимущества:**

- Предсказуемость
- Прозрачность
- Автоматизация
- Децентрализация

### 5.2 Проблемы

**Необратимость:**

- Ошибки нельзя исправить
- Потеря средств необратима
- Нет механизма отката

**Отсутствие гибкости:**

- Нельзя адаптироваться к изменениям
- Сложно обновлять
- Жёсткие правила

**Человеческий фактор:**

- Ошибки программирования
- Непредвиденные сценарии
- Социальные аспекты игнорируются

**Примеры проблем:**

- DAO hack (2016): уязвимость привела к краже $60M. DAO (Decentralized Autonomous Organization — децентрализованная автономная организация) — это организация, управляемая смарт-контрактами без центрального руководства. В 2016 году в смарт-контракте The DAO была обнаружена уязвимость reentrancy, которая позволила злоумышленнику украсть около $60 миллионов в эфире. Это привело к хард-форку Ethereum для возврата средств.
- Parity wallet bug (2017): заморозка $150M — ошибка в смарт-контракте кошелька Parity привела к случайной блокировке средств множества пользователей
- Невозможность отмены ошибочных транзакций

### 5.3 Решения

**Аудит:**

- Проверка кода экспертами
- Выявление уязвимостей
- Рекомендации по улучшению

**Тестирование:**

- Unit тесты
- Integration тесты
- Формальная верификация

**Upgradeable контракты:**
Контракты с возможностью обновления позволяют изменять логику контракта после деплоя. Обычно реализуются через Proxy паттерн (паттерн прокси): существует Proxy контракт, который хранит адрес логики, и при вызове функции прокси перенаправляет вызов на контракт с логикой. При обновлении меняется только адрес логики в прокси, что позволяет обновить функциональность без миграции данных. Однако это создаёт компромисс децентрализации, так как кто-то должен иметь право обновлять контракт, что может быть точкой централизации.

- **Смарт-контракты**: Самоисполняющийся код в блокчейне, автоматически выполняющий условия соглашения.

- **Solidity**: Основной язык для разработки смарт-контрактов в Ethereum, похож на JavaScript.

- **Типовые паттерны**: ERC-20, мультисиг, временные замки — стандартные решения для распространённых задач.

- **Уязвимости**: Reentrancy, переполнения, front-running — распространённые проблемы, требующие защиты.

- **"Code is Law"**: Код определяет правила, но необратимость создаёт риски, требующие тщательной разработки и аудита.
