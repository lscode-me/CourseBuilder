## 1. Происхождение UNIX

### 1.1 Создание UNIX

В конце 1960-х годов индустрия столкнулась с парадоксом: чем мощнее становились компьютеры, тем сложнее становились операционные системы. Проект Multics, амбициозная попытка создать универсальную многопользовательскую систему, превратился в колоссальный проект с сотнями разработчиков. Bell Labs вышла из проекта в 1969 году, разочаровавшись в его сложности и стоимости.

**UNIX** был создан в Bell Labs (AT&T) в 1969-1970 годах Кеном Томпсоном и Деннисом Ритчи как реакция на неудачу Multics. Они поставили перед собой радикально другую цель: создать не универсальную систему для всех возможных задач, а простую и элегантную систему для разработки программного обеспечения.

**Контекст:**

- **Проект Multics был слишком сложным и дорогим** — он пытался решить все проблемы сразу, что привело к чрезмерной сложности. Система требовала специального дорогого оборудования и огромных ресурсов для разработки. Это было критически важным уроком: попытка предусмотреть всё заранее приводит к неуправляемой сложности.

- **Нужна была простая система для разработки** — программисты Bell Labs остались без удобной интерактивной среды разработки. Кен Томпсон начал писать UNIX на простом мини-компьютере PDP-7, который нашёл неиспользуемым, чтобы создать игру Space Travel, но быстро понял, что создаёт операционную систему.

- **Первая версия написана на ассемблере для PDP-7** — система была настолько простой, что один человек мог её понять целиком. Это было революционным отличием от Multics с её сотнями человеко-лет разработки.

**Ключевые решения:**

- **Простота вместо сложности** — система должна быть настолько простой, чтобы её мог понять один человек. Это был сознательный выбор, основанный на понимании, что сложность — главный враг надёжности и сопровождаемости.

- **Малый размер системы** — первая версия UNIX занимала около 12 килобайт памяти для ядра. Это было критически важно для работы на скромном оборудовании PDP-7, но стало философией: держать систему маленькой и понятной.

- **Переносимость (переписан на C в 1973)** — это было революционным решением. До UNIX операционные системы писались на ассемблере для конкретного компьютера. Переписав систему на C, Томпсон и Ритчи сделали её переносимой между разными типами компьютеров. Это означало, что UNIX мог работать на любом компьютере, для которого существовал компилятор C.

### 1.2 Распространение UNIX

После создания UNIX произошло нечто неожиданное, что навсегда изменило индустрию программного обеспечения. AT&T, будучи регулируемой телефонной монополией, не могла легально продавать программное обеспечение. Это ограничение превратилось в величайший подарок компьютерной науке.

**Лицензирование:**

- **Изначально распространялся с исходным кодом** — это было революционным подходом. Организации получали не просто программу, а полный исходный код системы. Они могли читать его, понимать, как работает система, и модифицировать под свои нужды. Это означало, что каждый мог учиться у лучших программистов своего времени.

- **Университеты получили лицензии за символическую плату** — стоимость была настолько низкой (около $150-200), что практически любой университет мог себе это позволить. Это было критически важно для образования: целое поколение программистов выросло, изучая исходный код UNIX, понимая, как строятся настоящие системы.

- **Это способствовало быстрому распространению и развитию** — студенты и исследователи не просто использовали UNIX, они улучшали его. Университет Беркли создал BSD UNIX, добавив сетевые возможности и виртуальную память. Эти улучшения распространялись обратно в сообщество, создавая цикл непрерывного развития.

**Влияние:**

- **Стал основой для многих операционных систем** — сегодня большинство современных систем имеют UNIX в своей ДНК. Linux, macOS, iOS, Android, BSD — все они либо основаны на UNIX, либо следуют его принципам. Это было критически важным для стандартизации: программисты могли переносить свои знания между разными системами.

- **Влиял на развитие программного обеспечения** — философия UNIX (делай одно, делай хорошо, используй композицию) распространилась далеко за пределы операционных систем. Она повлияла на дизайн языков программирования, инструментов разработки, даже на архитектуру современных микросервисов.

- **Создал культуру открытого исходного кода** — UNIX показал, что открытый доступ к коду не убивает коммерческую ценность, а наоборот, создаёт более качественное программное обеспечение. Это было фундаментальным сдвигом в мышлении, который привёл к появлению движения свободного ПО и open source.

## 2. Философия UNIX

### 2.1 "Всё — файл"

Одна из самых революционных идей UNIX — унификация интерфейса для работы со всеми ресурсами системы. До UNIX каждый тип ресурса требовал своего специального интерфейса: для работы с диском использовались одни системные вызовы, для принтера — другие, для терминала — третьи. Программисты должны были изучать десятки различных интерфейсов.

**Принцип:**
В UNIX почти всё представлено как файл. Это означает, что для работы с любым ресурсом используются одни и те же операции: `open()`, `read()`, `write()`, `close()`. Это была фундаментальная абстракция, которая изменила способ думать о ресурсах компьютера.

- **Обычные файлы** — данные на диске, самый очевидный случай
- **Директории** — специальные файлы, содержащие списки других файлов
- **Устройства (/dev)** — революционная идея: принтер, диск, терминал — всё это файлы. `/dev/tty` — терминал, `/dev/null` — "чёрная дыра" для ненужных данных
- **Процессы (/proc)** — информация о работающих программах доступна как файловая система
- **Сетевые соединения** — даже сетевое соединение можно читать и писать как файл
- **И многое другое** — pipes, сокеты, символические ссылки

**Преимущества:**

- **Единый интерфейс для работы с разными ресурсами** — это было критически важным упрощением. Программист, знающий как читать файл, автоматически знал, как читать с терминала или из сетевого соединения. Это радикально снизило порог входа в системное программирование.

- **Простота программирования** — программы становились проще и короче. Не нужно было писать отдельный код для каждого типа устройства. Одна и та же программа могла работать с файлом на диске, данными из сети или вводом с терминала без изменений.

- **Композиция: программы могут работать с любыми "файлами"** — это было революционным для построения сложных систем. Программа `grep`, которая ищет текст, не заботится, откуда приходит текст: из файла, по сети, из другой программы через pipe. Это сделало возможным философию UNIX: соединять простые программы в сложные конвейеры.

**Пример:**
```bash
# Чтение из устройства как из файла

cat /dev/random

# Чтение информации о процессе

cat /proc/1/status
```

### 2.2 Минимализм

В эпоху больших монолитных программ, которые пытались делать всё сразу, UNIX предложил радикально другой подход. Вместо создания одной огромной программы с сотнями функций, создавать множество маленьких программ, каждая из которых делает одну вещь, но делает её идеально.

**Принцип:**

- **Каждая программа делает одну вещь хорошо** — это была сознательная философия, основанная на понимании человеческих ограничений. Маленькую программу можно понять целиком, отладить, протестировать. Большую программу со множеством функций понять невозможно. Это было критически важно для надёжности: простая программа имеет меньше ошибок.

- **Программы маленькие и сфокусированные** — типичная утилита UNIX помещается в несколько сотен строк кода. Это было революционным контрастом с монолитными приложениями того времени, которые содержали десятки тысяч строк. Маленькая программа означает, что любой программист может её прочитать, понять и при необходимости изменить.

- **Сложность достигается композицией простых программ** — вместо того чтобы писать сложную программу, которая делает всё, нужно написать несколько простых программ и соединить их вместе. Это фундаментальный принцип, который позже стал основой для микросервисной архитектуры и модульного программирования.

**Примеры:**

- **`cat`** — выводит содержимое файла. Делает только это, но делает безупречно.
- **`grep`** — ищет текст. Не читает файлы, не сортирует, не форматирует — только ищет.
- **`sort`** — сортирует строки. Не заботится, что эти строки означают.
- **`wc`** — считает слова/строки. Простейшая задача, но незаменимая в композиции.

**Композиция:**
```bash
# Композиция простых программ для сложной задачи

cat file.txt | grep "error" | sort | uniq | wc -l
```

### 2.3 Композиция через pipes

**Pipes (|)** — механизм передачи вывода одной программы на вход другой.

**Преимущества:**

- Программы не нужно модифицировать для работы вместе
- Гибкость: можно комбинировать программы разными способами
- Простота: каждая программа остаётся простой

**Пример:**
```bash
# Найти все файлы .txt, отсортировать, показать первые 10

find . -name "*.txt" | sort | head -10
```

## 3. Процессы в UNIX

### 3.1 Концепция процесса

**Процесс** — выполняющаяся программа с изолированными ресурсами.

**Характеристики:**

- Собственное адресное пространство
- Собственные файловые дескрипторы
- Собственный идентификатор (PID)

### 3.2 Создание процессов

**fork()** — системный вызов для создания нового процесса.

**Как работает:**

1. Текущий процесс клонируется
2. Создаётся точная копия (дочерний процесс)
3. Оба процесса продолжают выполнение с того же места
4. Различаются только возвращаемым значением fork()

**Пример: fork() в деталях**

```c
#include <unistd.h>
#include <stdio.h>
#include <sys/wait.h>

int main() {
    printf("Before fork: PID=%d\n", getpid());
    
    pid_t pid = fork();
    
    if (pid == 0) {
        // Дочерний процесс
        printf("Child: PID=%d, Parent PID=%d\n", 
               getpid(), getppid());
    } else if (pid > 0) {
        // Родительский процесс
        printf("Parent: PID=%d, Child PID=%d\n", 
               getpid(), pid);
        wait(NULL);  // Ждать завершения дочернего процесса
    } else {
        // Ошибка
        perror("fork failed");
        return 1;
    }
    
    return 0;
}
```

**exec()** — системный вызов для замены программы в процессе.

**Пример: exec() семейство**

```c
#include <unistd.h>

// exec() семейство функций
execl("/bin/ls", "ls", "-l", NULL);           // Список аргументов
execv("/bin/ls", argv);                        // Массив аргументов
execlp("ls", "ls", "-l", NULL);                // Поиск в PATH
execvp("ls", argv);                            // PATH + массив
execle("/bin/ls", "ls", NULL, envp);           // С переменными окружения
execve("/bin/ls", argv, envp);                 // Полный контроль
```

**Типичный паттерн:**
```c

pid_t pid = fork();
if (pid == 0) {
    // Дочерний процесс
    execl("/bin/ls", "ls", "-l", NULL);
    // Если exec() успешен, этот код не выполнится
    perror("exec failed");
    exit(1);
} else if (pid > 0) {
    // Родительский процесс
    int status;
    waitpid(pid, &status, 0);  // Ждать завершения
    if (WIFEXITED(status)) {
        printf("Child exited with code %d\n", WEXITSTATUS(status));
    }
} else {
    perror("fork failed");
}
```

### 3.3 Коммуникация процессов

**Механизмы:**

**1. Pipes** — однонаправленная коммуникация

**Пример: Anonymous pipe**

```c
#include <unistd.h>

int pipefd[2];
pipe(pipefd);  // pipefd[0] - read, pipefd[1] - write

pid_t pid = fork();
if (pid == 0) {
    // Дочерний процесс - пишет
    close(pipefd[0]);  // Закрыть read end
    write(pipefd[1], "Hello", 5);
    close(pipefd[1]);
} else {
    // Родительский процесс - читает
    close(pipefd[1]);  // Закрыть write end
    char buffer[100];
    read(pipefd[0], buffer, 100);
    printf("Received: %s\n", buffer);
    close(pipefd[0]);
}
```

**2. Named pipes (FIFO)** — именованные каналы

**Пример: FIFO**

```bash
# Создание FIFO
mkfifo mypipe

# Процесс 1 (пишет)
echo "Hello" > mypipe

# Процесс 2 (читает)
cat < mypipe
```

```c

// Программное создание FIFO
#include <sys/stat.h>
mkfifo("/tmp/mypipe", 0666);

// Открытие для записи
int fd = open("/tmp/mypipe", O_WRONLY);
write(fd, "Hello", 5);
close(fd);
```

**3. Signals** — асинхронные уведомления

**Пример: Обработка сигналов**

```c
#include <signal.h>
#include <stdio.h>

void signal_handler(int sig) {
    printf("Received signal %d\n", sig);
    if (sig == SIGINT) {
        printf("Interrupt signal, cleaning up...\n");
        exit(0);
    }
}

int main() {
    // Установка обработчика
    signal(SIGINT, signal_handler);
    
    // Игнорирование сигнала
    signal(SIGTERM, SIG_IGN);
    
    // Бесконечный цикл
    while (1) {
        sleep(1);
    }
    
    return 0;
}
```

**4. Shared memory** — общая память

**Пример: Shared memory**

```c
#include <sys/shm.h>
#include <sys/ipc.h>

// Создание shared memory
key_t key = ftok("/tmp", 'A');
int shmid = shmget(key, 1024, IPC_CREAT | 0666);

// Присоединение к shared memory
void *shm = shmat(shmid, NULL, 0);

// Использование
strcpy((char*)shm, "Hello from shared memory");

// Отсоединение
shmdt(shm);
```

**5. Sockets** — сетевые соединения

**Пример: Unix domain socket**

```c
#include <sys/socket.h>
#include <sys/un.h>

// Создание socket
int sockfd = socket(AF_UNIX, SOCK_STREAM, 0);

struct sockaddr_un addr;
addr.sun_family = AF_UNIX;
strcpy(addr.sun_path, "/tmp/mysocket");

bind(sockfd, (struct sockaddr*)&addr, sizeof(addr));
listen(sockfd, 5);

// Принятие соединения
int client = accept(sockfd, NULL, NULL);
```

## 4. Файловая система

### 4.1 Иерархическая структура

**Особенности:**

- Единое дерево файлов (начинается с `/`)
- Всё монтируется в одно дерево
- Логическая структура не зависит от физических устройств

**Структура:**
```

/
├── bin/      # Исполняемые программы
├── etc/      # Конфигурационные файлы
├── home/     # Домашние директории пользователей
├── tmp/      # Временные файлы
├── usr/      # Пользовательские программы
└── var/      # Переменные данные
```

### 4.2 Права доступа

**Модель прав:**

- Владелец (owner)
- Группа (group)
- Остальные (others)

**Права:**

- Чтение (r) = 4
- Запись (w) = 2
- Выполнение (x) = 1

**Пример:**
```bash

-rwxr-xr-- 1 user group 1024 file.txt
│││││││││
││││││││└── others: r-- (read only)
│││││││└─── others: r--
││││││└──── others: r--
│││││└───── group: r-x (read + execute)
││││└────── group: r-x
│││└─────── group: r-x
││└──────── owner: rwx (read + write + execute)
│└───────── owner: rwx
└────────── owner: rwx
```

**Числовое представление:**
```bash
# rwxr-xr-- = 754
# owner:  rwx = 4+2+1 = 7
# group:  r-x = 4+0+1 = 5
# others: r-- = 4+0+0 = 4

chmod 755 file.txt  # rwxr-xr-x
chmod 644 file.txt  # rw-r--r--
chmod 700 file.txt  # rwx------
```

**Пример: Изменение прав в C**

```c
#include <sys/stat.h>

// Установка прав
chmod("file.txt", S_IRUSR | S_IWUSR | S_IXUSR |  // owner: rwx
                  S_IRGRP | S_IXGRP |            // group: r-x
                  S_IROTH);                      // others: r--

// Или числовое
chmod("file.txt", 0754);  // rwxr-xr--
```

**Sticky bit, setuid, setgid:**
```bash
# Sticky bit (t) - только владелец может удалить файл в /tmp
chmod +t /tmp/file

# Setuid (s) - выполняется с правами владельца
chmod u+s /usr/bin/passwd

# Setgid (s) - выполняется с правами группы
chmod g+s /usr/bin/write
```

### 4.3 Символические и жёсткие ссылки

**Hard links:**
```bash
# Создание hard link
ln original.txt link.txt

# Оба файла указывают на одни данные
# Удаление одного не удаляет данные, пока есть другой
```

**Symbolic links:**
```bash
# Создание symbolic link
ln -s original.txt symlink.txt

# symlink.txt → указывает на original.txt
# Если original.txt удалён, symlink "сломается"
```

**Пример: Работа со ссылками в C**

```c
#include <unistd.h>

// Создание hard link
link("original.txt", "hardlink.txt");

// Создание symbolic link
symlink("original.txt", "symlink.txt");

// Чтение symbolic link
char target[256];
readlink("symlink.txt", target, sizeof(target));
```

## 5. Наследие UNIX

### 5.1 Потомки UNIX

**Прямые потомки:**

- **BSD** — Berkeley Software Distribution

- **Linux** — клон UNIX (не прямой потомок)

- **macOS** — основан на BSD

- **Solaris** — от Sun Microsystems

**Влияние:**

- Большинство современных ОС используют идеи UNIX
- Стандарты POSIX обеспечивают совместимость
- Командная строка стала стандартом

### 5.2 Философия в современных системах

**Применение:**

**Контейнеры (Docker):**
```bash
# Используют изоляцию процессов из UNIX
docker run ubuntu ls -l

# Композиция через pipes
docker ps | grep running | awk '{print $1}'
```

**Микросервисы:**

- Следуют принципу "одна программа — одна задача"
- Коммуникация через простые интерфейсы (как pipes)
- Легко комбинируются

**DevOps инструменты:**
```bash
# Композиция через pipes
kubectl get pods | grep running | awk '{print $1}' | xargs kubectl logs

# Каждая команда делает одну вещь
git log | grep "fix" | wc -l
```

**Функциональные ОС:**

- **NixOS / Guix** — операционные системы с декларативной конфигурацией
- Версионирование всей системы
- Воспроизводимые сборки
- Продолжают идеи UNIX о композиции и предсказуемости

**Пример: NixOS декларативная конфигурация**

```nix
# /etc/nixos/configuration.nix
{ config, pkgs, ... }:
{
  services.nginx.enable = true;
  services.nginx.virtualHosts."example.com" = {
    root = "/var/www";
  };
  
  # Вся система описана декларативно
  # Воспроизводимые сборки
}
```

**Актуальность:**
Философия UNIX остаётся актуальной спустя 50+ лет.

### 5.3 POSIX стандарт

**POSIX (Portable Operating System Interface):**

- Стандарт совместимости между UNIX-подобными системами
- Определяет API для системных вызовов
- Обеспечивает переносимость программ

**Пример: POSIX-совместимый код**

```c

// POSIX-совместимый код работает на Linux, macOS, BSD
#include <unistd.h>
#include <sys/types.h>

pid_t pid = fork();
if (pid == 0) {
    execl("/bin/ls", "ls", NULL);
}
```

## 💡 Key Takeaways

- **UNIX** создал философию простоты и композиции, которая влияет на современные системы

- **"Всё — файл"** — единый интерфейс упрощает программирование и позволяет композицию

- **Минимализм** — каждая программа делает одну вещь хорошо, сложность через композицию

- **Pipes** — мощный механизм композиции программ без их модификации

- **Наследие UNIX** видно во всех современных операционных системах и подходах к разработке
