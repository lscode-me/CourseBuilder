## 1. Реляционные БД

### 1.1 Концепция реляционной модели

В 1970 году Эдгар Кодд из IBM опубликовал статью, которая революционизировала способ хранения и работы с данными. До этого данные хранились в иерархических или сетевых структурах, где программист должен был точно знать физическое расположение данных и явно прописывать путь доступа к ним. Это было критически неудобно — любое изменение структуры данных требовало переписывания всех программ.

Реляционная модель Кодда предложила революционную идею: отделить логическую структуру данных от физической. Данные представляются как простые таблицы, а система сама оптимизирует доступ к ним. Это было фундаментальным прорывом, который сделал базы данных доступными не только специалистам по системам хранения, но и обычным программистам.

**Реляционная база данных:**

- **Данные организованы в таблицы (отношения)** — простая и интуитивно понятная структура. Таблица — это то, что понимает любой человек, работавший с Excel или бумажными формами. Эта простота была критически важна для массового принятия технологии.

- **Связи между таблицами через ключи** — вместо физических указателей используются логические связи через значения полей. Это позволило избежать проблем с повреждением указателей и сделало базы данных более надёжными.

- **Структурированные данные** — каждый столбец имеет определённый тип, что обеспечивает целостность данных и позволяет системе оптимизировать хранение и запросы.

**Основные понятия:**

- **Таблица (Relation)** — набор строк и столбцов

- **Строка (Tuple)** — запись в таблице

- **Столбец (Attribute)** — поле данных

- **Ключ (Key)** — уникальный идентификатор

**Пример:**
```

Таблица Users:
id | name  | email
1  | Alice | alice@example.com
2  | Bob   | bob@example.com
```

### 1.2 SQL

Вместе с реляционной моделью появилась потребность в стандартизированном языке запросов. До SQL каждая СУБД имела свой собственный язык, что делало приложения привязанными к конкретной системе. SQL изменил эту ситуацию, став первым успешным стандартом в области баз данных.

**SQL (Structured Query Language)** — язык для работы с реляционными БД. Его революционность заключалась в декларативном подходе: вместо того чтобы описывать *как* получить данные (какие индексы использовать, в каком порядке читать таблицы), программист описывает *что* он хочет получить, а система сама выбирает оптимальный план выполнения. Это было критически важным прорывом — разработчики могли сосредоточиться на бизнес-логике, а не на деталях оптимизации.

**Пример: Создание таблицы**

```sql

CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT,
    amount DECIMAL(10, 2),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

**Операции:**

**SELECT — выборка данных:**
```sql

-- Простой запрос
SELECT name, email FROM users WHERE id = 1;

-- JOIN для связи таблиц
SELECT u.name, o.amount 
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.amount > 100;

-- Агрегация
SELECT user_id, SUM(amount) as total
FROM orders
GROUP BY user_id
HAVING total > 1000;
```

**INSERT — вставка данных:**
```sql

INSERT INTO users (name, email) 
VALUES ('Alice', 'alice@example.com');

-- Множественная вставка
INSERT INTO users (name, email) VALUES
    ('Bob', 'bob@example.com'),
    ('Charlie', 'charlie@example.com');
```

**UPDATE — обновление данных:**
```sql

UPDATE users 
SET email = 'newemail@example.com'
WHERE id = 1;
```

**DELETE — удаление данных:**
```sql

DELETE FROM users WHERE id = 1;

-- Каскадное удаление (если настроено)
DELETE FROM users WHERE id = 1;  -- Удалит связанные orders
```

**Преимущества:**

- Стандартизированный язык (ANSI SQL)
- Мощные возможности запросов (JOIN, подзапросы, агрегация)
- Оптимизация запросов (query optimizer)
- Декларативный подход (описываем что нужно, не как)

## 2. ACID

### 2.1 Свойства транзакций

Одна из самых критически важных проблем при работе с данными — обеспечение их целостности при сбоях и параллельном доступе. Представьте банковскую транзакцию: деньги списываются с одного счёта и зачисляются на другой. Что произойдёт, если после списания произойдёт сбой питания? Или если два человека одновременно попытаются снять деньги с одного счёта?

Эти проблемы были критически важны для бизнес-приложений, и их решение стало фундаментальным вкладом теории баз данных. В 1980-х годах были формализованы свойства ACID — набор гарантий, которые должна обеспечивать любая серьёзная СУБД. Это было революционным достижением: разработчики получили простые и понятные гарантии, на которые можно полагаться при проектировании приложений.

**ACID** — четыре свойства транзакций:

- **Atomicity (Атомарность)** — транзакция выполняется полностью или не выполняется вообще. Это означает, что нет промежуточных состояний: либо все изменения применены, либо ни одно. В примере с банковским переводом: либо деньги списались *и* зачислились, либо остались на исходном счёте. Половинчатых ситуаций быть не может.

- **Consistency (Согласованность)** — база данных остаётся в согласованном состоянии. Все правила целостности (ограничения, внешние ключи, триггеры) выполняются до и после транзакции. База данных не может перейти в состояние, нарушающее бизнес-правила.

- **Isolation (Изоляция)** — транзакции не мешают друг другу

- **Durability (Долговечность)** — изменения сохраняются после завершения транзакции

### 2.2 Важность ACID

**Гарантии:**

- Надёжность данных
- Предсказуемое поведение
- Защита от ошибок

**Пример: Перевод денег**

```sql

BEGIN TRANSACTION;

-- Снять со счёта A
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- Добавить на счёт B
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- Если обе операции успешны
COMMIT;
-- Если ошибка
ROLLBACK;  -- Откат обеих операций
```

**Без транзакций:**
```sql

-- Плохо: нет атомарности
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Если здесь сбой → деньги потеряны!
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

**Isolation уровни:**
```sql

-- READ UNCOMMITTED: видим незафиксированные изменения
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- READ COMMITTED: видим только зафиксированные (стандарт)
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- REPEATABLE READ: одинаковые чтения в транзакции
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- SERIALIZABLE: полная изоляция (самый строгий)
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

## 3. NoSQL

### 3.1 Ограничения реляционных БД

**Проблемы:**

- Сложность масштабирования
- Жёсткая схема
- Сложность для неструктурированных данных

### 3.2 Типы NoSQL

**Документные БД:**

- Хранение документов (JSON, XML)
- Гибкая схема
- Примеры: MongoDB, CouchDB

**Пример: MongoDB**

```javascript

// Вставка документа
db.users.insertOne({
    name: "Alice",
    email: "alice@example.com",
    orders: [
        { product: "Laptop", price: 999 },
        { product: "Mouse", price: 29 }
    ]
});

// Запрос
db.users.find({ "orders.price": { $gt: 100 } });
```

**Ключ-значение:**

- Простая структура
- Быстрый доступ
- Примеры: Redis, DynamoDB

**Пример: Redis**

```python

import redis
r = redis.Redis()

# Запись
r.set("user:1:name", "Alice")
r.set("user:1:email", "alice@example.com")

# Чтение
name = r.get("user:1:name")
```

**Колоночные:**

- Оптимизация для аналитики
- Примеры: Cassandra, HBase

**Пример: Cassandra CQL**

```sql

CREATE TABLE sales (
    date DATE,
    product TEXT,
    amount DECIMAL,
    PRIMARY KEY (date, product)
);

-- Эффективно для аналитики (агрегация по колонкам)
SELECT date, SUM(amount) FROM sales GROUP BY date;
```

**Графовые:**

- Хранение связей
- Примеры: Neo4j

**Пример: Neo4j Cypher**

```cypher

// Создание узлов и связей
CREATE (alice:Person {name: "Alice"})
CREATE (bob:Person {name: "Bob"})
CREATE (alice)-[:FRIENDS_WITH]->(bob)

// Запрос связей
MATCH (a:Person)-[:FRIENDS_WITH]->(b:Person)
RETURN a.name, b.name
```

## 4. OLTP vs OLAP

### 4.1 OLTP

**OLTP (Online Transaction Processing):**

- Обработка транзакций в реальном времени
- Много коротких транзакций
- Оптимизация для записи
- Примеры: банковские системы, интернет-магазины

**Характеристики:**

- Высокая доступность
- Быстрый отклик
- ACID гарантии

### 4.2 OLAP

**OLAP (Online Analytical Processing):**

- Аналитическая обработка данных
- Сложные запросы
- Оптимизация для чтения
- Примеры: системы бизнес-аналитики, хранилища данных

**Характеристики:**

- Агрегация данных
- Исторические данные
- Оптимизация для анализа

## 5. Почему БД — отдельный мир

### 5.1 Специализация

**Базы данных:**

- Специализированные системы
- Собственные алгоритмы и структуры данных
- Оптимизация для конкретных задач

**Отличия от файловых систем:**

- Транзакции
- Индексы
- Оптимизация запросов
- Управление конкурентным доступом

### 5.2 Важность

**Критичность:**

- Данные — основа приложений
- Потеря данных критична
- Производительность важна

**Результат:**
Базы данных развиваются как отдельная область со своими специалистами и технологиями.

### 5.3 Индексы

**Индексы ускоряют поиск:**

**Пример: B-tree индекс**

```sql

-- Создание индекса
CREATE INDEX idx_email ON users(email);

-- Запрос использует индекс
SELECT * FROM users WHERE email = 'alice@example.com';
-- Без индекса: полное сканирование таблицы (O(n))
-- С индексом: поиск в B-tree (O(log n))
```

**Типы индексов:**

- B-tree: для большинства запросов
- Hash: для точного совпадения
- Full-text: для текстового поиска

### 5.4 Оптимизация запросов

**Query Optimizer:**
```sql

-- Плохой запрос (N+1 проблема)
SELECT * FROM users;
-- Для каждого user:
SELECT * FROM orders WHERE user_id = ?;

-- Хороший запрос (JOIN)
SELECT u.*, o.* 
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
```

**EXPLAIN для анализа:**
```sql

EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
-- Показывает план выполнения, использование индексов
```

## 💡 Key Takeaways

- **Реляционные БД** обеспечивают структурированное хранение данных через таблицы и связи

- **ACID свойства** гарантируют надёжность и предсказуемость транзакций

- **NoSQL** решает проблемы масштабирования и гибкости схемы для различных типов данных

- **OLTP и OLAP** — разные оптимизации для транзакций и аналитики

- **Базы данных — отдельный мир** со специализированными системами, алгоритмами и экспертизой
