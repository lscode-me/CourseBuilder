## 1. От одноядерных к многоядерным процессорам

### 1.1 Конец эпохи частоты

**1990-е - начало 2000-х:** Производительность росла за счёт увеличения частоты (MHz → GHz).

**Проблема:** "Power Wall"
- Потребление энергии ∝ Частота³
- Intel Pentium 4 (3.8 GHz, 2004) потреблял 115W — критический предел для воздушного охлаждения

**2005: Переломный момент**
- Intel и AMD перешли на многоядерные процессоры
- Вместо одного быстрого ядра — несколько медленнее работающих

**Free Lunch is Over** (Herb Sutter, 2005) — статья о том, что производительность больше не растёт автоматически, программистам нужно использовать параллелизм.

### 1.2 Многоядерные архитектуры

**Современный процессор:**
```

┌─────────────────────────────┐
│        CPU Package          │
│  ┌─────┐  ┌─────┐  ┌─────┐ │
│  │Core0│  │Core1│  │Core2│ │
│  │ L1  │  │ L1  │  │ L1  │ │
│  │ L2  │  │ L2  │  │ L2  │ │
│  └──┬──┘  └──┬──┘  └──┬──┘ │
│     └────────┴────────┘     │
│          L3 Cache           │
│      (Shared между ядрами)  │
└─────────────────────────────┘
```

**Характеристики:**

- Каждое ядро — полноценный процессор
- Private L1/L2 кэши для каждого ядра
- Shared L3 кэш для всех ядер
- Независимое выполнение инструкций

## 2. Concurrency vs Parallelism

### 2.1 Определения

**Concurrency (Конкурентность):**

- Несколько задач *progress* одновременно
- Может выполняться на одном ядре (time-slicing)
- О структуре программы

**Parallelism (Параллелизм):**

- Несколько задач выполняются *одновременно*
- Требует несколько ядер/процессоров
- О выполнении

**Пример:**

- **Конкурентность:** Один повар готовит три блюда, переключаясь между ними

- **Параллелизм:** Три повара готовят три блюда одновременно

### 2.2 Типы параллелизма

**Data Parallelism:**

- Одна операция на много данных
- Пример: применить фильтр к каждому пикселю изображения

**Task Parallelism:**

- Разные операции параллельно
- Пример: один поток рендерит UI, другой загружает данные

**Pipeline Parallelism:**

- Последовательность стадий обработки
- Каждая стадия обрабатывает свой элемент

## 3. Синхронизация и проблемы параллелизма

### 3.1 Race Condition

**Проблема:** Два потока модифицируют общие данные.

```c

int counter = 0;

// Thread 1            // Thread 2
counter++;             counter++;
```

**Ожидаем:** counter = 2  
**Реально может быть:** counter = 1

**Почему?**

```

counter++ это не атомарная операция:

1. READ counter (0)
2. ADD 1
3. WRITE counter (1)

Thread 1: READ(0) → ADD → WRITE(1)
Thread 2:         READ(0) → ADD → WRITE(1)
Результат: 1 вместо 2!
```

### 3.2 Критическая секция и Mutex

**Mutex (Mutual Exclusion)** — механизм блокировки

```c

pthread_mutex_t lock;

void increment() {
    pthread_mutex_lock(&lock);
    counter++;  // только один поток здесь
    pthread_mutex_unlock(&lock);
}
```

**Trade-off:** Mutex решает race condition, но вносит overhead и может вызвать:

- **Deadlock:** Два потока ждут друг друга

- **Livelock:** Потоки активны, но не прогрессируют

- **Starvation:** Поток никогда не получает ресурс

### 3.3 Атомарные операции

**Atomic operations** — операции, которые выполняются неделимо

```c

atomic_int counter = 0;

atomic_fetch_add(&counter, 1);  // атомарно, без mutex
```

**Реализация:** CPU инструкции (x86: `lock add`, ARM: LDREX/STREX)

Быстрее mutex для простых операций, но не заменяют его для сложной логики.

## 4. Модели памяти

### 4.1 Sequential Consistency

**Идеальная модель:** Все операции выполняются в порядке, как написано в коде.

**Реальность:** Компиляторы и процессоры переупорядочивают операции для оптимизации.

### 4.2 Memory Reordering

**Пример проблемы:**

```c

// Thread 1          // Thread 2
x = 1;               while (flag == 0);
flag = 1;            assert(x == 1);  // может упасть!
```

**Компилятор или CPU может переставить операции в Thread 1:**
```c

flag = 1;
x = 1;  // слишком поздно!
```

### 4.3 Memory Barriers

**Решение:** Memory barriers (fences) запрещают переупорядочивание

```c

x = 1;
__sync_synchronize();  // memory barrier
flag = 1;
```

**Типы барьеров:**

- **Compiler barrier:** запрещает переупорядочивание компилятором

- **CPU barrier:** запрещает переупорядочивание процессором

- **Acquire/Release semantics:** более гранулярный контроль

## 5. Symmetric Multi-Processing (SMP)

### 5.1 Архитектура SMP

**Определение:** Все ядра имеют равный доступ к общей памяти.

```

Core 0 ─┐
Core 1 ─┼─ Shared Bus ─ Memory
Core 2 ─┘
```

**Преимущества:**

- Простая программная модель
- Любой поток может работать на любом ядре

**Недостатки:**

- Bus contention при большом количестве ядер
- Ограниченная масштабируемость

### 5.2 NUMA (Non-Uniform Memory Access)

**Проблема SMP:** Не масштабируется за 16-32 ядра

**NUMA решение:**
```

┌──────────┐      ┌──────────┐
│ CPU 0    │◄────►│ CPU 1    │
│ Memory 0 │      │ Memory 1 │
└──────────┘      └──────────┘
```

**Характеристики NUMA:**

- Каждый CPU имеет "локальную" память
- Доступ к локальной памяти быстрее
- Доступ к удалённой памяти медленнее (remote latency)

**Важность для программирования:**

- Thread affinity — привязать потоки к определённым ядрам
- Memory affinity — размещать данные в нужной NUMA node

## 6. Многопоточное программирование

### 6.1 Threads vs Processes

**Process:**

- Отдельное адресное пространство
- Изолирован от других процессов
- Тяжёлый context switch

**Thread:**

- Разделяет адресное пространство процесса
- Легковесный
- Быстрый context switch
- Но: проблемы синхронизации

### 6.2 Паттерны параллелизма

**Thread Pool:**
```

┌─────────┐
│ Queue   │ → Worker Thread 1
│ of Tasks│ → Worker Thread 2
└─────────┘ → Worker Thread 3
```

**Thread Pool:** Переиспользование потоков вместо создания новых для каждой задачи.

**Fork-Join:**
```

Main ──fork──┬─ Task 1
             ├─ Task 2
             └─ Task 3
         join──┘
```

**Fork-Join:** Разделить работу, затем собрать результаты.

**Producer-Consumer:**
```

Producer → [Buffer] → Consumer
```

**Producer-Consumer:** Производитель создаёт данные, потребитель обрабатывает.

## 7. False Sharing

### 7.1 Проблема

**False Sharing** — скрытая проблема производительности в многопоточном коде.

**Что происходит:**

```c

// Thread 1 на Core 0        // Thread 2 на Core 1
int counter1 = 0;             int counter2 = 0;

counter1++;                   counter2++;
```

**Проблема:** Если `counter1` и `counter2` находятся в одной cache line (64 байта), каждое изменение инвалидирует cache line на другом ядре, хотя потоки логически не разделяют данные.

### 7.2 Механизм

```

Cache Line (64 bytes):
┌─────────────────────────────────────┐
│ counter1 │ counter2 │ ... padding   │
└─────────────────────────────────────┘
     ↑              ↑
  Core 0        Core 1
```

**Механизм:**

1. Core 0 модифицирует `counter1` → инвалидирует cache line
2. Core 1 должен перезагрузить cache line из памяти
3. Core 1 модифицирует `counter2` → инвалидирует cache line
4. Core 0 должен перезагрузить cache line из памяти
5. Цикл повторяется → множество cache misses

### 7.3 Решение

**Cache Line Padding:**

```c

struct {
    int counter1;
    char padding[64 - sizeof(int)];  // выравнивание до cache line
} data1;

struct {
    int counter2;
    char padding[64 - sizeof(int)];
} data2;
```

**Или использовать `alignas(64)` в C++:**

```cpp

alignas(64) int counter1;
alignas(64) int counter2;
```

**Важно:** False sharing может серьёзно снизить производительность, даже если потоки работают с разными данными.

## 8. Закон Амдала

### 8.1 Формула

**Speedup = 1 / ((1 - P) + P/N)**

Где:

- P — доля программы, которую можно распараллелить
- N — количество процессоров

**Максимальное ускорение (при N → ∞):**

**Speedup_max = 1 / (1 - P)**

### 8.2 Практический смысл

Если 90% программы можно распараллелить (P=0.9):

- 2 ядра: speedup = 1.82x
- 4 ядра: speedup = 3.08x
- 8 ядер: speedup = 4.71x
- ∞ ядер: speedup = 10x (теоретический максимум)

**Вывод:** Последовательная часть (1-P) ограничивает максимальное ускорение!

### 8.3 Ограничения

- Overhead синхронизации
- Cache coherency traffic
- False sharing (см. раздел 7)
- Load imbalance

Реальное ускорение обычно ниже теоретического.

## 💡 Key Takeaways

- **Многоядерные процессоры** стали необходимостью из-за Power Wall — невозможности увеличивать частоту

- **Concurrency vs Parallelism:** Concurrency — о структуре, parallelism — о выполнении

- **Race conditions** требуют синхронизации через mutex, atomic operations или другие механизмы

- **Memory models** и memory barriers критичны для корректного многопоточного кода

- **False sharing** может серьёзно снизить производительность, даже когда потоки работают с разными данными

- **Закон Амдала** показывает фундаментальные ограничения параллелизма — последовательная часть ограничивает ускорение
