## 1. От одноядерных к многоядерным процессорам

### 1.1 Конец эпохи частоты

История развития процессоров показывает, как инженеры столкнулись с физическими ограничениями и были вынуждены изменить подход к повышению производительности. Переход от увеличения частоты к многоядерности был революционным изменением, которое определило развитие вычислительной техники на десятилетия вперёд.

**1990-е - начало 2000-х: Производительность росла за счёт увеличения частоты (MHz → GHz).**

В 1990-е и начале 2000-х годов производительность процессоров росла в основном за счёт увеличения тактовой частоты. Процессоры развивались от мегагерц к гигагерцам, и каждое новое поколение было быстрее предыдущего. Это был "золотой век" для программистов: они могли писать программы, не задумываясь о параллелизме, и каждая новая модель процессора автоматически делала программы быстрее. Это было время, когда "бесплатный обед" был реальностью: производительность росла без усилий со стороны программистов.

**Проблема: "Power Wall"**

Однако увеличение частоты столкнулось с фундаментальной физической проблемой — "Power Wall":

- **Потребление энергии ∝ Частота³** — потребление энергии процессора пропорционально кубу частоты. Это означает, что удвоение частоты увеличивает потребление энергии в 8 раз. Это создавало серьёзные проблемы с энергопотреблением и тепловыделением. Процессоры становились слишком "горячими" и потребляли слишком много энергии

- **Intel Pentium 4 (3.8 GHz, 2004) потреблял 115W — критический предел для воздушного охлаждения** — процессор Intel Pentium 4 на частоте 3.8 GHz потреблял 115 ватт, что было критическим пределом для воздушного охлаждения. Дальнейшее увеличение частоты требовало более сложных и дорогих систем охлаждения, что делало процессоры непрактичными. Это был физический барьер, который нельзя было преодолеть простым увеличением частоты

**2005: Переломный момент**

В 2005 году произошёл переломный момент в развитии процессоров:

- **Intel и AMD перешли на многоядерные процессоры** — вместо попыток увеличить частоту одного ядра, Intel и AMD начали размещать несколько ядер на одном чипе. Это было революционным изменением подхода к повышению производительности. Вместо одного быстрого ядра появилось несколько ядер, работающих параллельно

- **Вместо одного быстрого ядра — несколько медленнее работающих** — новый подход означал, что вместо одного ядра на частоте 4 GHz появилось несколько ядер на частоте 2-3 GHz. Это позволяло увеличить общую производительность без критического увеличения энергопотребления. Однако это требовало от программистов переосмысления подхода к программированию

**Free Lunch is Over** (Herb Sutter, 2005) — статья о том, что производительность больше не растёт автоматически, программистам нужно использовать параллелизм.

Статья "Free Lunch is Over" Герба Саттера стала знаковым моментом в истории программирования. Она провозгласила конец эпохи, когда производительность росла автоматически с каждым новым процессором. Отныне программисты должны были явно использовать параллелизм для повышения производительности. Это было вызовом для всей индустрии программного обеспечения, которая привыкла к автоматическому росту производительности. Статья стала призывом к действию для программистов и определила направление развития программного обеспечения на следующие десятилетия.

### 1.2 Многоядерные архитектуры

**Современный процессор:**
```

┌─────────────────────────────┐
│        CPU Package          │
│  ┌─────┐  ┌─────┐  ┌─────┐  │
│  │Core0│  │Core1│  │Core2│  │
│  │ L1  │  │ L1  │  │ L1  │  │
│  │ L2  │  │ L2  │  │ L2  │  │
│  └──┬──┘  └──┬──┘  └──┬──┘  │
│     └────────┴────────┘     │
│          L3 Cache           │
│      (Shared между ядрами)  │
└─────────────────────────────┘
```

**Характеристики:**

- Каждое ядро — полноценный процессор
- Private L1/L2 кэши для каждого ядра
- Shared L3 кэш для всех ядер
- Независимое выполнение инструкций

## 2. Concurrency vs Parallelism

### 2.1 Определения

Понимание различия между конкурентностью и параллелизмом критически важно для правильного проектирования параллельных систем. Эти концепции часто путают, но они описывают разные аспекты параллельного программирования.

**Concurrency (Конкурентность):**

Конкурентность описывает структуру программы и способ организации задач:

- **Несколько задач *progress* одновременно** — конкурентность означает, что несколько задач продвигаются в выполнении одновременно, даже если они не выполняются физически в одно и то же время. Это концепция о структуре программы и способе организации работы. Конкурентные программы могут выполняться на одном ядре через переключение между задачами

- **Может выполняться на одном ядре (time-slicing)** — конкурентные программы могут выполняться на одном ядре процессора через механизм разделения времени (time-slicing). Операционная система быстро переключается между задачами, создавая иллюзию одновременного выполнения. Это позволяет программировать конкурентные системы даже на одноядерных процессорах

- **О структуре программы** — конкурентность — это свойство структуры программы, а не способа выполнения. Конкурентная программа может быть написана так, чтобы использовать несколько задач, независимо от того, сколько ядер доступно. Это делает программы более гибкими и масштабируемыми

**Parallelism (Параллелизм):**

Параллелизм описывает способ выполнения программы и использование аппаратных ресурсов:

- **Несколько задач выполняются *одновременно*** — параллелизм означает, что несколько задач выполняются физически одновременно на разных ядрах процессора. Это концепция о выполнении программы и использовании аппаратных ресурсов. Параллельные программы требуют нескольких ядер для одновременного выполнения

- **Требует несколько ядер/процессоров** — параллелизм требует наличия нескольких ядер процессора или нескольких процессоров. Без нескольких ядер невозможно физическое одновременное выполнение задач. Это ограничивает параллелизм аппаратными возможностями системы

- **О выполнении** — параллелизм — это свойство выполнения программы, а не её структуры. Параллельная программа использует несколько ядер для одновременного выполнения задач. Это позволяет достичь реального ускорения выполнения программы

**Пример:**

Пример с поварами помогает понять разницу между конкурентностью и параллелизмом:

- **Конкурентность: Один повар готовит три блюда, переключаясь между ними** — один повар может готовить три блюда конкурентно, переключаясь между ними. Он может начать готовить первое блюдо, затем переключиться на второе, затем на третье, и так далее. Это конкурентность: несколько задач продвигаются одновременно, но выполняются одним ресурсом (поваром). Это похоже на выполнение нескольких потоков на одном ядре процессора

- **Параллелизм: Три повара готовят три блюда одновременно** — три повара могут готовить три блюда параллельно, каждый работая над своим блюдом одновременно. Это параллелизм: несколько задач выполняются физически одновременно разными ресурсами (поварами). Это похоже на выполнение нескольких потоков на разных ядрах процессора

Важно понимать, что конкурентность и параллелизм не исключают друг друга: конкурентная программа может выполняться параллельно на многоядерном процессоре, что позволяет достичь максимальной производительности.

### 2.2 Типы параллелизма

**Data Parallelism:**

- Одна операция на много данных
- Пример: применить фильтр к каждому пикселю изображения

**Task Parallelism:**

- Разные операции параллельно
- Пример: один поток рендерит UI, другой загружает данные

**Pipeline Parallelism:**

- Последовательность стадий обработки
- Каждая стадия обрабатывает свой элемент

## 3. Синхронизация и проблемы параллелизма

### 3.1 Race Condition

Race condition (состояние гонки) является одной из самых распространённых и опасных проблем в параллельном программировании. Понимание механизма race condition критически важно для написания корректных многопоточных программ.

**Проблема:** Два потока модифицируют общие данные.

Race condition возникает, когда два или более потока обращаются к общим данным, и результат выполнения зависит от порядка выполнения операций. Это создаёт недетерминированное поведение программы, где результат может быть разным при каждом запуске. Race condition особенно опасны, потому что они могут проявляться редко и быть трудно воспроизводимыми, что делает их сложными для отладки.

```c

int counter = 0;

// Thread 1            // Thread 2
counter++;             counter++;
```

В этом примере два потока пытаются увеличить счётчик на 1. Интуитивно кажется, что результат должен быть 2, но из-за race condition результат может быть 1 или даже другим значением.

**Ожидаем:** counter = 2  
**Реально может быть:** counter = 1

Ожидаемый результат — 2 (каждый поток увеличивает счётчик на 1). Однако из-за race condition реальный результат может быть 1 или другим непредсказуемым значением. Это происходит потому, что операция увеличения счётчика не является атомарной и состоит из нескольких шагов.

**Почему?**

Проблема возникает из-за того, что операция `counter++` не является атомарной:

```

counter++ это не атомарная операция:

1. READ counter (0)
2. ADD 1
3. WRITE counter (1)

Thread 1: READ(0) → ADD → WRITE(1)
Thread 2:         READ(0) → ADD → WRITE(1)
Результат: 1 вместо 2!
```

Операция `counter++` состоит из трёх шагов: чтение значения из памяти, увеличение на 1, запись обратно в память. Если два потока выполняют эту операцию одновременно, они могут прочитать одно и то же значение, увеличить его и записать обратно, что приводит к потере одного из увеличений. В примере оба потока читают значение 0, увеличивают его до 1 и записывают 1 обратно, в результате чего счётчик становится 1 вместо ожидаемого 2. Это классический пример race condition, который показывает важность синхронизации в многопоточных программах.

### 3.2 Критическая секция и Mutex

Критическая секция — это часть кода, которая должна выполняться только одним потоком в данный момент времени. Mutex (Mutual Exclusion) — это механизм синхронизации, который обеспечивает взаимное исключение, гарантируя, что только один поток может выполнять критическую секцию одновременно.

**Mutex (Mutual Exclusion)** — механизм блокировки

Mutex — это примитив синхронизации, который обеспечивает взаимное исключение доступа к критической секции. Когда поток захватывает mutex, другие потоки должны ждать, пока mutex не будет освобождён. Это гарантирует, что только один поток может выполнять критическую секцию одновременно, что предотвращает race condition.

```c

pthread_mutex_t lock;

void increment() {
    pthread_mutex_lock(&lock);
    counter++;  // только один поток здесь
    pthread_mutex_unlock(&lock);
}
```

В этом примере mutex используется для защиты операции увеличения счётчика. Когда поток вызывает `pthread_mutex_lock()`, он пытается захватить mutex. Если mutex уже захвачен другим потоком, текущий поток блокируется и ждёт освобождения mutex. Когда поток завершает критическую секцию, он вызывает `pthread_mutex_unlock()` для освобождения mutex, что позволяет другим потокам продолжить выполнение. Это гарантирует, что операция `counter++` выполняется атомарно с точки зрения других потоков.

**Trade-off:** Mutex решает race condition, но вносит overhead и может вызвать:

Использование mutex решает проблему race condition, но создаёт новые проблемы и накладные расходы:

- **Deadlock: Два потока ждут друг друга** — deadlock возникает, когда два или более потока блокируют друг друга, ожидая освобождения ресурсов, которые удерживаются другими потоками. Например, поток A захватывает mutex 1 и ждёт mutex 2, а поток B захватывает mutex 2 и ждёт mutex 1. Оба потока блокируются навсегда, и программа зависает. Deadlock — это серьёзная проблема, которая требует тщательного проектирования порядка захвата mutex

- **Livelock: Потоки активны, но не прогрессируют** — livelock возникает, когда потоки активны и пытаются выполнить работу, но не могут прогрессировать из-за постоянного конфликта. Например, два потока постоянно пытаются захватить mutex, но каждый раз уступают друг другу, в результате чего ни один поток не может завершить работу. Livelock похож на deadlock, но потоки активны, а не заблокированы

- **Starvation: Поток никогда не получает ресурс** — starvation возникает, когда поток никогда не получает доступ к ресурсу из-за того, что другие потоки постоянно его захватывают. Например, если несколько потоков постоянно захватывают mutex, один поток может никогда не получить возможность выполнить критическую секцию. Starvation может привести к тому, что программа работает, но некоторые потоки не прогрессируют

Эти проблемы показывают, что mutex — это мощный инструмент, но его использование требует осторожности и тщательного проектирования. Правильное использование mutex требует понимания порядка захвата ресурсов, таймаутов и других механизмов предотвращения проблем синхронизации.

### 3.3 Атомарные операции

**Atomic operations** — операции, которые выполняются неделимо

```c

atomic_int counter = 0;

atomic_fetch_add(&counter, 1);  // атомарно, без mutex
```

**Реализация:** CPU инструкции (x86: `lock add`, ARM: LDREX/STREX)

Быстрее mutex для простых операций, но не заменяют его для сложной логики.

## 4. Модели памяти

### 4.1 Sequential Consistency

**Идеальная модель:** Все операции выполняются в порядке, как написано в коде.

**Реальность:** Компиляторы и процессоры переупорядочивают операции для оптимизации.

### 4.2 Memory Reordering

**Пример проблемы:**

```c

// Thread 1          // Thread 2
x = 1;               while (flag == 0);
flag = 1;            assert(x == 1);  // может упасть!
```

**Компилятор или CPU может переставить операции в Thread 1:**
```c

flag = 1;
x = 1;  // слишком поздно!
```

### 4.3 Memory Barriers

**Решение:** Memory barriers (fences) запрещают переупорядочивание

```c

x = 1;
__sync_synchronize();  // memory barrier
flag = 1;
```

**Типы барьеров:**

- **Compiler barrier:** запрещает переупорядочивание компилятором

- **CPU barrier:** запрещает переупорядочивание процессором

- **Acquire/Release semantics:** более гранулярный контроль

## 5. Symmetric Multi-Processing (SMP)

### 5.1 Архитектура SMP

**Определение:** Все ядра имеют равный доступ к общей памяти.

```

Core 0 ─┐
Core 1 ─┼─ Shared Bus ─ Memory
Core 2 ─┘
```

**Преимущества:**

- Простая программная модель
- Любой поток может работать на любом ядре

**Недостатки:**

- Bus contention при большом количестве ядер
- Ограниченная масштабируемость

### 5.2 NUMA (Non-Uniform Memory Access)

**Проблема SMP:** Не масштабируется за 16-32 ядра

**NUMA решение:**
```

┌──────────┐      ┌──────────┐
│ CPU 0    │◄────►│ CPU 1    │
│ Memory 0 │      │ Memory 1 │
└──────────┘      └──────────┘
```

**Характеристики NUMA:**

- Каждый CPU имеет "локальную" память
- Доступ к локальной памяти быстрее
- Доступ к удалённой памяти медленнее (remote latency)

**Важность для программирования:**

- Thread affinity — привязать потоки к определённым ядрам
- Memory affinity — размещать данные в нужной NUMA node

## 6. Многопоточное программирование

### 6.1 Threads vs Processes

**Process:**

- Отдельное адресное пространство
- Изолирован от других процессов
- Тяжёлый context switch

**Thread:**

- Разделяет адресное пространство процесса
- Легковесный
- Быстрый context switch
- Но: проблемы синхронизации

### 6.2 Паттерны параллелизма

**Thread Pool:**
```

┌─────────┐
│ Queue   │ → Worker Thread 1
│ of Tasks│ → Worker Thread 2
└─────────┘ → Worker Thread 3
```

**Thread Pool:** Переиспользование потоков вместо создания новых для каждой задачи.

**Fork-Join:**
```

Main ──fork──┬─ Task 1
             ├─ Task 2
             └─ Task 3
         join──┘
```

**Fork-Join:** Разделить работу, затем собрать результаты.

**Producer-Consumer:**
```

Producer → [Buffer] → Consumer
```

**Producer-Consumer:** Производитель создаёт данные, потребитель обрабатывает.

## 7. False Sharing

### 7.1 Проблема

**False Sharing** — скрытая проблема производительности в многопоточном коде.

**Что происходит:**

```c

// Thread 1 на Core 0        // Thread 2 на Core 1
int counter1 = 0;             int counter2 = 0;

counter1++;                   counter2++;
```

**Проблема:** Если `counter1` и `counter2` находятся в одной cache line (64 байта), каждое изменение инвалидирует cache line на другом ядре, хотя потоки логически не разделяют данные.

### 7.2 Механизм

```

Cache Line (64 bytes):
┌─────────────────────────────────────┐
│ counter1 │ counter2 │ ... padding   │
└─────────────────────────────────────┘
     ↑              ↑
  Core 0        Core 1
```

**Механизм:**

1. Core 0 модифицирует `counter1` → инвалидирует cache line
2. Core 1 должен перезагрузить cache line из памяти
3. Core 1 модифицирует `counter2` → инвалидирует cache line
4. Core 0 должен перезагрузить cache line из памяти
5. Цикл повторяется → множество cache misses

### 7.3 Решение

**Cache Line Padding:**

```c

struct {
    int counter1;
    char padding[64 - sizeof(int)];  // выравнивание до cache line
} data1;

struct {
    int counter2;
    char padding[64 - sizeof(int)];
} data2;
```

**Или использовать `alignas(64)` в C++:**

```cpp

alignas(64) int counter1;
alignas(64) int counter2;
```

**Важно:** False sharing может серьёзно снизить производительность, даже если потоки работают с разными данными.

## 8. Закон Амдала

### 8.1 Формула

**Speedup = 1 / ((1 - P) + P/N)**

Где:

- P — доля программы, которую можно распараллелить
- N — количество процессоров

**Максимальное ускорение (при N → ∞):**

**Speedup_max = 1 / (1 - P)**

### 8.2 Практический смысл

Если 90% программы можно распараллелить (P=0.9):

- 2 ядра: speedup = 1.82x
- 4 ядра: speedup = 3.08x
- 8 ядер: speedup = 4.71x
- ∞ ядер: speedup = 10x (теоретический максимум)

**Вывод:** Последовательная часть (1-P) ограничивает максимальное ускорение!

### 8.3 Ограничения

- Overhead синхронизации
- Cache coherency traffic
- False sharing (см. раздел 7)
- Load imbalance

Реальное ускорение обычно ниже теоретического.
