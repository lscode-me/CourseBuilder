## Question 1: Power Wall

Почему индустрия перешла от увеличения частоты к многоядерным процессорам в середине 2000-х?

A) Многоядерные процессоры дешевле производить

B) Потребление энергии растёт пропорционально частоте в кубе — дальнейшее увеличение частоты стало невозможным

C) Программное обеспечение не могло использовать высокие частоты

D) Это было маркетинговое решение

**Ответ: B**

**Пояснение:** Потребление энергии ∝ Частота³. Intel Pentium 4 на 3.8 GHz потреблял 115W — предел воздушного охлаждения. Дальнейшее увеличение частоты приводило к перегреву. В 2005 индустрия перешла на многоядерные процессоры — вместо одного быстрого ядра несколько более медленных, но общая производительность выше при меньшем энергопотреблении.

## Question 2: Concurrency vs Parallelism

В чём разница между concurrency и parallelism?

A) Это синонимы — одно и то же

B) Concurrency — несколько задач прогрессируют (может быть на одном ядре), parallelism — выполняются одновременно (требует несколько ядер)

C) Concurrency для языков программирования, parallelism для hardware

D) Concurrency быстрее parallelism

**Ответ: B**

**Пояснение:**
- **Concurrency:** О структуре — несколько задач могут прогрессировать, переключаясь (time-slicing) даже на одном ядре
- **Parallelism:** О выполнении — задачи реально выполняются одновременно на разных ядрах

Аналогия: один повар готовит три блюда (concurrency) vs три повара готовят три блюда (parallelism).

## Question 3: Race Condition

Почему `counter++` может вызвать race condition?

A) Это атомарная операция

B) `counter++` раскладывается на READ-ADD-WRITE, и потоки могут прерваться между этими шагами

C) Переменная counter повреждена

D) Это ошибка компилятора

**Ответ: B**

**Пояснение:** `counter++` выполняется в три шага:
1. READ counter
2. ADD 1
3. WRITE result

Если два потока выполняют это одновременно, они могут оба прочитать одно значение, увеличить его и записать — результат будет +1 вместо +2. Это классическая race condition.

## Question 4: Mutex

Для чего используется mutex?

A) Для увеличения скорости параллельного кода

B) Для обеспечения mutual exclusion — только один поток может войти в критическую секцию

C) Для создания новых потоков

D) Для cache coherency

**Ответ: B**

**Пояснение:** Mutex (Mutual Exclusion) — механизм блокировки, гарантирующий, что только один поток может находиться в критической секции кода. Это решает race conditions, но вносит overhead и может вызвать deadlock, если не используется аккуратно.

## Question 5: Закон Амдала

Если 80% программы можно распараллелить и у вас бесконечно много ядер, каково максимальное теоретическое ускорение?

A) 4x

B) 5x

C) 8x

D) Бесконечное

**Ответ: B**

**Пояснение:** Закон Амдала: Speedup_max = 1 / (1 - P), где P — доля параллелизуемого кода.
При P = 0.8: Speedup = 1 / 0.2 = 5x

Последовательная часть (20%) ограничивает максимальное ускорение. Даже с бесконечным числом ядер эти 20% всё равно будут выполняться последовательно.

## Question 6: Atomic Operations

Чем атомарные операции отличаются от использования mutex?

A) Атомарные операции медленнее

B) Атомарные операции гарантируют неделимое выполнение на уровне CPU инструкций, обычно быстрее mutex для простых операций

C) Атомарные операции работают только на GPU

D) Разницы нет

**Ответ: B**

**Пояснение:** Atomic operations используют специальные CPU инструкции (x86: `lock add`, ARM: LDREX/STREX), которые гарантируют неделимое выполнение. Они быстрее mutex для простых операций (инкремент, compare-and-swap), но не заменяют mutex для сложной логики с несколькими операциями.

## Question 7: Memory Reordering

Почему компилятор или CPU могут переупорядочивать операции?

A) Это ошибка

B) Для оптимизации производительности — переупорядочивание не влияет на однопоточный код

C) Для экономии памяти

D) Это происходит только в debug builds

**Ответ: B**

**Пояснение:** Компилятор и CPU переупорядочивают операции для оптимизации (лучшее использование pipeline, cache). В однопоточном коде это не видно. Но в многопоточном коде это может вызвать проблемы, где один поток полагается на порядок операций в другом. Memory barriers запрещают переупорядочивание в критичных местах.

## Question 8: SMP vs NUMA

В чём основное различие между SMP и NUMA?

A) SMP быстрее NUMA

B) В SMP все ядра имеют одинаковый доступ к памяти, в NUMA доступ к локальной памяти быстрее

C) SMP для Intel, NUMA для AMD

D) Это одно и то же

**Ответ: B**

**Пояснение:**
- **SMP** (Symmetric Multi-Processing): все ядра имеют равный доступ к общей памяти через shared bus. Не масштабируется за 16-32 ядра.
- **NUMA** (Non-Uniform Memory Access): память разделена на nodes, каждый CPU имеет локальную память с быстрым доступом и удалённую с медленным доступом. Лучше масштабируется.

## Question 9: Thread vs Process

Что разделяют threads в одном процессе?

A) Ничего — они полностью изолированы

B) Адресное пространство (память)

C) Только CPU время

D) Только файловые дескрипторы

**Ответ: B**

**Пояснение:** Threads в одном процессе разделяют:
- Адресное пространство (память)
- Файловые дескрипторы
- Сигналы

Но имеют отдельные:
- Стек
- Регистры
- Program counter

Это делает threads легковесными (быстрый context switch), но требует синхронизации для доступа к общим данным.

## Question 10: False Sharing

Что такое false sharing?

A) Два потока случайно используют одну переменную

B) Два потока модифицируют разные переменные в одной cache line, вызывая конфликты

C) Программист неправильно разделил данные

D) Ошибка в алгоритме синхронизации

**Ответ: B**

**Пояснение:** False sharing происходит, когда два потока на разных ядрах модифицируют разные переменные, но они находятся в одной cache line (64 байта). Каждое изменение инвалидирует cache line на другом ядре, хотя логически потоки не разделяют данные. Решение — cache line padding.
