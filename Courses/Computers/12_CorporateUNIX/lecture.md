## 1. Solaris и SPARC

### 1.1 Создание Solaris

К концу 1980-х годов стало очевидно, что корпоративному рынку нужна операционная система, способная обрабатывать критически важные задачи с максимальной надёжностью. UNIX был хорош, но требовал доработок для работы на крупных серверах с сотнями пользователей и терабайтами данных. Sun Microsystems решила создать систему, которая объединит стабильность UNIX с инновационными технологиями для корпоративного мира.

**Solaris** — операционная система от Sun Microsystems (теперь Oracle), основанная на UNIX System V. Это была не просто ещё одна версия UNIX, а комплексное решение, спроектированное для работы на серверах следующего поколения.

**История и причины создания:**

- **Разработана для процессоров SPARC** — это было революционным подходом. Вместо того чтобы адаптировать систему под разные архитектуры, Sun создала интегрированное решение "железо + программное обеспечение", где каждый компонент оптимизирован для другого.

- **Оптимизирована для серверных задач** — в отличие от настольных систем, серверы должны работать годами без перезагрузки, обслуживать тысячи одновременных соединений и обрабатывать критически важные данные. Solaris проектировалась именно для этого.

- **Высокая надёжность и масштабируемость** — система могла работать на серверах с десятками процессоров и сотнями гигабайт памяти, что было фантастикой для того времени. Это означало, что крупные компании могли консолидировать свою инфраструктуру на меньшем количестве машин.

**Особенности, изменившие индустрию:**

Solaris включала несколько революционных технологий, которые изменили индустрию и повлияли на развитие современных операционных систем:

**ZFS** — продвинутая файловая система

ZFS (Zettabyte File System) была революционной файловой системой, которая решала многие проблемы традиционных файловых систем. В отличие от традиционных файловых систем, которые были разработаны десятилетия назад и имели ограничения по размеру и надёжности, ZFS была спроектирована с нуля для современных требований. ZFS объединяла файловую систему и менеджер томов в одно целое, что упрощало управление и повышало надёжность. Одной из ключевых особенностей ZFS была самовосстанавливающаяся природа: файловая система могла обнаруживать и исправлять ошибки данных автоматически, используя контрольные суммы и избыточность. Это было критически важно для серверов, где потеря данных могла стоить миллионы долларов.

**Пример: ZFS команды**

```bash
# Создание ZFS pool
zpool create tank mirror /dev/sda /dev/sdb

# Создание файловой системы
zfs create tank/documents

# Создание snapshot
zfs snapshot tank/documents@backup1

# Клонирование snapshot
zfs clone tank/documents@backup1 tank/documents-clone

# Проверка целостности
zfs scrub tank

# Информация о pool
zpool status tank
zfs list
```

**DTrace** — инструмент динамической трассировки

DTrace был революционным инструментом для диагностики и отладки работающих систем. До DTrace системные администраторы и разработчики должны были перезапускать систему с отладочными флагами или использовать сложные инструменты, которые могли влиять на производительность. DTrace позволял динамически добавлять точки трассировки в работающую систему без перезапуска и с минимальным влиянием на производительность. Это было критически важно для диагностики проблем в продакшн-системах, где перезапуск был недопустим. DTrace мог отслеживать системные вызовы, операции ввода-вывода, использование памяти и множество других аспектов работы системы, предоставляя глубокое понимание того, что происходит внутри системы.

**Пример: DTrace скрипт**

```dtrace
#!/usr/sbin/dtrace -s

syscall:::entry
{
    @[execname] = count();
}

END
{
    printa("System calls by process: %s = %@d\n", @);
}
```

**Контейнеры** — ранняя реализация контейнеризации (zones)

Solaris Zones были одной из первых реализаций контейнеризации, задолго до того, как Docker сделал контейнеры популярными. Zones позволяли создавать изолированные окружения внутри одной операционной системы, где каждое окружение имело свои собственные процессы, файловую систему и сетевые интерфейсы, но разделяло одно ядро. Это было критически важно для консолидации серверов: вместо того чтобы запускать отдельный сервер для каждого приложения, можно было запустить несколько зон на одном физическом сервере, экономя ресурсы и упрощая управление. Zones также обеспечивали изоляцию безопасности: приложение в одной зоне не могло влиять на приложения в других зонах, что было важно для мультитенантных сред.

**Пример: Solaris Zones**

```bash
# Создание zone
zonecfg -z myzone
zonecfg:myzone> create
zonecfg:myzone> set zonepath=/zones/myzone
zonecfg:myzone> set autoboot=true
zonecfg:myzone> commit
zonecfg:myzone> exit

# Установка zone
zoneadm -z myzone install

# Запуск zone
zoneadm -z myzone boot
```

**Масштабируемость** — поддержка больших систем

Solaris была спроектирована для масштабирования на большие системы с десятками процессоров и сотнями гигабайт памяти. Это было критически важно для корпоративных клиентов, которым нужна была возможность обрабатывать растущие нагрузки без полной замены инфраструктуры. Solaris поддерживала симметричную многопроцессорность (SMP) и могла эффективно использовать множество процессоров для параллельной обработки задач. Это означало, что компании могли начать с небольшого сервера и масштабировать его по мере роста, добавляя процессоры и память, вместо того чтобы покупать новые серверы. Масштабируемость также включала поддержку больших файловых систем и сетевых соединений, что было важно для серверов баз данных и веб-серверов с высокой нагрузкой.

### 1.2 Связь с SPARC

Одной из ключевых причин успеха Solaris была её глубокая интеграция с архитектурой SPARC. Это был пример software-hardware co-design — когда операционная система и процессор проектируются вместе, учитывая возможности друг друга. Такой подход позволял достичь производительности, недоступной системам общего назначения.

**Интеграция на глубоком уровне:**

- **Solaris оптимизирована для архитектуры SPARC** — это означало, что каждая системная операция, от переключения контекста до управления памятью, использовала уникальные возможности SPARC. Код ядра писался с учётом особенностей процессора, что было критически важно для достижения максимальной производительности.

- **Использование особенностей SPARC (регистровые окна)** — SPARC имел уникальную систему регистровых окон, которая делала вызовы функций невероятно быстрыми. Solaris использовала это для минимизации накладных расходов на системные вызовы, что давало огромное преимущество при обработке тысяч запросов в секунду.

- **Высокая производительность на SPARC системах** — комбинация оптимизированной ОС и специализированного железа давала производительность, которую невозможно было достичь на системах x86 того времени. Это было революционным преимуществом для корпоративных клиентов.

**Результат:**
Создание интегрированных решений "железо + ОС" для серверов. Это означало, что компании покупали не просто сервер, а комплексную экосистему, где каждый компонент был оптимизирован для работы с другими. Такой подход доминировал в серверном мире до появления дешёвых x86 серверов.

### 1.3 Современное состояние

**OpenSolaris → illumos:**

- Solaris стала открытой (OpenSolaris)
- Развитие продолжается в проекте illumos
- Используется в специализированных системах

## 2. BSD-системы

### 2.1 Происхождение BSD

В то время как AT&T развивала коммерческий UNIX, в академической среде происходила параллельная революция. Калифорнийский университет в Беркли получил исходный код UNIX и начал его улучшать, добавляя функции, которые были нужны исследователям и студентам. Это было фундаментально важно: впервые операционная система развивалась не корпорацией, а академическим сообществом, что определило её открытый характер.

**BSD (Berkeley Software Distribution)** — вариант UNIX, разработанный в Калифорнийском университете в Беркли. Название отражает суть: это была "дистрибуция" — набор улучшений и дополнений к оригинальному UNIX, которые распространялись бесплатно среди университетов.

**История и эволюция:**

- **Начало в 1970-х годах** — студенты и преподаватели Беркли начали добавлять функции в UNIX, которых не хватало для их исследований. Это была эпоха, когда исходный код был доступен, и люди могли свободно экспериментировать. Такая открытость была критически важна для инноваций.

- **Добавления к оригинальному UNIX** — BSD не просто копировала UNIX, она добавляла революционные возможности. Многие улучшения были настолько значительными, что позже вошли в коммерческие версии UNIX. Это было доказательством того, что академическая среда может создавать технологии уровня индустрии.

- **Развитие сетевых возможностей** — это было самым важным вкладом BSD. В конце 1970-х годов сети только зарождались, и BSD стала лабораторией для экспериментов с сетевыми протоколами. Здесь родились идеи, которые позже легли в основу всего интернета.

**Вклад, изменивший мир:**

**TCP/IP стек:**
```c

// BSD sockets API (стал стандартом)
#include <sys/socket.h>
#include <netinet/in.h>

// Создание TCP socket
int sockfd = socket(AF_INET, SOCK_STREAM, 0);

struct sockaddr_in addr;
addr.sin_family = AF_INET;
addr.sin_port = htons(80);
inet_aton("192.168.1.1", &addr.sin_addr);

connect(sockfd, (struct sockaddr*)&addr, sizeof(addr));
```

**Виртуальная память:**

- Demand paging
- Memory mapping
- Swap space

**Файловая система FFS (Fast File System):**

- Улучшения над оригинальной файловой системой UNIX
- Цилиндрические группы
- Лучшая производительность

**Множество утилит:**

- vi, csh, tcsh
- Сетевые утилиты (ping, traceroute)
- Системные утилиты

### 2.2 Варианты BSD

**FreeBSD:**

- Фокус на производительности
- Широкое использование в серверах
- Основа для многих систем

**Пример: FreeBSD особенности**

```bash
# Ports system для установки ПО
cd /usr/ports/www/nginx
make install clean

# Jail (контейнеры)
jail -c name=myjail path=/jails/myjail \
     command=/bin/sh

# ZFS поддержка

zpool create tank /dev/ada0
```

**OpenBSD:**

- Фокус на безопасности
- Аудит безопасности кода
- Используется в критичных системах

**Пример: OpenBSD security features**

```bash
# W^X (Write XOR Execute) - страницы либо writable, либо executable
# ASLR (Address Space Layout Randomization)
# Stack canaries
# Privilege separation

# Проверка безопасности

auditd  # Security audit daemon
```

**NetBSD:**

- Фокус на переносимости
- Работает на множестве платформ
- Встроенные системы

**Поддерживаемые платформы:**

- x86, ARM, MIPS, PowerPC, SPARC, Alpha
- Embedded systems
- Рекордное количество платформ

**macOS:**

- Основан на BSD (Darwin)
- Показывает успех BSD в настольных системах

**Пример: macOS BSD команды**

```bash
# macOS использует BSD версии утилит

ps aux    # BSD формат (не System V)
ls -l     # BSD ls
```

### 2.3 BSD vs Linux

**Различия:**
| Аспект | BSD | Linux |
|--------|-----|-------|
| Лицензия | BSD (свободная) | GPL (copyleft) |
| Kernel + Userland | Единая система | Kernel + разные дистрибутивы |
| Происхождение | Прямой потомок UNIX | Клон UNIX |
| Инициализация | BSD init | systemd/sysvinit |
| Производительность | Высокая | Высокая |

### 2.3 Лицензия BSD

**Особенности:**

- Более свободная, чем GPL
- Позволяет использование в проприетарном ПО
- Способствовала распространению

## 3. Надёжность и масштабируемость

### 3.1 Требования корпоративных систем

Корпоративные системы имеют требования, которые значительно отличаются от требований настольных систем. В то время как настольный компьютер может быть перезагружен при проблемах, корпоративный сервер должен работать непрерывно, обрабатывая критически важные задачи. Эти требования формировали дизайн корпоративных операционных систем.

**Надёжность:**

Надёжность была критически важна для корпоративных систем, где простой мог стоить миллионы долларов:

- **Минимальное время простоя** — корпоративные серверы должны работать 24/7/365, с минимальным временем простоя для обслуживания. Это означало, что система должна была поддерживать обновления без перезагрузки, замену компонентов без остановки работы, и автоматическое восстановление после ошибок. Время простоя измерялось в минутах или часах в год, а не в днях

- **Отказоустойчивость** — система должна была продолжать работать даже при отказе отдельных компонентов. Это достигалось через избыточность: резервные диски, сетевые интерфейсы, источники питания и даже серверы. Отказ одного компонента не должен был приводить к остановке всей системы

- **Восстановление после сбоев** — даже при сбоях система должна была автоматически восстанавливаться и продолжать работу. Это включало автоматическое переключение на резервные компоненты, восстановление данных из резервных копий, и автоматический перезапуск сервисов после ошибок

**Масштабируемость:**

Корпоративные системы должны были масштабироваться для обработки растущих нагрузок:

- **Поддержка большого количества пользователей** — корпоративные серверы должны были обслуживать тысячи одновременных пользователей без деградации производительности. Это требовало эффективного управления процессами, памятью и сетевыми соединениями. Система должна была распределять ресурсы справедливо между пользователями и предотвращать ситуации, когда один пользователь мог монополизировать ресурсы

- **Обработка больших объёмов данных** — корпоративные системы должны были обрабатывать терабайты и петабайты данных. Это требовало эффективных файловых систем, которые могли масштабироваться до больших размеров, и систем управления данными, которые могли эффективно обрабатывать большие объёмы информации

- **Горизонтальное и вертикальное масштабирование** — система должна была поддерживать оба типа масштабирования. Вертикальное масштабирование (добавление ресурсов к одному серверу) позволяло увеличить мощность без изменения архитектуры. Горизонтальное масштабирование (добавление серверов) позволяло распределять нагрузку между несколькими серверами, что было важно для обработки пиковых нагрузок

**Производительность:**

Производительность была критически важна для корпоративных систем, где каждая миллисекунда задержки могла влиять на бизнес:

- **Высокая пропускная способность** — система должна была обрабатывать большое количество операций в секунду. Это было важно для серверов баз данных, веб-серверов и файловых серверов, которые должны были обрабатывать тысячи запросов одновременно

- **Низкая задержка** — для интерактивных приложений и систем реального времени низкая задержка была критически важна. Система должна была минимизировать время отклика на запросы пользователей, что требовало эффективного планирования процессов и управления памятью

- **Эффективное использование ресурсов** — корпоративные системы должны были эффективно использовать доступные ресурсы, минимизируя отходы. Это означало эффективное управление памятью, процессорным временем и дисковым пространством, чтобы максимизировать количество работы, которую система могла выполнить с доступными ресурсами

### 3.2 Технологии надёжности

Корпоративные системы использовали множество технологий для обеспечения надёжности и защиты от отказов. Эти технологии были критически важны для предотвращения потери данных и обеспечения непрерывной работы систем.

**RAID:**

RAID (Redundant Array of Independent Disks) был одной из ключевых технологий для обеспечения надёжности хранения данных:

- **Избыточное хранение данных** — RAID использовал несколько дисков для хранения данных с избыточностью. Это означало, что данные хранились на нескольких дисках одновременно, что защищало от потери данных при отказе одного диска. Различные уровни RAID обеспечивали разные компромиссы между избыточностью и производительностью

- **Защита от отказов дисков** — при отказе одного диска в RAID-массиве система могла продолжать работать, используя данные с оставшихся дисков. Это было критически важно для серверов, где отказ диска не должен был приводить к остановке работы. Система могла автоматически обнаруживать отказы дисков и уведомлять администраторов, позволяя заменить диск без остановки работы

**Пример: RAID в Solaris**

```bash
# Solaris Volume Manager
metainit d10 1 1 c0t0d0s0
metainit d20 1 1 c0t1d0s0
metainit d0 -m d10
metattach d0 d20  # Mirror
```

**Кластеризация:**

Кластеризация позволяла нескольким серверам работать вместе как единая система, обеспечивая высокую доступность и масштабируемость:

- **Несколько серверов работают вместе** — кластер состоял из нескольких серверов, которые работали вместе для обработки нагрузки. Это позволяло распределять нагрузку между серверами и обеспечивать резервирование: если один сервер выходил из строя, другие серверы могли взять на себя его нагрузку. Кластеризация также позволяла масштабировать систему горизонтально, добавляя новые серверы по мере роста нагрузки

- **Высокая доступность** — кластеризация обеспечивала высокую доступность через автоматическое переключение на резервные серверы при отказе основного сервера. Это означало, что система могла продолжать работать даже при отказе отдельных серверов, что было критически важно для критически важных приложений. Высокая доступность также включала автоматическое обнаружение отказов и переключение нагрузки, что минимизировало время простоя

**Резервное копирование:**

Резервное копирование было критически важно для защиты данных от потери из-за ошибок, сбоев или катастроф:

- **Регулярные бэкапы** — корпоративные системы выполняли регулярные резервные копии данных, чтобы обеспечить возможность восстановления данных в случае потери. Резервные копии выполнялись автоматически по расписанию, что гарантировало, что данные всегда были защищены. Различные стратегии резервного копирования обеспечивали разные компромиссы между частотой копирования и использованием ресурсов

- **Восстановление данных** — система должна была обеспечивать быстрое и надёжное восстановление данных из резервных копий. Это включало возможность восстановления отдельных файлов, директорий или всей системы, в зависимости от потребностей. Быстрое восстановление было критически важно для минимизации времени простоя при сбоях

**Пример: ZFS snapshots для backup**

```bash
# Автоматические snapshots
zfs set snapdir=visible tank/documents
zfs snapshot -r tank/documents@$(date +%Y%m%d)

# Отправка snapshots на удалённый сервер

zfs send tank/documents@snapshot1 | \
    ssh remote zfs receive tank/backup
```

### 3.3 Масштабирование

Масштабирование было критически важно для корпоративных систем, которые должны были обрабатывать растущие нагрузки. Существовало два основных подхода к масштабированию, каждый со своими преимуществами и ограничениями.

**Вертикальное масштабирование:**

Вертикальное масштабирование (scaling up) означало увеличение мощности одного сервера:

- **Увеличение мощности одного сервера** — вместо добавления новых серверов система увеличивала мощность существующего сервера, добавляя больше процессоров, памяти, дисков и других ресурсов. Это было проще в управлении, так как требовало управления только одним сервером, но имело ограничения по максимальной мощности одного сервера

- **Больше процессоров, памяти** — вертикальное масштабирование включало добавление процессоров для увеличения вычислительной мощности и памяти для обработки больших объёмов данных. Это позволяло системе обрабатывать больше одновременных запросов и большие объёмы данных без изменения архитектуры приложений. Однако вертикальное масштабирование имело ограничения по стоимости и доступности оборудования

**Горизонтальное масштабирование:**

Горизонтальное масштабирование (scaling out) означало добавление новых серверов:

- **Добавление серверов** — вместо увеличения мощности одного сервера система добавляла новые серверы для обработки растущей нагрузки. Это было более гибким подходом, так как позволяло добавлять серверы по мере необходимости, но требовало более сложного управления и распределения нагрузки

- **Распределение нагрузки** — горизонтальное масштабирование требовало распределения нагрузки между несколькими серверами, что включало балансировку нагрузки, синхронизацию данных между серверами и управление состоянием. Это было более сложным в реализации, но обеспечивало лучшую масштабируемость и отказоустойчивость

## 4. Серверный мир 90-х и 2000-х

### 4.1 Доминирование UNIX

**1990-е:**

- UNIX доминировал в серверном мире
- Различные варианты: Solaris, AIX, HP-UX, BSD
- Высокая стоимость, но необходимая надёжность

**Применение:**

- Корпоративные серверы
- Базы данных
- Веб-серверы (ранний интернет)
- Файловые серверы

### 4.2 Конкуренция

**Linux:**

- Появление Linux в 1990-х
- Бесплатная альтернатива
- Рост популярности

**Windows NT Server:**

- Конкуренция от Microsoft
- Упрощённое администрирование
- Интеграция с Windows клиентами

**Результат:**
Трёхсторонняя конкуренция: проприетарный UNIX, Linux, Windows Server.

### 4.3 Изменения в 2000-х

**Консолидация:**

- Меньше вариантов проприетарного UNIX
- Доминирование Linux и Windows Server
- Облачные вычисления

**Наследие:**
Идеи и технологии из корпоративного UNIX перешли в Linux и современные системы.

## 💡 Key Takeaways

- **Solaris** показала важность интеграции ОС и аппаратуры (SPARC) для серверных систем, создала технологии (ZFS, DTrace, zones), которые повлияли на современные системы

- **BSD** внесла огромный вклад в развитие UNIX (TCP/IP, виртуальная память, FFS) и сетевых технологий, более свободная лицензия способствовала распространению

- **Надёжность и масштабируемость** — ключевые требования корпоративных систем (RAID, кластеризация, резервное копирование, вертикальное и горизонтальное масштабирование)

- **Серверный мир 90-2000-х** был эпохой доминирования UNIX (Solaris, AIX, HP-UX, BSD), которая сформировала современные подходы, многие идеи перешли в Linux и современные системы
