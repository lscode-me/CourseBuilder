## 1. Эволюция графических систем

### 1.1 Текстовые терминалы (1960-е - 1980-е)

Эпоха текстовых терминалов была временем, когда компьютеры взаимодействовали с пользователями через текст, а не графику. Это был период фундаментальных ограничений: память была дорогой, процессоры — медленными, а цветные дисплеи — роскошью. Текстовый режим был не просто выбором дизайна — это был единственный практичный способ взаимодействия с компьютером при существующих технологических возможностях.

Важно понимать, что текстовые терминалы не были временной мерой — они доминировали более двух десятилетий и заложили основы многих концепций, которые мы используем до сих пор. Командная строка, которую мы используем сегодня в Linux и macOS, является прямым наследником этой эпохи.

**Character mode:**

Текстовые терминалы работали в режиме символов (character mode), где экран представлял собой сетку символов фиксированного размера. Это было революционно простое решение: вместо управления каждым пикселем, система управляла только символами, что требовало на порядки меньше памяти и вычислительной мощности.

- **80x25 символов** — стандартный размер экрана терминала составлял 80 символов в ширину и 25 строк в высоту, что давало 2000 символов на экране. Это был критически важный компромисс между читаемостью и стоимостью. Для хранения экрана требовалось всего 2000 байт памяти (по одному байту на символ), что было приемлемо даже для компьютеров того времени. Если бы система работала с пикселями, требовалось бы на порядки больше памяти. Число 80 не было случайным — оно соответствовало стандартной ширине перфокарт и бумажных распечаток, что обеспечивало совместимость с существующей инфраструктурой

- **ASCII таблица** — символы отображались с использованием таблицы ASCII (American Standard Code for Information Interchange), которая определяла соответствие между числами (0-127) и символами. Это было фундаментальным достижением стандартизации — до ASCII каждый производитель использовал свою кодировку символов, что делало обмен данными между системами практически невозможным. ASCII создала общий язык для всех компьютеров, что было революционным для развития индустрии. Таблица содержала 128 символов: 95 печатных (буквы, цифры, знаки препинания) и 33 управляющих (перевод строки, табуляция и другие)

- **Псевдографика для "рисования"** — для создания простых графических элементов использовалась псевдографика — специальные символы ASCII (коды 176-223 в расширенной таблице), которые могли создавать линии, рамки и простые формы. Это был гениальный компромисс: программисты могли создавать визуально привлекательные интерфейсы и диаграммы, не выходя за пределы текстового режима. Псевдографика позволила появиться первым интерактивным приложениям с "графическим" интерфейсом, таким как Norton Commander и Lotus 1-2-3, которые стали невероятно популярными в 1980-х годах

### 1.2 Bitmap графика

Переход к bitmap графике был одним из самых революционных изменений в истории компьютеров. Это было не просто техническое улучшение — это был концептуальный прорыв, который изменил саму природу взаимодействия человека с компьютером. Вместо ограниченного набора из 2000 символов на экране, компьютер теперь мог управлять сотнями тысяч пикселей, создавая произвольные изображения.

Почему это было так важно? Bitmap графика открыла путь к графическим интерфейсам пользователя (GUI), которые сделали компьютеры доступными миллионам людей, не знающих командную строку. Это была фундаментальная демократизация вычислительной техники — компьютеры из инструмента для специалистов превратились в инструмент для всех.

**Framebuffer** — область памяти, представляющая экран:

Framebuffer — это критически важная концепция, которая создала прямое соответствие между памятью и экраном. Каждый пиксель на экране представлен одним или несколькими байтами в памяти. Это означает, что программа может "рисовать" на экране, просто записывая значения в память. Простота и элегантность этой идеи трудно переоценить — она стала основой всей современной компьютерной графики:

```

Экран 640x480, 8-bit color → 307,200 bytes
```

В этом примере экран размером 640x480 пикселей с 8-битным цветом (256 цветов) требует 307,200 байт памяти для хранения содержимого экрана. Это было значительным объёмом памяти для того времени, но позволяло создавать произвольные изображения. Framebuffer сделал возможным программное рисование пикселей, что было основой для графических интерфейсов и приложений.

**Ранние системы:**

Переход к bitmap графике происходил постепенно в разных системах, и каждая система внесла свой вклад в развитие этой революционной технологии:

- **Xerox Alto (1973)** — это был абсолютно революционный компьютер, который опередил своё время на десятилетие. Alto был первым компьютером с bitmap дисплеем (606x808 пикселей) и полноценным графическим интерфейсом с окнами, иконками и мышью. Стоимость Alto была огромной — около $40,000, что делало его доступным только для исследовательских лабораторий. Но его влияние трудно переоценить: когда Стив Джобс посетил Xerox PARC в 1979 году и увидел Alto, он понял будущее компьютеров. Alto напрямую вдохновил создание Apple Lisa и Macintosh. Фактически, вся индустрия персональных компьютеров следующих 40 лет развивалась по пути, заложенному Alto

- **Apple II (1977)** — это был один из первых массовых персональных компьютеров с цветной bitmap графикой. Apple II имел несколько графических режимов, включая режим высокого разрешения 280x192 пикселей с 6 цветами. Это было критически важным достижением: впервые домашний компьютер стоимостью около $1300 мог отображать цветную графику. Apple II породил целую индустрию образовательных программ и игр, что сделало компьютеры привлекательными для широкой аудитории. Программы типа VisiCalc (первая электронная таблица) и игры типа Prince of Persia показали потенциал bitmap графики для практических приложений и развлечений

- **IBM PC with CGA/EGA/VGA** — IBM PC начал в 1981 году с простого графического адаптера CGA (320x200, 4 цвета), который был компромиссом между стоимостью и возможностями. Затем последовал EGA в 1984 году (640x350, 16 цветов) и революционный VGA в 1987 году (640x480, 16 цветов или 320x200, 256 цветов). VGA стал фундаментальным стандартом — он был достаточно хорош для профессиональных приложений и игр, достаточно доступен по цене для массового рынка, и его 15-контактный разъём используется до сих пор (спустя почти 40 лет!). VGA обеспечил стандартизацию, которая позволила развиться индустрии графических приложений и игр на платформе PC

### 1.3 Графические ускорители

К началу 1990-х годов стало очевидно, что центральный процессор (CPU) не справляется с задачами графики. Программное рисование было слишком медленным — для отрисовки одного кадра сложной сцены CPU мог тратить секунды или даже минуты. Это был фундаментальный барьер для развития графических приложений и игр.

Появление графических ускорителей было революционным ответом на эту проблему. Идея была проста, но радикальна: создать специализированное аппаратное обеспечение, которое выполняет графические операции на порядки быстрее, чем универсальный процессор. Это был критически важный шаг в эволюции компьютерной графики, который заложил основу для современных GPU.

**1990-е: 2D accelerators**

Первое поколение графических ускорителей фокусировалось на ускорении 2D операций, которые были основой графических интерфейсов Windows и других операционных систем того времени:

- **BitBlt (Bit Block Transfer)** — это была революционная операция, которая копировала прямоугольные области экрана аппаратно, вместо медленного программного копирования пикселей. BitBlt ускорял прокрутку окон, перемещение окон, отрисовку кнопок и других элементов интерфейса в десятки раз. Это превратило Windows из медленного и неотзывчивого интерфейса в практичную систему

- **Hardware line drawing** — аппаратное рисование линий, прямоугольников и других примитивов. Вместо того чтобы CPU вычислял каждый пиксель линии, графический ускоритель делал это мгновенно. Это было критически важно для CAD-приложений и векторной графики

- **Sprite support** — аппаратная поддержка спрайтов (небольших изображений, которые можно быстро перемещать), что было особенно важно для игр. Спрайты позволяли создавать плавную анимацию без нагрузки на CPU

**Конец 1990-х: 3D accelerators**

Появление 3D ускорителей ознаменовало начало новой эры в компьютерной графике. Это было революционное изменение, которое сделало возможными современные 3D игры и профессиональную 3D графику:

- **3dfx Voodoo (1996)** — это был первый массовый 3D ускоритель, который изменил индустрию игр навсегда. Voodoo мог рендерить 3D сцены в реальном времени с текстурами, освещением и другими эффектами. Игры типа Quake и Tomb Raider на Voodoo выглядели на порядок лучше, чем программный рендеринг. Voodoo создал рынок 3D ускорителей и показал, что специализированное оборудование может обеспечить качественный опыт 3D графики для массового рынка

- **NVIDIA Riva 128 (1997)** — первая карта NVIDIA с полноценной 3D функциональностью. NVIDIA сделала ставку на интеграцию 2D и 3D в одном чипе, в отличие от Voodoo, которая требовала отдельную 2D карту. Это было стратегически важное решение, которое помогло NVIDIA стать лидером рынка. Riva 128 была дешевле и практичнее, чем решения конкурентов

- **ATI Rage (1996)** — карта ATI, которая также предлагала интегрированное 2D/3D решение. Конкуренция между ATI, NVIDIA и 3dfx привела к быстрому развитию технологий и снижению цен, что сделало 3D графику доступной миллионам пользователей

**Пример: BitBlt операция**

```c

// Копирование прямоугольной области экрана
BitBlt(
    hDestDC,      // Destination device context
    x, y,         // Destination coordinates
    width, height,// Size
    hSrcDC,       // Source device context
    srcX, srcY,   // Source coordinates
    SRCCOPY       // Operation: copy
);
```

**Преимущество:** Hardware-ускорение вместо медленного программного копирования пикселей.

## 2. Архитектура GPU

### 2.1 CPU vs GPU Philosophy

В конце 1990-х годов произошёл фундаментальный сдвиг в понимании того, как должны работать вычислительные системы. Стало очевидно, что для разных типов задач нужны радикально разные архитектуры. CPU и GPU представляют собой два противоположных подхода к проектированию вычислительных систем — это было революционным осознанием в индустрии.

Архитектура CPU и GPU представляет собой фундаментально разные философии проектирования вычислительных систем. Это не просто технические различия — это отражение двух разных подходов к решению вычислительных задач, каждый из которых оптимизирован для своего класса проблем. CPU оптимизирован для универсальности и быстрого выполнения последовательных операций, в то время как GPU оптимизирован для массового параллелизма и высокой пропускной способности.

Почему эти различия так важны? Потому что они определяют, какой процессор лучше подходит для конкретной задачи. Попытка использовать CPU для задач, оптимальных для GPU (и наоборот), может привести к разнице в производительности в 10-100 раз. Это не просто количественная разница — это разница между возможным и невозможным. Многие современные приложения (глубокое обучение, научные симуляции, рендеринг) были бы невозможны без GPU. Это было критически важное открытие для развития вычислительной техники.

**CPU (Central Processing Unit):**

CPU — это "универсальный солдат" компьютера, оптимизированный для выполнения любых задач быстро и эффективно. Философия CPU: "делай всё хорошо, особенно последовательные задачи с низкой задержкой":

- **Несколько мощных ядер (4-64)** — современные CPU имеют относительно небольшое количество мощных ядер, каждое из которых может выполнять сложные операции быстро. Это позволяет эффективно выполнять последовательные задачи, где важна низкая задержка и быстрый отклик. Небольшое количество ядер упрощает управление и синхронизацию

- **Сложные инструкции** — CPU поддерживает сложные инструкции, которые могут выполнять множество операций за один такт. Это включает инструкции для условных переходов, циклов, вызовов функций и других сложных операций. Сложные инструкции позволяют эффективно выполнять последовательный код

- **Большие кэши** — CPU имеют большие многоуровневые кэши (L1, L2, L3), которые минимизируют задержку доступа к памяти. Это критически важно для последовательных задач, где важна низкая задержка. Большие кэши также помогают предсказывать доступ к данным и инструкциям

- **Low latency, high throughput per thread** — CPU оптимизирован для низкой задержки и высокой пропускной способности на поток. Это означает, что один поток может выполнять операции быстро и эффективно. Это важно для интерактивных приложений, где важна быстрая реакция

- **Оптимизирован для последовательных задач** — CPU оптимизирован для выполнения последовательных задач, где операции выполняются одна за другой. Это включает большинство программного обеспечения: операционные системы, приложения, игры. Последовательные задачи требуют сложной логики и условных переходов, для которых CPU идеально подходит

**GPU:**

GPU (Graphics Processing Unit) оптимизирован для параллельных задач и высокой пропускной способности:

- **Тысячи простых ядер (2000-10000+)** — GPU имеют огромное количество простых ядер, каждое из которых может выполнять простые операции параллельно. Это позволяет обрабатывать тысячи элементов данных одновременно, что критически важно для графики и параллельных вычислений. Большое количество ядер компенсирует их простоту

- **Простые инструкции** — GPU поддерживают простые инструкции, которые выполняются быстро и эффективно. Это включает арифметические операции, операции с памятью и простые условные переходы. Простые инструкции позволяют эффективно использовать параллелизм

- **Маленькие кэши** — GPU имеют маленькие кэши, так как они оптимизированы для пропускной способности, а не задержки. Это означает, что доступ к памяти может быть медленным, но большое количество ядер компенсирует это через параллелизм. Маленькие кэши также упрощают архитектуру и снижают стоимость

- **High latency, massive throughput** — GPU оптимизирован для высокой пропускной способности, даже если это означает высокую задержку для отдельных операций. Это означает, что одна операция может быть медленной, но тысячи операций выполняются одновременно, что даёт огромную общую пропускную способность. Это важно для задач, где важна общая производительность, а не задержка отдельных операций

- **Оптимизирован для параллельных задач** — GPU оптимизирован для выполнения параллельных задач, где одна и та же операция применяется к множеству элементов данных. Это включает рендеринг графики, научные вычисления, машинное обучение. Параллельные задачи требуют простой логики и большого количества данных, для которых GPU идеально подходит

### 2.2 SIMD архитектура

Концепция SIMD (Single Instruction, Multiple Data) возникла ещё в 1960-х годах в суперкомпьютерах, но её истинный потенциал раскрылся только с появлением GPU. Идея была проста, но революционна: вместо того чтобы выполнять одну операцию для одного элемента данных, процессор выполняет одну операцию для множества элементов одновременно. Это было фундаментальным изменением в подходе к вычислениям.

Почему SIMD так важна для GPU? Потому что графические задачи идеально подходят для этой модели — при рендеринге сцены одна и та же операция (например, вычисление цвета) применяется к миллионам пикселей. Это означает, что одна инструкция может обработать тысячи пикселей одновременно, что даёт колоссальный прирост производительности. Без SIMD современная компьютерная графика в реальном времени была бы невозможна.

**Single Instruction, Multiple Data:**

Чтобы понять революционность SIMD, важно увидеть разницу в подходах. CPU выполняет одну инструкцию для одного элемента:
```c

// CPU: последовательное выполнение
for (int i = 0; i < 1000; i++) {
    result[i] = a[i] + b[i];
}
// Время: ~1000 циклов (если 1 операция = 1 цикл)
```

**CPU с SIMD (SSE/AVX):**
```c

// CPU с AVX-512: 16 элементов за раз
#include <immintrin.h>
for (int i = 0; i < 1000; i += 16) {
    __m512 va = _mm512_load_ps(&a[i]);
    __m512 vb = _mm512_load_ps(&b[i]);
    __m512 vresult = _mm512_add_ps(va, vb);
    _mm512_store_ps(&result[i], vresult);
}
// Время: ~63 цикла (1000/16)
```

GPU выполняет одну инструкцию для тысяч элементов одновременно:
```c

// GPU: параллельное выполнение
// Все 1000 элементов обрабатываются одновременно
result[0..1000] = a[0..1000] + b[0..1000];  // параллельно!
// Время: ~1 цикл (если достаточно ядер)
```

**Масштабирование:**

- CPU: 4-64 ядра → 4-64 операции параллельно
- GPU: 2000-10000 ядер → тысячи операций параллельно

### 2.3 Современная GPU архитектура

Современные GPU — это результат десятилетий эволюции и оптимизации. То, что начиналось как простой графический ускоритель для отрисовки треугольников, превратилось в сложнейшую параллельную вычислительную систему с тысячами ядер. Это была революционная трансформация, которая изменила не только графику, но и всю индустрию вычислений.

Архитектура современного GPU организована иерархически, что критически важно для эффективного использования параллелизма. Множество вычислительных блоков (Streaming Multiprocessors) работают независимо друг от друга, обрабатывая разные части данных. Внутри каждого блока десятки ядер выполняют одинаковые инструкции параллельно. Эта иерархическая структура позволяет GPU масштабироваться от тысяч до десятков тысяч ядер без потери эффективности.

**NVIDIA Ampere/Ada (пример):**
```

GPU
├── Streaming Multiprocessors (SM) x 128
│   ├── CUDA Cores x 64
│   ├── Tensor Cores
│   ├── RT Cores (ray tracing)
│   └── Shared Memory
├── L2 Cache
└── VRAM (GDDR6/HBM)
```

Эта архитектура представляет собой вершину инженерной мысли. Каждый компонент тщательно оптимизирован для конкретной задачи: CUDA Cores для общих вычислений, Tensor Cores для операций с матрицами (критически важно для AI), RT Cores для трассировки лучей в реальном времени (это было революционным достижением). Вместе они создают невероятно мощную и гибкую вычислительную платформу.

**Каждый SM:**

- 64-128 CUDA cores
- Shared memory (~100 KB)
- Warp scheduler

**Warp** — группа из 32 потоков, выполняющих одну инструкцию.

**Пример: Warp execution**

```c

// 32 потока в warp выполняют одну инструкцию
__global__ void vectorAdd(float *a, float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];  // Все 32 потока выполняют одновременно
    }
}
```

**Важно:** Если потоки в warp идут по разным путям (divergence), производительность падает:
```c

// Плохо: divergence в warp
if (threadIdx.x % 2 == 0) {
    result = a + b;  // 16 потоков
} else {
    result = a - b;  // 16 потоков
}
// Обе ветки выполняются последовательно → 2x медленнее
```

### 2.4 Memory Hierarchy в GPU

Память — это критически важный аспект архитектуры GPU, возможно даже более важный, чем количество вычислительных ядер. Почему? Потому что тысячи ядер должны постоянно получать данные для обработки, и если данные поступают медленно, ядра простаивают. Это фундаментальная проблема параллельных систем: чем больше ядер, тем острее проблема доступа к памяти.

GPU решает эту проблему через иерархию памяти — это была революционная идея, заимствованная из архитектуры CPU, но доведённая до совершенства. Память организована в несколько уровней: от сверхбыстрых регистров внутри каждого ядра до медленной, но огромной глобальной памяти. Эффективное использование этой иерархии — ключ к высокой производительности GPU. Разница между хорошим и плохим использованием памяти может быть в 100 раз!

**Уровни памяти (от быстрого к медленному):**

```

Registers (per thread)     → ~1 cycle, ~256 KB per SM
Shared Memory (per block)   → ~5 cycles, ~100 KB per SM
L1/L2 Cache                 → ~50 cycles, несколько MB
Global Memory (VRAM)        → ~400 cycles, GB
```

Обратите внимание на огромную разницу в скорости: доступ к глобальной памяти в 400 раз медленнее доступа к регистрам! Это означает, что эффективная программа должна минимизировать доступ к глобальной памяти и максимально использовать локальную память. Это критически важное понимание для программирования GPU.

**Пример: Использование shared memory**

```c

__global__ void matrixMultiply(float *A, float *B, float *C, int N) {
    __shared__ float tileA[16][16];  // Shared memory
    __shared__ float tileB[16][16];
    
    // Загрузить tile в shared memory (быстро)
    tileA[threadIdx.y][threadIdx.x] = A[...];
    tileB[threadIdx.y][threadIdx.x] = B[...];
    __syncthreads();  // Ждать загрузки всех
    
    // Вычисления с данными из shared memory
    float sum = 0;
    for (int k = 0; k < 16; k++) {
        sum += tileA[threadIdx.y][k] * tileB[k][threadIdx.x];
    }
    C[...] = sum;
}
```

**Оптимизация:** Использование shared memory может ускорить код в 10-100 раз по сравнению с прямым доступом к global memory.

## 3. Графический pipeline

### 3.1 Rendering Pipeline

```

3D Model → Vertex Processing → Rasterization → Fragment Processing → Display
```

**Детальный pipeline:**

```

1. Input Assembler      → Собирает вершины в примитивы (треугольники)
2. Vertex Shader       → Трансформация координат, освещение
3. Hull Shader         → Tessellation (разбиение на подтреугольники)
4. Domain Shader       → Обработка tessellated вершин
5. Geometry Shader     → Генерация новых примитивов
6. Rasterization       → Конвертация в пиксели
7. Fragment Shader     → Цвет каждого пикселя
8. Output Merger       → Blending, depth test, stencil test
```

**Vertex Shader (GLSL пример):**
```glsl

// Vertex shader
#version 330 core
layout (location = 0) in vec3 aPos;      // Позиция вершины
layout (location = 1) in vec2 aTexCoord; // Текстурные координаты

uniform mat4 model;      // Матрица модели
uniform mat4 view;       // Матрица вида
uniform mat4 projection; // Матрица проекции

out vec2 TexCoord;

void main() {
    // Трансформация в clip space
    gl_Position = projection * view * model * vec4(aPos, 1.0);
    TexCoord = aTexCoord;
}
```

**Fragment Shader (GLSL пример):**
```glsl

// Fragment shader
#version 330 core
in vec2 TexCoord;
out vec4 FragColor;

uniform sampler2D ourTexture;

void main() {
    // Текстурирование
    FragColor = texture(ourTexture, TexCoord);
}
```

**Rasterization:**

- Конвертация треугольников в пиксели
- Интерполяция атрибутов (цвет, текстура) между вершинами
- Z-buffer для определения видимости

**Fragment/Pixel Shader:**

- Текстурирование
- Lighting calculations (Phong, PBR)
- Effects (bloom, shadows, reflections)

## 4. GPGPU - General Purpose GPU Computing

### 4.1 Идея

**Проблема:** GPU мощны, но используются только для графики.

**Решение:** Использовать GPU для общих вычислений.

### 4.2 CUDA (2007)

**NVIDIA CUDA** — платформа для программирования GPU:

**Полный пример: Vector Addition**

```c
#include <cuda_runtime.h>
#include <stdio.h>

// Kernel функция (выполняется на GPU)
__global__ void vectorAdd(int *a, int *b, int *c, int n) {
    // Вычисляем индекс для этого потока
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

int main() {
    int n = 10000;
    size_t size = n * sizeof(int);
    
    // Host (CPU) память
    int *h_a = (int*)malloc(size);
    int *h_b = (int*)malloc(size);
    int *h_c = (int*)malloc(size);
    
    // Инициализация
    for (int i = 0; i < n; i++) {
        h_a[i] = i;
        h_b[i] = i * 2;
    }
    
    // Device (GPU) память
    int *d_a, *d_b, *d_c;
    cudaMalloc(&d_a, size);
    cudaMalloc(&d_b, size);
    cudaMalloc(&d_c, size);
    
    // Копирование CPU → GPU
    cudaMemcpy(d_a, h_a, size, cudaMemcpyHostToDevice);
    cudaMemcpy(d_b, h_b, size, cudaMemcpyHostToDevice);
    
    // Запуск kernel
    int threadsPerBlock = 256;
    int blocksPerGrid = (n + threadsPerBlock - 1) / threadsPerBlock;
    vectorAdd<<<blocksPerGrid, threadsPerBlock>>>(d_a, d_b, d_c, n);
    
    // Копирование GPU → CPU
    cudaMemcpy(h_c, d_c, size, cudaMemcpyDeviceToHost);
    
    // Проверка результата
    printf("c[0] = %d, c[9999] = %d\n", h_c[0], h_c[9999]);
    
    // Освобождение памяти
    cudaFree(d_a);
    cudaFree(d_b);
    cudaFree(d_c);
    free(h_a);
    free(h_b);
    free(h_c);
    
    return 0;
}
```

**Концепции:**

- **Kernel** — функция, выполняемая на GPU (помечена `__global__`)

- **Thread** — один экземпляр kernel (имеет `threadIdx`)

- **Block** — группа threads (до 1024, имеет `blockIdx`)

- **Grid** — набор blocks (весь запуск kernel)

**Иерархия потоков:**
```

Grid (весь kernel launch)
  └── Block 0
      ├── Thread 0
      ├── Thread 1
      └── ...
  └── Block 1
      └── ...
```

**Вычисление индекса:**
```c

int globalIndex = blockIdx.x * blockDim.x + threadIdx.x;
// blockIdx.x    - номер блока в grid
// blockDim.x    - размер блока (количество threads)
// threadIdx.x   - номер thread в блоке
```

### 4.3 OpenCL (альтернатива CUDA)

**OpenCL** — открытый стандарт для GPGPU (работает на NVIDIA, AMD, Intel):

```c

// OpenCL kernel (похож на CUDA)
__kernel void vectorAdd(__global int *a, 
                        __global int *b, 
                        __global int *c) {
    int i = get_global_id(0);
    c[i] = a[i] + b[i];
}
```

**Преимущества OpenCL:**

- Работает на любых GPU/CPU
- Vendor-agnostic

**Недостатки:**

- Меньше оптимизаций для конкретных GPU
- Сложнее в использовании

### 4.4 Применения GPGPU

**Machine Learning:**

**Пример: Matrix Multiplication для нейросетей**

```c

// Упрощённый пример умножения матриц на GPU
__global__ void matrixMultiply(float *A, float *B, float *C, 
                                int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    
    if (row < M && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < K; k++) {
            sum += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}
```

**Применения:**

- Convolutions (CNNs)
- Training neural networks (backpropagation)
- Inference (предсказания)

**Scientific Computing:**

**Пример: Molecular Dynamics**

```c

// Вычисление сил между частицами
__global__ void computeForces(float3 *positions, 
                               float3 *forces, 
                               int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    
    float3 force = make_float3(0, 0, 0);
    for (int j = 0; j < n; j++) {
        if (i != j) {
            float3 r = positions[j] - positions[i];
            float dist = length(r);
            // Lennard-Jones potential
            float f = 4 * epsilon * (pow(sigma/dist, 12) - pow(sigma/dist, 6));
            force += f * normalize(r);
        }
    }
    forces[i] = force;
}
```

**Cryptocurrency:**

## 5. Графическая память

### 5.1 VRAM vs System RAM

**VRAM (Video RAM):**

- Находится на видеокарте
- High bandwidth (до 1 TB/s!)
- Доступна GPU напрямую
- Изолирована от CPU

**Типы:**

- **GDDR6:** 16-24 Gbps per pin (gaming GPUs)

- **HBM2/3** (High Bandwidth Memory): stacked memory, до 2 TB/s (datacenter GPUs)

### 5.2 Unified Memory (Apple Silicon, AMD APU)

**Идея:** CPU и GPU разделяют одну память

**Пример: Unified Memory в CUDA**

```c

// Unified Memory автоматически управляется системой
__managed__ int *data;  // Доступна и CPU, и GPU

// Выделение unified memory
cudaMallocManaged(&data, n * sizeof(int));

// CPU может писать
for (int i = 0; i < n; i++) {
    data[i] = i;
}

// GPU может читать (без явного копирования!)
__global__ void process(int *data, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        data[i] *= 2;  // GPU изменяет данные
    }
}

// CPU может читать результат (без явного копирования!)
printf("%d\n", data[0]);
```

**Преимущества:**

- Нет копирования CPU ↔ GPU (автоматическая миграция страниц)
- Упрощение программирования (один указатель)
- Меньше ошибок (нет забытых копирований)

**Недостатки:**

- Меньше bandwidth для GPU (shared bus)
- Конкуренция за память
- Latency при миграции страниц

**Сравнение подходов:**

| Подход | Bandwidth | Сложность | Производительность |
|--------|-----------|-----------|-------------------|
| Separate Memory | Высокая (1 TB/s) | Высокая | Максимальная |
| Unified Memory | Средняя (50 GB/s) | Низкая | Хорошая |

### 5.3 Memory Management Best Practices

**1. Minimize Host-Device Transfers**

```c

// Плохо: много маленьких копирований
for (int i = 0; i < 1000; i++) {
    cudaMemcpy(d_data, h_data, size, cudaMemcpyHostToDevice);
    kernel<<<...>>>(d_data);
}

// Хорошо: одно большое копирование
cudaMemcpy(d_data, h_data, totalSize, cudaMemcpyHostToDevice);
for (int i = 0; i < 1000; i++) {
    kernel<<<...>>>(d_data);
}
```

**2. Использование Pinned Memory**

```c

// Pinned memory быстрее для Host-Device transfers
float *h_pinned;
cudaMallocHost(&h_pinned, size);  // Pinned (page-locked)
// ... копирование быстрее в 2-3 раза
cudaFreeHost(h_pinned);
```

**3. Memory Coalescing**

```c

// Хорошо: coalesced access (последовательные адреса)
__global__ void good(float *data) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    data[i] = ...;  // Все threads читают последовательно
}

// Плохо: uncoalesced access (случайные адреса)
__global__ void bad(float *data) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    data[random[i]] = ...;  // Случайные адреса → медленно
}
```

## 6. Ray Tracing

### 6.1 Rasterization vs Ray Tracing

**Rasterization (традиционный):**

- Проекция треугольников на экран
- Fast (~60+ FPS)
- Приближения для освещения

**Ray Tracing:**

- Симуляция физики света
- Каждый луч отслеживается от камеры
- Реалистичные отражения, тени, глобальное освещение
- Very slow без hardware support

### 6.2 RT Cores

**NVIDIA RTX (2018):**

- Dedicated RT cores
- Hardware-accelerated ray-triangle intersection
- BVH (Bounding Volume Hierarchy) traversal

**Как работает RT Core:**
```

Ray → BVH Traversal → Triangle Intersection → Result
      (RT Core)        (RT Core)              (Shader)
```

**Пример: Ray Tracing в Vulkan/GLSL**

```glsl

// Ray tracing shader
#version 460
#extension GL_EXT_ray_tracing : require

layout(binding = 0) uniform accelerationStructureEXT topLevelAS;
layout(binding = 1, rgba8) uniform image2D image;

void main() {
    vec3 origin = ...;
    vec3 direction = ...;
    
    // Hardware-accelerated ray tracing
    rayQueryEXT rayQuery;
    rayQueryInitializeEXT(rayQuery, topLevelAS, 
                          gl_RayFlagsNoneEXT, 
                          0xFF, origin, 0.01, direction, 1000.0);
    
    while(rayQueryProceedEXT(rayQuery)) {
        // RT Core обрабатывает intersection
    }
    
    if (rayQueryGetIntersectionTypeEXT(rayQuery, true) != 
        gl_RayQueryCommittedIntersectionNoneEXT) {
        // Hit: вычисляем цвет
        vec3 color = ...;
        imageStore(image, ivec2(gl_LaunchIDEXT.xy), vec4(color, 1.0));
    }
}
```

**Производительность:**

- Software ray tracing: ~1 FPS (на CPU)
- Hardware RT cores: 30-60 FPS (на RTX GPU)
- **Ускорение: 30-60x**

**Применения:**

- Realistic lighting в играх
- Reflections, refractions
- Global illumination
- Path tracing для кино (offline rendering)

### 6.3 Hybrid Rendering

**Современный подход:** Комбинация rasterization + ray tracing

```

Base Pass (Rasterization)     → Быстро, 60+ FPS
  └── Ray Traced Reflections   → Медленно, но реалистично
  └── Ray Traced Shadows       → Точные тени
  └── Ray Traced GI            → Глобальное освещение
```

**Пример: Hybrid в игре**
- Rasterization: геометрия, текстуры, базовое освещение
- Ray Tracing: только отражения и тени (частично)
- Результат: 60 FPS с реалистичными эффектами

## 7. AI и Tensor Cores

### 7.1 Tensor Cores

**Специализированные блоки для matrix operations:**

```

D = A × B + C
```

Одна инструкция выполняет умножение 4x4 матриц.

**Использование:**

- Deep learning (training, inference)
- DLSS (AI upscaling)

### 7.2 DLSS (Deep Learning Super Sampling)

**Идея:**

- Рендерить в низком разрешении (1080p)
- AI upscaling до 4K
- Performance boost + качество

**Как работает DLSS:**
```

1. Render в низком разрешении (1080p) → быстро
2. Motion vectors (куда движутся объекты)
3. Tensor Core обрабатывает через нейросеть
4. Upscale до 4K с восстановлением деталей
5. Результат: качество близко к нативному 4K, но быстрее
```

**Производительность DLSS:**

- Native 4K: 30 FPS
- DLSS Quality (4K from 1440p): 60 FPS, качество ~95%
- DLSS Performance (4K from 1080p): 90 FPS, качество ~85%

**Другие AI upscaling технологии:**

- **AMD FSR** (FidelityFX Super Resolution): Software-based, работает на любых GPU

- **Intel XeSS**: AI upscaling для Intel Arc

- **NVIDIA DLSS**: Hardware-accelerated (требует Tensor Cores)

## 8. Оптимизация GPU кода

### 8.1 Профилирование

**Инструменты:**

- **NVIDIA Nsight Compute**: Детальный анализ kernel

- **NVIDIA Nsight Systems**: Timeline профилирование

- **AMD Radeon GPU Profiler**: Для AMD GPU

**Метрики производительности:**
```

Occupancy          → % использования SM (цель: >50%)
Memory Throughput  → Bandwidth использования (цель: >80%)
Instruction Throughput → Сколько инструкций выполняется
```

### 8.2 Common Optimizations

**1. Maximize Occupancy**

```c

// Плохо: мало threads per block
kernel<<<1000, 32>>>();  // 32 threads/block

// Хорошо: больше threads per block
kernel<<<125, 256>>>();  // 256 threads/block → лучше occupancy
```

**2. Avoid Divergence**

```c

// Плохо: divergence в warp
if (threadIdx.x < 16) {
    // 16 threads идут сюда
} else {
    // 16 threads идут сюда
}  // Обе ветки выполняются последовательно

// Хорошо: все threads идут одним путём
int value = array[threadIdx.x];  // Нет divergence
```

**3. Coalesced Memory Access**

```c

// Хорошо: последовательный доступ
int i = blockIdx.x * blockDim.x + threadIdx.x;
data[i] = ...;  // Coalesced

// Плохо: случайный доступ
int i = blockIdx.x * blockDim.x + threadIdx.x;
data[random[i]] = ...;  // Uncoalesced → медленно
```

**4. Использование Shared Memory**

```c

// Кэширование данных в shared memory
__shared__ float cache[256];
cache[threadIdx.x] = global_data[blockIdx.x * 256 + threadIdx.x];
__syncthreads();
// Использование cache вместо global_data → быстрее
```

### 8.3 Performance Tips

**DO:**

- ✅ Использовать shared memory для часто используемых данных
- ✅ Максимизировать occupancy (threads per block)
- ✅ Обеспечить coalesced memory access
- ✅ Минимизировать Host-Device transfers

**DON'T:**

- ❌ Слишком маленькие или большие block sizes
- ❌ Divergence в warps
- ❌ Частые синхронизации (`__syncthreads()`)
- ❌ Копирование данных туда-сюда без необходимости

## 💡 Key Takeaways

- **GPU эволюционировали** от простых 2D accelerators к массивно-параллельным процессорам с тысячами ядер

- **Архитектура GPU** оптимизирована для параллельных задач — тысячи простых ядер vs десятки сложных в CPU, trade-off: быстры для параллелизма, медленны для последовательных задач

- **GPGPU** расширила применение GPU за пределы графики — ML, научные вычисления, криптовалюты, обработка видео с ускорением в 10-100x

- **Специализированные блоки** (RT cores для ray tracing, Tensor cores для AI) ускоряют конкретные задачи на порядки (30-100x)

- **Memory hierarchy** критична для производительности — правильное использование shared memory, coalesced access и минимизация transfers могут ускорить код в 10-100 раз
