## Answer Key

1. **B** - Процессы нужны для предсказуемости, документирования знаний и уменьшения зависимости от людей

2. **C** - "Maximum rules" противоречит принципу "Minimal viable process"

3. **B** - Процесс внедряется, когда есть реальная проблема, которую он решает

4. **B** - Правильный порядок: Identify → Design → Pilot → Iterate → Roll Out → Maintain

5. **B** - Pilot нужен, чтобы найти проблемы до полного rollout и собрать feedback

6. **B** - Вовлечение команды создаёт ownership и улучшает adoption

7. **B** - 4-8 часов (business hours) — разумный SLA для первого review

8. **D** - P1 — Production down, все пользователи affected

9. **B** - Показать проблему, вовлечь команду, начать с малого

10. **B** - Метрики нужны, чтобы понять, работает ли процесс, и находить bottlenecks

11. **C** - Lines of Code не входит в DORA metrics

12. **B** - Удалять, когда проблема не существует или overhead превышает benefit

13. **B** - Daily Standup: 15 минут максимум

14. **B** - Retrospective: только команда, без stakeholders

15. **B** - Kanban лучше для support/maintenance с непредсказуемым потоком

16. **B** - Handoff: active issues, recent deployments, upcoming changes, fragile areas

17. **C** - Хранение только в головах — плохая практика

18. **B** - Owner нужен, чтобы следить за соблюдением и обновлять процесс

19. **B** - Между хаосом и бюрократией — минимально достаточный баланс

20. **B** - Quarterly review процессов рекомендуется

## Scoring Guide

- **18-20 правильных (90-100%)**: Отлично! Вы готовы выстраивать процессы в команде
- **14-17 правильных (70-89%)**: Хорошо. Повторите framework внедрения и DORA metrics
- **10-13 правильных (50-69%)**: Удовлетворительно. Рекомендуется перечитать лекцию
- **Менее 10 правильных (< 50%)**: Необходимо внимательно изучить материал
